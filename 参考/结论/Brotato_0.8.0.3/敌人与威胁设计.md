# Brotato v0.8.0.3 敌人与威胁设计

> [数值设计报告.md](数值设计报告.md) §1~§2 拆过敌人的**数值曲线**（线性、斜率写死在 `.tres` 里）
> 与波次投放节奏；这篇补的是另一半：**威胁是怎么组装出来的**——
> 移动行为 × 攻击行为的正交组合、Boss/精英的状态机、三条互相独立的刷怪流、以及掉落的三层递减。
> 版本口径：`Brotato_0.8.0.3/`，只对 zone_1 的 20 波成立。

---

## 0. 一句话结论

Brotato 的敌人**没有 AI**，只有**两个正交的行为槽**：
一个 `MovementBehavior`（5 种）+ 一个 `AttackBehavior`（3 种），
26 个敌人就是这两个槽的不同填法加一张数值表。
**威胁感不是靠单个敌人做出来的，是靠"同屏组合"和"投放节奏"做出来的。**

三条互相独立的刷怪流叠在一起才是玩家实际面对的压力：
波次自带组（117 组，34 组被危险等级门控）、
**全波次常驻组**（树 + 宝箱怪，查 `_波次刷怪组.csv` 查不到，挂在 `main.tscn` 上）、
以及兽潮/精英组（挂在 `WaveManager` 的导出数组上）。

## 1. 先纠正一个表的口径

`配置CSV/_敌人总表.csv` 有 28 行，但**不是 28 个敌人**：

## 2. 威胁的组装方式：两个正交的行为槽

### 2.1 五种移动行为

`源码/entities/units/movement_behaviors/`：

| 行为 | 逻辑 | 参数 |
|---|---|---|
| （不挂） | 默认直冲玩家（`FollowPlayerMovementBehavior`） | — |
| `StayInRangeFromPlayer` | 维持与玩家的固定距离，**远了靠近、近了后退** | `target_range`（±100 随机） |
| `TargetRandPos` | 在地图里随机游走，到点换点 | — |
| `TargetRandPosAroundPlayer` | 每次取玩家周围 `±range` 的随机点 | `range_around_player`（默认 300，±100） |
| `FollowRandPosAroundPlayer` | 开局定一个**固定偏移量**，此后永远保持这个相对位置 | `range_around_player`（默认 200） |

`TargetRandPosAroundPlayer` 和 `FollowRandPosAroundPlayer` 的差别很容易看漏：
前者**每到一个点就重新随机**（表现为绕着你乱窜），
后者的偏移量在 `init()` 里只算一次（表现为**像卫星一样吊在你旁边固定方位**）。

### 2.2 三种攻击行为

`源码/entities/units/enemies/attack_behaviors/`：

| 行为 | 逻辑 | 关键参数 |
|---|---|---|
| （不挂） | 只有接触伤害 | — |
| `ChargingAttackBehavior` | 冷却到 + 在 `[min_range, max_range]` 内 → 播放蓄力动画 → 锁定方向 → 以 `charge_speed` 冲 `charge_duration` 秒 | `cooldown` `charge_speed` `charge_duration` `target`(玩家/玩家附近随机点) |
| `ShootingAttackBehavior` | 冷却到 + 在射程内 → 发射 `number_projectiles` 发 | 20 个导出参数，见 §3 |
| `SpawningAttackBehavior` | 冷却到 → 召唤 `nb_to_spawn` 只指定敌人 | `enemy_to_spawn` `nb_to_spawn` `spawn_in_radius_around_unit` |

**冷却全部带随机化**：`rand_range(cooldown - max_cd_randomization, cooldown + max_cd_randomization)`，
单位是物理帧（60 帧 = 1 秒）。这一条随机化就足够让同屏同类敌人不齐射，
是"看起来有 AI"的最低成本做法。

`ChargingAttackBehavior` 有一个值得抄的细节：
`start_shoot()` 时 `_can_move = false`（**蓄力期间原地不动**），
`shoot()` 才解锁并把 `_move_locked = true` 锁住转向。
也就是**冲锋方向在蓄力开始的那一刻就定死了**——
这给了玩家一个明确的、可以靠走位规避的读条窗口，而不是无解的追踪。

### 2.4 七个"带机制"的敌人，每个只有十几行代码

绝大多数敌人零代码，只是行为槽 + 数值。真正写了脚本的只有这几个
（`源码/entities/units/enemies/<编号>/`）：

| 编号 | 机制 | 代码量 |
|---|---|---|
| `005` | 每隔一段时间 `bonus_speed += 45`，最多 10 次（**+450 速度**）；**一旦碰到玩家就清零** | 20 行 |
| `007` | 每 4 秒给光环内一只随机敌人**永久**加 `HP×1.5 / 伤害+25% / 速度+50%`，一只只吃一次 | 40 行 |
| `008` | 被**远程武器**命中时 25% 概率立刻反射一发随机方向弹；近战打它不触发 | 10 行 |
| `012` | 进入其光环的敌人回复 `100 + 10×(波次-1)` 血 | 20 行 |
| `016` | 死亡时在半径 200 内**分裂出 3 只 017** | 12 行 |
| `023` | 召唤 1 只 024 之后**立刻自杀** | 6 行 |
| `026` | 冲锋锁定期间每 30 帧额外射 2 发 | 15 行 |

**005 的"撞到你就清零"是整套敌人设计里最精巧的一条**：
它把"越追越快"这个本来会失控的机制，变成了一个**玩家可以主动重置的计时器**——
故意让它蹭一下反而是正确操作。十几行代码造出了一个真正的操作决策。

**007 和 012 是仅有的两个"针对玩家输出模型"的敌人**：
007 让"不优先点掉支援"的代价被永久固化（加成不会随它死亡消失），
012 让 DPS 不足的构筑**永远打不死它护着的目标**。
两个都放在 w7 / w16，正好卡在玩家该有稳定输出的时点。

## 3. 远程伤害走的是另一套数值

这是最容易算错的一条：**敌人弹幕的伤害不来自 `_敌人总表.csv`。**

`_敌人总表.csv` 的「伤害 / 每波+伤害」是 `unit.stats` 上的**接触伤害**；
而 `ShootingAttackBehavior` 有**自己的** `damage` 和 `damage_increase_each_wave`
（`attack_behaviors/shooting_attack_behavior.gd:8-9`），
在 `spawn_projectile()` 里独立计算：

```gdscript
projectile.call_deferred("set_damage",
    ((damage + ((RunData.current_wave - 1) * damage_increase_each_wave)) as int))
```

各射手的弹幕参数（从 `.tscn` 解出，冷却单位是帧）：

| 编号 | 冷却 | 射程 | 弹数 | 散布 | 弹速 | 弹幕伤害/波 | 特殊 |
|---|---:|---:|---:|---:|---:|---:|---|
| 003 | 120 | 700 | 1 | 0 | 600 | +0.75 | — |
| 008 | — | 500 | 1 | 0 | 200 | +1.0 | 冷却 1e9，**只能被反击触发** |
| 017 | 120 | **≥200** | 1 | 1.2 | 500 | +1.0 | `min_range=200`，**贴脸反而不挨打** |
| 024 | 75 | 500 | 1 | — | 0 | +1.0 | 弹速 0 + 落点随机（范围 200） |
| 025 | 60 | 500 | 2 | 0.8 | 300 | +1.0 | `constant_spread`，固定夹角 |
| 026 | 30 | 99999 | 2 | 1.0 | 600 | +0.75 | 冲锋期间才射 |
| 011 | 50 | 2000 | **10** | — | **0** | **+1.15** | 落点砸在玩家周围 500 内，开场 120 帧不打 |
| 021 | 75 / 45 | 1000 / 2000 | 4 / 3 | — | 0 | +1.15 / +0.75 | 两段，都是落点型 |
| 022 | 75 / — | 2000 | 6 / 10 | 1.0 | 400 / 0 | +1.15 | 两段 |

三条读法：

- **`projectile_speed = 0` + `spawn_projectiles_on_target = true` 是"砸地"型**：
  弹体不飞行，直接生成在玩家周围的随机点上。所有 Boss/精英的主力弹幕都是这一类，
  因为它无视距离、逼玩家持续移动，而不是靠躲子弹线。
- **017 的 `min_range = 200` 让"贴脸"成为有效解**——射程有下限的敌人，近战构筑反而克它。
- **011/021/022 的 `damage_increase_each_wave = 1.15` 比接触伤害的 1.5 低**，
  但弹数多（10 / 4 / 6~10）。Boss 的压力是**面积**而不是**单发**。

## 4. Boss 与精英共用同一个状态机

`源码/entities/units/enemies/boss/boss.gd` + `boss_state.gd`。
`Boss` 是 `Enemy` 的子类，全游戏只有 5 个单位用它：`010` `011`（第 20 波双 Boss）
和 `020` `021` `022`（三个精英）。

### 4.1 切换条件：血量**或**计时，谁先到算谁

```gdscript
func _on_CheckStateTimer_timeout() -> void:
    elapsed_time += 1
    for i in _states.size():
        if _current_state < i and (current_stats.health <= (max_stats.health * _states[i][0])
                                   or elapsed_time >= _states[i][1]):
            on_state_changed(i)
            _current_state = i
            _current_movement_behavior = _states[i][2]
            _current_attack_behavior   = _states[i][3]
```

每个 `BossState` 只有两个导出字段：`hp_start`（血量比例）和 `timer_start`（秒）。
**"或"的设计是关键**：高 DPS 构筑靠血量推进阶段、低 DPS 构筑靠时间推进阶段，
两种玩家都会看到完整的阶段演出，**不会出现"秒杀跳过全部形态"或"卡在一阶段磨到超时"**。

### 4.2 五个单位的阶段表

| 单位 | 阶段 | 触发（血量 / 秒） | 换成什么 |
|---|---|---|---|
| `010` Boss A | State1 | 50% / 45s | 旋转弹幕 `Pivot` 转速 ×1.25 |
| `011` Boss B | State1 | 75% / 30s | — |
| | State2 | 40% / 60s | `reset_stats(0, 1.5)` → **移速 ×1.5** |
| `020` 犀牛 | State1 | 60% / 25s | 冲锋中的伴随弹幕从 2 发 spread 1.0 换成 **4 发 spread 2.0** |
| `021` 屠夫 | State1 | 70% / 20s | 4 发落点斩击（间隔 75f） |
| | State2 | 40% / 40s | 3 发随机方向斩击（间隔 45f，动画 ×3） |
| `022` 僧侣 | State0 | 75% / 10s | 召唤 3 只 `023`（半径 300，每 1 秒） |
| | State1 | 50% / 30s | 6 发扇形弹（spread 1.0，弹速 400） |
| | State2 | 30% / 40s | 召唤 2 只 `025`（半径 500，每 2 秒） |

僧侣的召唤链值得单说：**`022 → 023 → 024` 是两级链**——
僧侣召唤孵化器，孵化器再孵出斩击兵然后自杀。
所以对付僧侣的正解是**打断中间那一级**（023 只有 5 + 3×波 血），
而不是去追最终产物。三个敌人、不到 10 行代码，做出了一条有解法的威胁链。

### 4.3 两处血量折扣

`boss.gd:init()`：

```gdscript
if RunData.effects["double_boss"] and RunData.current_wave == RunData.nb_of_waves:
    max_stats.health = round(max_stats.health * 0.75)     # 危险 5 的双 Boss，各打 75 折
elif RunData.current_wave <= 12:
    max_stats.health = round(max_stats.health * 0.75)     # 第 12 波及以前出现的精英，打 75 折
```

第二条对应的是**第一个精英（w11~12）**——它是玩家这一局第一次见到精英，
75 折是一个不写在任何 UI 上的新手保护。
第一条则让危险 5 的总 Boss 血量 = `29900 × 0.75 × 2 = 44850`，
比危险 <5 的单 Boss 29900 高 **1.5 倍**，而不是想当然的 2 倍。

另外 `Boss:take_damage()` 是 `damage_against_bosses` 这条属性唯一的消费点，
`get_giant_factor()` 则是 `giant_crit_damage / 1000`（注意是 1000 不是 100）。

## 5. 投放：三条互相独立的刷怪流

玩家同屏面对的敌人来自三个完全不同的来源，**只有第一条能在 `_波次刷怪组.csv` 里查到**。

### 5.1 波次自带组（117 组，在表里）

`配置CSV/_波次刷怪组.csv`，字段含义：

| 字段 | 作用 |
|---|---|
| `出现时机秒` | 从波次**开始**算起多少秒后触发（代码里是 `time_left <= wait_time - spawn_timing`） |
| `重复次数` / `重复间隔` | 触发后再重复几次、每次隔几秒 |
| `间隔递减` / `最小间隔` | 每重复一次间隔减去 `间隔递减`，下限 `最小间隔` —— **这是波内压力递增的唯一来源** |
| `最低难度` | 危险等级门控，34 组被门控 |
| `沿边缘刷` / `区域` | 刷在地图边缘，还是某个半径内 |

**`间隔递减` 值得单独说**：波次自带组里绝大多数是 0（匀速投放），
真正用到它的是兽潮组（§5.3）。这是"同一套数据结构，靠一个字段区分两种节奏"的例子。

### 5.2 全波次常驻组（表里查不到）

挂在 `资源/main.tscn` 的 `WaveManager.groups_data_in_all_waves` 上，
`wave_manager.gd:28-30` 在每一波开始时无条件塞进当前波次数据里。只有两组：

| 组 | 内容 | 时机 | 重复 |
|---|---|---|---|
| `000_all/group_1` | **树** 1~2 棵，`spawn_chance = 0.33` | 开局 10 秒 | 999 次，每 10 秒 |
| `000_all/group_2` | **宝箱怪 013** ×1，`spawn_chance = 0.1` | 开局 25 秒 | 3 次，每 15 秒 |

这两组解释了两件在表里看不出来的事：

- **树是每一波都会不断长出来的**，不是场景装饰。树的 `掉落率 1.0` 意味着**砍树必掉消耗品**，
  20% 概率是道具箱；再加上材料价值 3 和 `金币散布 75`，
  树是一条完全独立于杀怪的经济来源。`trees` 这条效果加的就是这一组的 `flat_mod`。
- **宝箱怪 013 每波有 4 次 10% 的机会出现**（首次 + 3 次重复），
  材料价值 8、必掉消耗品、且**必掉道具箱**（见 §6.3）。

### 5.3 兽潮组（表里查不到）

挂在 `WaveManager.horde_groups`，只在兽潮波追加。5 组全部 `is_horde = true`：

| 组 | 单位 | 起始时机 | 初始间隔 | 递减 | 下限 | 波次门槛 |
|---|---|---:|---:|---:|---:|---|
| group_1 | 001×4 + 002×4，**从地图边缘刷** | 1s | 5s | −1 | 2s | — |
| group_2 | 001×4 | 8s | 4s | −1 | 2s | — |
| group_3 | 002×4 | 15s | 3s | −1 | 1s | — |
| group_4 | 014×8~9 | 25s | 2s | −1 | 1s | **w14+** |
| group_5 | 015×6~7 + 001×4 + 002×4 | 30s | 2s | −1 | 1s | **w15+** |

**五组的起始时机是错开的（1/8/15/25/30 秒），而且每组的间隔都在递减。**
所以兽潮波不是"一次性倒一堆怪"，是一条**五段叠加、各自加速**的压力曲线：
前 15 秒只有三组在跑，25 秒后第四组进场，30 秒后五组同时把间隔压到 1~2 秒。

补偿写在 `main.gd:462`：兽潮波的材料掉落概率 `× 0.65`，
且 `manage_harvesting()` 里的和平主义加成减半。**兽潮怪多但穷。**

### 5.4 精英组

`WaveManager.elite_group` 是一个 `wave_units_data` 为空的壳，
`init_elite_group()` 在运行时按 `elites_spawn` 里记下的 `my_id` 往里填单位。
`is_boss = true` 让它走 `queue_to_spawn_bosses` 这条独立队列。

### 5.5 两条全局约束

`源码/global/entity_spawner.gd`：

| 常量 | 值 | 作用 |
|---|---:|---|
| `MIN_DIST_FROM_PLAYER` | **300** | 刷怪点距玩家不足 300 就重roll，**永远不会在脸上刷怪** |
| `_current_wave_data.max_enemies` | **100** | 超上限时**随机杀掉多余的敌人**并把它们的 `can_drop_loot` 置 false |
| `MAX_STRUCTURES` | 50 | 玩家的炮台/构筑物上限 |
| `MAX_GOLDS`（`main.gd:18`） | 50 | 场上材料实体超 50 时，新掉的材料**合并进一个已有实体**（value 相加、体积变大） |

`max_enemies` 那条是**性能剔除，但玩家会为此损失材料**——
被剔掉的敌人不掉落任何东西。它同时被计进 `enemies_removed_for_perf`，
喂给和平主义的波末结算，所以和平主义流在同屏爆满时反而受益。

## 6. 精英与兽潮的排程

`源码/singletons/run_data.gd:188-223` 的 `init_elites_spawn(base_wave = 10, horde_chance = 0.4)`，
每局开始时算一次：

```
危险 < 2       → 一个都不出
危险 2 ~ 3     → 1 个
危险 4 ~ 5     → 3 个

第 1 个：波次 rand(11, 12)
第 2 个：波次 rand(14, 15)
第 3 个：波次 rand(17, 18)   ← 强制 ELITE，不会是兽潮

每个 40% 概率是兽潮（HORDE）、60% 是精英（ELITE）
精英从 3 个里**不放回**抽取
角色 character_jack → horde_chance = 0（永远不出兽潮）
```

三条设计读法：

1. **危险 0~1 完全没有精英和兽潮。** 这两档只有"新敌人"（`EFFECT_NEW_ENEMIES` 解锁被门控的 34 组刷怪组）。
   也就是说**前两档难度改的是敌人种类，第三档起才改数值，第四档起才改结构**：

   | 危险 | 新敌人 | 精英/兽潮 | `enemy_health` / `enemy_damage` | 更多精英 | 双 Boss |
   |---:|:-:|:-:|---:|:-:|:-:|
   | 0 | | | — | | |
   | 1 | ✓ | | — | | |
   | 2 | ✓ | ✓（1 个） | — | | |
   | 3 | ✓ | ✓（1 个） | +12 / +12 | | |
   | 4 | ✓ | ✓（3 个） | +26 / +26 | ✓ | |
   | 5 | ✓ | ✓（3 个） | +40 / +40 | ✓ | ✓ |

2. **排程是开局就定死的，商店 UI 会提前告诉你**
   （`ui/menus/shop/elite_container.gd` 读 `RunData.elites_spawn` 显示还有几波来精英）。
   这是 Brotato 极少数**主动向玩家披露未来随机结果**的地方——
   因为精英是需要提前配装应对的，藏起来只会变成纯粹的意外死亡。

3. **不放回抽精英**保证一局最多各见一次犀牛/屠夫/僧侣，
   和 Balatro 的 Boss 轮转（`bosses_used` 取最小值那批）是同一个思路：
   用"轮转"代替"独立随机"，把体验从"可能连撞两次"变成"轮流考一遍"。

> ⚠ `main.gd:50` 的 `_elite_killed_bonus` 和 `main.gd:901` 的 `elite_end_wave_bonus`
> 在整个包里**只被读取、从未被赋值**，恒为 0。
> `manage_harvesting()` 里那两项加数是死代码，波末收获实际只有
> `stat_harvesting + 和平主义加成`。

## 7. 掉落：三层各自递减

`源码/main.gd:455-512`。一只敌人死了之后走三道独立的判定：

### 7.1 材料（`spawn_gold`）

```
spawn_chance = (1 + diff_factor) × gold_drops                      若 wave < 5
             = max(0.25, (1 - wave × 0.015 + diff_factor) × gold_drops)  否则
兽潮波再 × 0.65
```
命中后按 `unit.stats.value` 生成**这么多个**材料实体（不是一个实体带 N 点）。
详细曲线见 [数值设计报告.md](数值设计报告.md) §3.1。

### 7.2 消耗品（`spawn_consumables`）

```
drop_chance = min(1, base_drop_chance × (1 + 幸运/100))
无尽期再 ÷ (1 + 无尽系数 × 3)
always_drop_consumables 的单位直接置 1.0
```

`base_drop_chance`（表里的「掉落率」列）分布很陡：
普通杂兵 0.01~0.03，**宝箱怪 013 / 三个精英 / 两个 Boss / 树 全是 1.0**。

### 7.3 道具箱：**同一波里越掉越难**

```gdscript
var item_chance = (unit.stats.item_drop_chance * (1 + luck)) / (1 + _items_spawned_this_wave)
```

**分母是"这一波已经掉出来的道具箱数"**——
第一个道具箱按原概率，第二个减半，第三个只剩三分之一。
这是全局唯一一条**波内自我抑制**的掉落机制，用来防止幸运流把一波刷爆。

两个例外绕过它：

- `always_drop_consumables && item_drop_chance >= 1.0 && wave <= 20` → `item_chance = 1.0`。
  命中这一条的是**宝箱怪 013**：无论这波已经掉了多少，它照样必给一个道具箱。
- `unit is Boss && wave <= 20` → 掉的是 **`legendary_item_box`（传奇道具箱）**。
  所以**三个精英每个必给一个传奇道具箱**，这才是危险 2 以上打精英的真正回报——
  材料价值 10 只是零头。

### 7.4 合并与剔除

- 场上材料实体超过 `MAX_GOLDS = 50` 时，新掉的材料**合并进一个随机已有实体**，
  `value` 相加、`scale` 按 `value × 0.05` 放大。所以后期地上那几颗大材料是"打包"出来的，
  **不捡就是真的全丢**。
- 同屏敌人超 100 被剔除时 `can_drop_loot = false`，那部分材料**根本不会生成**。

## 8. 六条可以直接拿走的设计手法

1. **把敌人拆成"移动槽 × 攻击槽 + 一张数值表"。** 5 × 3 的正交组合加斜率表就撑起 26 个敌人，
   真正写代码的只有 7 个。**威胁感来自同屏组合与投放节奏，不来自单个敌人的复杂度。**
2. **冲锋要有"锁定方向"的读条窗口**（`_can_move = false` 期间原地蓄力，`shoot()` 后方向已定死）。
   可规避的威胁才是玩法，无解追踪只是伤害。
3. **Boss 阶段用"血量或计时"双触发。** 高 DPS 靠血量推进、低 DPS 靠时间推进，
   两种玩家都能看完全部形态，既不会被秒杀跳过也不会卡死在第一阶段。
4. **一个字段造两种节奏**（`间隔递减`）。波次自带组填 0 是匀速投放，
   兽潮组填 1 就变成自我加速的压力曲线，数据结构完全不用改。
5. **提前披露需要配装应对的随机结果。** 精英排程开局就定死，商店 UI 明着告诉玩家还有几波来精英——
   需要准备的威胁藏起来只会变成意外死亡。
6. **给"越滚越大"的掉落加一条波内自我抑制**（`/(1 + 本波已掉道具数)`），
   再单独开几个白名单例外（宝箱怪、精英的传奇箱）。
   这比给幸运加硬上限更自然：**幸运仍然有用，只是同一波内的边际收益在掉。**

两条反面观察：

- **敌人 `009` 做完了资源却没接入**（无任何波次、刷怪组或召唤方引用它），
  和 `_升级总表.csv` 里那 14 张没挂进 `ItemService.upgrades` 的升级卡是同一类问题
  （见 [升级卡系统.md](升级卡系统.md) §2.3）。
  **"资源存在 ≠ 内容存在"在这个包里出现了至少两次，核对时必须从消费端倒着查。**
- **性能剔除会静默吞掉玩家的材料**（超 100 只时随机杀敌并禁掉掉落）。
  从数值上说这等于给"把怪堆满屏"的玩法一个隐形惩罚，但玩家完全看不到这件事在发生。
