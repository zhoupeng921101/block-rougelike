# ui-blocking-layer.md — 全屏拦截层的共存与退出核对

> 按需规则:**新增或改动全屏拦截层**时读。承载两道核对程序(谁被盖住 / 怎么撤掉),不重复 UILayer 的事实描述(那在 `.claude/references/tengine/ui-lifecycle.md`「UILayer 层级」节)。

**适用**:客户端 UI 开发(devflow-ui / devflow-client 段与主工程通道同此)。

## 触发面(窄,不是改任意 UI 都查)

改动落在以下任一项时才走本卡:

- 新增一个**铺满屏且吃点击**的节点(遮罩、闸窗背景、引导遮罩、模态底板;判据 = `raycastTarget` 为真且尺寸覆盖全屏,或实现 `ICanvasRaycastFilter` 且在某些状态下整片返回 true)。
- 改动这类节点的**拦截条件**(什么时候拦、什么时候放行、开不开洞)。
- 改动任何窗的 `UILayer` 或 `fullScreen`。

## 核对一:谁被盖住

**问一句:这层拦截生效期间,屏幕上还可能有谁,它们需要玩家操作吗?**

逐个列出可能同时在场的窗,按 `UILayer` 值比大小(值大压值小,枚举与含义见 ui-lifecycle.md)。**被这层盖住、而又需要玩家点的窗,就是缺陷**——不是"体验不好",是玩家卡死在那一屏。

同时在场的来源容易漏的三类:①自动弹窗(经被动入口排队、按条件自己弹出的);②系统层的窗与错误框(错误日志窗、二选一确认框);③本模块自己在别的步骤/状态下开出来的窗(教学的演示步、结算后的连续展示)。

## 核对二:这层怎么撤

**问一句:这层拦截的每一条退出路径上,都有人把它撤掉吗?**

把退出路径列全:成功是一条,**其余每条失败各算一条**——超时、重试耗尽、资源加载失败、存档读写失败、用户取消。逐条读到底:那条路上的守卫(阶段判断、状态位、早退 `return`)会不会把撤窗那一步整个跳过。**任何一条路上没有「撤掉这层 + 给玩家下一步」的收口,就是缺陷**——玩家永久停在那一屏,且这次屏幕底下什么都没有,连可点的东西都不存在。

判据不是"代码里有没有 Close 调用",是**那条具体路径走不走得到它**。

容易漏的是**第二阶段的失败**:第一次失败有出口(弹重试框),而"失败 → 自动重试 → 重试再耗尽"那条路没有——写重试的人默认总会成功,写闸窗的人默认失败都走第一条出口。同款的还有按阶段早退的守卫:`if (!已进主界面) return;` 这类,在"还没进主界面"时把整个失败处置跳过,而那恰恰是闸窗铺满屏的阶段。

## 接错症状

两道核对对应两种症状,都不报错、不抛异常。

漏了核对一:**点什么都没反应**。玩家侧无从判断是卡死还是没点中;日志侧只有"进度不推进",没有任何指向层级的线索。定位手段是对着那个点做一次 `EventSystem.RaycastAll`,看命中列表首项是谁、`sortingOrder` 多少——两个数字直接给出答案,比读代码快得多。

漏了核对二:**画面停在闸窗上不动**,进度条卡在某个百分比,没有任何提示或按钮。日志里能看到失败已经发生(重试耗尽、加载失败),但那之后再无任何 UI 动作——日志与画面之间这段空白就是缺口所在,顺着最后一条失败日志找它的订阅方,看守卫把它挡在哪。

## 不做

不要求为此改层级设计,也不要求把拦截层降层——引导要压在弹窗之上、闸窗要压在一切之上,都是有意的。本卡只要求在改动当时把两份清单各过一遍:共存清单里"需要操作却被盖住"的那些窗给出处置(让开、开洞、延后弹出、或先关掉对方);退出路径清单里没有收口的那几条补上出口。
