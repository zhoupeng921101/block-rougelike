# refs-check — references ↔ 代码 事实核验

本 skill 管一件事:**文档与注释里写的代码事实,与代码实际是否一致**。

**与其他检查的边界**:`/rules-audit` 管规则之间的关系(副本 / 死规则 / 矛盾)与写作规约合规;`/devflow-check` 管 devflow 族的引用完整性与脚本↔卡片同步,且**明文不验工程实体**(其检查项 2:「规则栈文件里出现的 `Assets/` 等工程实体路径不验存在,代码现实由开发与自检覆盖」;其检查项 6 只核规则栈脚本里判据正则的着落,不验文档断言)。故「文档说的代码行为 ↔ 代码实际怎么写」这一面由本 skill 核,不替代二者。

**产品代码注释**容易读成与 `/rules-audit` 重叠、实为正交:`/rules-audit` 查项 8 明文不扫业务代码注释,理由是注释规约由 `tengine-conventions`「注释准入」在写入时约束、不回溯存量。那管的是**规约**;本 skill 回溯的是**事实**——注释里点名的符号还在不在。写入时的规约约束拦不住「当时写对、后来别处改了」这一类。

> **为什么卡内断言也要纳入**:2026-08-21 实测(block-client),`devflow-ui` 的「核对 impl(已知缺陷,必做)」步防的失效模式(生成器读 `Selection` 把他人回调写进本 impl)在同日的另一个提交里就已根治,规则却活了 40 天——因为它过期的表现是「每建一个面板多做一步无用核对」,不报错、不失败、无人显形。references 有本 skill 兜底,卡内断言过去没有。

| | 路径 |

## 范围选定

参数按主题、篇名或卡名给。`.claude/references/tengine/` 篇目的主题→篇目映射经 **CLAUDE.md「TEngine 框架知识路由」表**,本卡不复制这份映射;其余 skill 的 references 数量少、无路由表,直接按篇名点名。卡名(如 `/refs-check devflow-ui`)= 核该卡的代码断言,一张卡算一篇;`/refs-check 工程计划` = 核其工程现状段,算一篇。产品代码注释按**模块**点名(如 `/refs-check UIModule 注释`),一轮一个模块目录;不接受「全仓扫注释」——注释数量无界,套不上按篇核验的模型,硬跑的结果是抽样质量塌掉。

无参数时不默认全量:列出现役篇目请用户点名。一轮核一到三篇——全量比对要逐条回读代码,篇数越界会稀释复核质量。注释模块按一个目录算一篇。

## 阶段一:抽取待验断言

Read 目标篇正文,抽出可证伪的事实断言,分以下几类:

1. **API 签名** — 类型名、方法名、参数名与顺序、返回类型
2. **示例代码** — 片段里出现的调用形态
3. **存在性声明** — 「有 X 重载」「X 已废弃」「用 X 不用 Y」
4. **工具行为声明** — 「生成器只产窗一档」「菜单 X 报空引用清单」「Y 是只读生成物」「默认层是 Z」:凡描述某个工具/生成器**做什么、产出什么形态**的句子(卡内断言多属此类)
5. **符号引用** — 注释或文档正文里点名的别处符号:`<see cref="X"/>`、`<c>X</c>`、以及纯文本的 `类名.成员名`。**编译器不检查这些**(Unity 不开 XML 文档生成,实测编译警告里没有 CS1574),指向已删符号也无声,故只能靠本 skill 核

不可证伪的内容(设计取向、优先级建议、排查顺序)不在核验面,不因「读着像过时」就改。

**核产品代码注释时的取舍判据**:这条注释描述的是**本方法自己在做什么**,还是**别处的代码是什么样**?前者与代码同文件同批改、不会漂,跳过;后者才是核验面。
- 核:「与规则核心 X.Y 一致」「取代已下架的 Z」「对应 A 的 B 方法」「见 C 的注释」——引用了本文件之外的事实
- 不核:「这里取 2 倍是给冰壳留余量」「按行外列内遍历」——就地可验、不依赖别处

**跨架构变更的残留长这样**:一次架构变更(某层职责搬家、某个模块下架)之后,引用旧架构的描述留在原地。它的表现不是报错,而是**读的人据此做出错误的风险评估**——照着一个不存在的调用点去分析影响面。本 skill 在注释上最高价值的发现就是这类。本作的框架与 UI 核心是从 block-client 搬来的,搬来的注释与篇目常点名本作没有的底座层 `GameBase`、服务端、登录流程或 block-client 的业务窗:抽断言时对这类跨边界措辞额外留意,逐个 grep 落地。

**核 SKILL.md 时的取舍判据**:一条句子能不能用 grep 代码判真假。能 → 核;不能 → 整条跳过。
- 核:「`uiGenTypeName` 无第二个合法值」「`_Gen.g.cs` 置只读位」「生成器给新窗的默认层是 `UILayer.Window`」「Part 无生成器一档」
- 不核:「改动小不豁免」「呈报只承载索引与待办」「界外发现只报不做」——流程裁定,无代码事实可比

**已根治的规则长这样**:卡里写着「已知缺陷 / 必做核对 / 记得先做 X / 容易漏 Y」,而代码里那个失效模式的**成因已被移除**。这是本 skill 在卡上最高价值的发现——它不报错、不失败,只让人每次白做一步,因而能潜伏很久。抽断言时对这几类措辞额外留意:不要只验「这个 API 还在不在」,要验**「它防的那个失效模式还可能发生吗」**。成因没了 → 整步进阶段三删除,不是改写。

## 阶段二:逐条对代码验证(强制)

1. Grep 断言中的类型名 / 方法名,确认当前是否存在
2. Read 命中位置,抄下当前完整签名与 `文件:行号`
3. 按下表判定:

| 复核结果 | 处置 |
|---|---|
| 文档与代码一致 | 不动,计入核对通过 |
| 文档描述错(签名 / 参数名 / 重载集) | 阶段三按代码实际修正 |
| 文档提及的 API 已不存在 | 删除该段;有替代物则改指替代物 |
| 代码里的主流用法文档未覆盖 | 记为覆盖缺口进报告待裁定,不擅自扩写——新增章节是内容决策,不是事实修正 |

**红线**:未在代码中定位到出处的断言不得写入 references。宁可留在待确认清单里,不把一个错的换成另一个错的。

## 阶段三:修正

1. **最小 diff** — 只改被证伪的行与段;不重排章节、不统一文风、不顺手补充。
2. **保持该篇既有结构** — 不因核验改写头部。`.claude/references/tengine/` 各篇为首行 `# 标题` + 第二行 `> **适用场景**：… | **关联文档**：[xxx.md](xxx.md)`;`devflow-ui` 两篇为 `# 篇名 — 一句定位` + 导语引用块,照其原样。交叉引用一律写同目录相对链接。`新游戏/工程计划.md` 按仓根 `AGENTS.md` 的写法改,只动被证伪的那一条。

3. **产品代码注释只报不改** — 核出的问题写进报告的「待走 devflow 修正」栏,给出 `文件:行号` + 现注释原文 + 应改成什么 + 代码依据。**不在主工程直接改** `Assets/` 下任何文件,通道判据见「禁止事项」首条。
4. **示例可编译** — 修正后的代码片段与阶段二抄下的真实签名逐字一致。
5. 遵 `.claude/rules-ondemand/file-conventions.md`:覆盖式重写,不叠勘误注保留旧文。

## 阶段四:连带同步

1. **交叉引用** — Grep 被改动的 API 名在 references 全目录与 `新游戏/工程计划.md` 的其他出现点,同批改到一致(同一 API 常跨两篇,如资源加载 API 同时出现在 `resource-api.md` 与 `resource-patterns.md`)。
2. **路由与宿主卡指针** — 增删篇目、或改动使概述失准时同步:`.claude/references/tengine/` 篇目同步 **CLAUDE.md「TEngine 框架知识路由」表**(连同表下那段「本作的工程形态与这些篇目的出入」),`devflow-ui` 两篇同步其 SKILL.md「开工前」对该篇内容的一句话概述。
   **删改卡内整节/整步时另核 `devflow-check` 的不变量矩阵**:其「出现点」列按节点名, 指向被删的节即成失效指针。核对后仍有取舍的(该不该在矩阵里保留该行)进报告待裁定,不自行改矩阵——那是 `/devflow-check` 的写入面。
3. **evals** — Read `.claude/references/tengine/evals.json`,本次改动若触及某条的 `expected_patterns` / `forbidden_patterns` 字符串,同步该条,否则用例与新规范脱节。
4. **核心禁止事项** — 改动触及「核心禁止事项」任一条时,核 `.claude/rules-ondemand/tengine-conventions.md`「核心禁止事项」的表述是否需同步(该节为单一正本,无需跨文件比对)。

## 报告格式

- **已修正**:篇名 + 章节 + 一句问题 + 代码依据 `文件:行号`(逐条)
- **核对通过**:逐篇一句,含本轮抽验的断言条数(证明查过,不只报异常)
- **待走 devflow 修正**:产品代码注释里核出的问题,逐条给 `文件:行号` + 现注释原文 + 应改成什么 + 代码依据。这一栏是**下一个任务的输入**,写到能直接当简报用(无则省略本栏)
- **待裁定**:覆盖缺口、复核无定论项(无则省略本栏)

## 禁止事项

- 不改 `Assets/` 下任何文件——**注释也算**。核出的注释问题进报告的「待走 devflow 修正」栏,由用户按 devflow 立项修。本 skill 的写入面全在人工入库通道内(清单式提交、不推送),而产品代码改动属 devflow 通道,两者的提交与检查路径完全不同,混在一轮里做会让两类改动进同一个提交。
- 不写 `.claude/rules/`;devflow 族卡**只改其代码断言处**(判据见阶段一「核 SKILL.md 时的取舍判据」),流程条款分属 `/rules-audit` 与 `/devflow-check`。越界发现只在报告里建议跑对应 skill。
- git:修复经呈报后按人工入库通道处置(义务正本 = CLAUDE.md「devflow 适用面」人工入库通道条);本卡写入面都不在客户端自检读取面内(登记见 `校验库.ps1` `ClientGateScanSurface`),提交前不必先跑自检。
