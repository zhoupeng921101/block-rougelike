# 四类归因 · 合并后缺陷处置细则

devflow 卡「四类归因」节的细则正本;需求属「修一个已合并交付的缺陷」时 Read 本文执行。

## 四类归因矩阵

该缺陷本该被哪道拦截拦住?四选一,各对应固定修法,与修复同轮落地:

| 归因 | 修法 |
|---|---|
| 规则不存在(rule-missing) | 走规则准入新增(判据 `.claude/rules-ondemand/rule-authoring.md`;绑事件+保证等级,登记义务台账) |
| 规则存在但未装载(not-loaded) | 修装载信道(hook 路由/matcher 补键),不动规则正文 |
| 装载了但未遵从(not-followed) | 沿可执行化层级上爬一级(散文→注入→审查项→静态检查) |
| 检查存在但漏了(check-gap) | 修检查(正则/脚本),附漏检样本 |

## 预期取舍简化归因

缺陷无任何成文规则覆盖、唯有运行时测试才能拦(「重开发轻测试」的预期产物)时,归因记 `accepted-tradeoff` 一句话即可,不走四类归因修法;同一批修复内同类缺陷只归因一次(按缺陷类,不逐条)。三种情形禁走简化归因、必须完整四类归因:①缺陷违反任何成文规则(命名空间 / tengine-conventions / 按需规则篇等);②同类缺陷第二次暴露,不限发现渠道——每日审查报告/手测/用户反馈皆计(判据同 CLAUDE.md「修复前先定性(根治/补丁)」条:同类问题第二次出现禁止再补);③缺陷落在某道机器检查声称覆盖的范围内(check-gap 嫌疑)。
> 理由见 .claude/devflow/rationale.md#fast-track-anti-ritual

## 留痕

呈报必含归因结论;把一句说明写进临时文件,跑 `.claude/devflow/归因留痕.ps1 -Route <路由> -NoteFile <说明文件>` 落遥测(简化归因同样落遥测,`-Route accepted-tradeoff`)。
