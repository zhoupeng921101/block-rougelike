# daily-code-review — 每日审查/夜审(正确性审查唯一承载点)

在 Windows 本机对仓库近 24 小时改动执行代码审核。目标仓库 = 仓根 block-rougelike(记作 `<仓根>`,即主工作目录 `Demo/` 的父目录),审查面 = `<仓根>/Demo` 下的改动。`参考/`、`复刻/`、`新游戏/` 不归 devflow,按仓根 `AGENTS.md` 管,不在本审范围。

**定位**:开发期采用「重开发轻测试」,devflow 把正确性审查整体后移到本每日审查(交付前审什么见 devflow 第三步「自审」,正确性审查不在其内),故本轮是正确性缺陷合并入库后的主要拦截点,重点找正确性缺陷。程序正本在此文件。触发:用户显式 `/daily-code-review` 手动运行(**未启用定时任务**;要启用时 shim 只读本文件执行,不内联程序副本);不在常规 devflow 中自动触发。

## 执行步骤

1. **圈定范围**:仓库内用 git 收集当前分支(通常 main)最近 24 小时落在 `Demo/` 下的提交(`git log --since="24 hours ago" --stat -- Demo`)加工作区未提交改动(`git status` / `git diff`,同限 `Demo/`)。两者皆空 → 写一句话「今日无改动」简报到报告目录后结束。

2. **审查**:优先用 `/code-review` 以 high 档审查上述范围;不可用则读 diff 逐文件手工审。关注优先级:正确性缺陷(空引用、边界条件、状态机漏分支、异步/时序)> 规则核心与表现层的状态一致性(含局内存档的序列化往返、同一种子的可复现性)> 资源泄漏与生命周期(Unity 事件注册/反注册、UI 窗口生命周期)。含公共接口 / 事件 / 配置表结构改动的,核对其调用方 / 消费方是否同步。

3. **安全面专项核对**:改动涉及处理不可信输入(本地存档与配置文件的读入与反序列化、文件路径拼接、外部进程调用)时,按 `Demo/.claude/skills/devflow/references/security-review.md` 的视角清单对步骤 1 圈定的范围手工审。不调内置 `/security-review`:它只抓会话 cwd 所在仓的 git status/diff、不接受指定范围,对不上步骤 1 圈定的 24 小时提交。命中则给结论,未命中写「不涉及」。

4. **硬约束(审查阶段只读)**:审查与报告阶段不改业务代码、不编译、不触碰 Unity 编辑器(不调用 UnityMCP 工具)、不自行提交/推送。修复不在此阶段做,经步骤 6 整体交 devflow 承载——devflow 有自己的编辑 / 自检 / gated 提交,不受本条约束。

5. **产出报告**:写中文报告到 `<仓根父目录>\_review-reports-3b\<YYYY-MM-DD>.md`(仓根父目录 = flow-config 的 `SlotBaseDir`,即槽位池所在层;目录名带 `-3b` 后缀,与同层 block-client 的报告目录分开;目录不存在先建)。结构:
   - ① 审查范围:提交哈希 + 标题列表、未提交改动概况;
   - ② 发现清单,按严重度降序,每条含 `文件路径:行号`、一句话缺陷描述、具体失败场景、置信级(**确认** / **存疑**——只静态读码未执行验证的标存疑);
   - ③ 安全面核对结论,或「不涉及」;
   - ④ 与 `_review-reports-3b\` 最近一份旧报告对照,重复出现且未修复的标「跨日未修复」。
   - 末尾一两句总结:发现总数与最严重一条。

6. **修复派生(确认级发现交 devflow)**:报告产出后,把本轮**确认级(CONFIRMED)**发现作为一个修复批次,经 Skill 工具调 `devflow`(简报含每条的 `文件路径:行号` + 缺陷描述 + 失败场景 + 建议方向,不含猜测式改法;多条独立发现由 devflow 按其多任务并行分派规则分组处理,本步不逐条各起一次)。修复的实现 / 编译 / 自检 / gated 提交全部由 devflow 承载。**禁止事项**:
   - **存疑(PLAUSIBLE)发现不派、留报告**——可能是有意取舍,交人工定夺;
   - **落在人工入库通道范围内的发现不派、留报告**(范围正本 = CLAUDE.md「devflow 适用面」条款)——这些域不进 devflow,不适合无人值守执行,交人工;
   - 本流程**不自行编辑业务代码、不自行提交**,一切改动经 devflow 检查;
   - 每日审查无人值守:devflow 命中阻塞裁定项(设计分叉 / 合并冲突 / 检查未过)时按其规则呈报、**不强行落库**,该发现留待人工;
   - 把 devflow 的派生结果(每条:已修复的分支 / 提交,或阻塞原因)回写报告 ② 对应发现条目,使报告成为「发现 + 修复去向」的单一追溯点。devflow 分组并行时结果陆续回来,等各组子会话都结束后一次回写;停在待裁定或停机的组,回写「阻塞:<原因>」并附该会话链接。
   本轮无确认级发现 → 跳过本步,报告注明「无确认级发现,未派修复」。

7. **最终回复**:一句话摘要——发现数量、最严重问题、修复派生结果(已派 devflow 修复 N 条 / 阻塞 M 条 / 无确认级发现)、报告文件路径。
