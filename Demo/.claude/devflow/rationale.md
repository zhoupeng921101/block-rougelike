# devflow 设计理由库

本文件收纳从 devflow 工作流族规则卡(`devflow*` / `unity-check`)外移的**审计期理由**——「为何这样设计、当初踩了什么坑」。规则卡执行时整篇加载进 agent 上下文,而这些理由只有**改规则/审计的人**才需要读,故按读者频率拆出本文件,不占执行 token。

**用法**:规则卡里对应规则处留一行指针 `理由见 .claude/devflow/rationale.md#<slug>`,全文在此。改规则时循指针来核理由是否仍成立;理由与所注规范同步存废。

**对齐保证**:`.claude/devflow/理由对齐核对.ps1` 双向核对——卡里每个指针都能解析到本文条目(无悬空指针)、本文每个条目都有卡在引用(无未被引用的理由)。改动规则卡或本文件后跑一次;失配即报。

> 本文只承载理由层。规范(规则本身)仍在规则卡,不在此复制;执行期告诫(跑的时候真要照做的告诫,如 push 失败处置)也留在卡里,不外移。
>
> 本文随 devflow 从 block-client 搬来:条目里的日期、实测数字、提交号与事故(含服务端、部署、业务窗口名)都出自 block-client,是理由的来历,本仓查不到对应提交;只服务于服务端通道的条目已随通道删除。

## parallel-subsession-dispatch

经子会话并行为 2026-10-20 用户裁定,取代 2026-07-20 的多任务串行裁定。串行当时的理由是并行派活要由主会话一并承载批量并发调查、范围重叠分流与多槽位调度,复杂度不抵吞吐。桌面端子会话(同日实测主↔子、子↔子消息双向送达)让每组任务在自己的会话里走完整 devflow,协调者只粗分组与转述;漏判的重叠由领取入口的路径比对兜底,并发交付早由合并预检与 STALE 重跑承载。

单任务不拆子会话:UI 与客户端共用槽位编辑器,客户端改 `.cs` 触发的编译与域重载会打断 UI 段的 MCP 操作;客户端还要往 UI 段生成的 impl partial 里填逻辑,依赖是真的。block-client 唯一拆得开的是服务端线(独立 worktree、实现期不跑 build、不抢编辑器),本作没有服务端,段内并行随之取消。

子会话起在主工程目录:cwd 不在 Demo 下的会话,Skill 找不到实现段卡。取号条的实发:2026-09-26 dev1 与 dev3 并行各按 main 取下一个空号,后合并方留下冲突标记;领取比对只看路径不看号。

试点实测(2026-10-21,子会话在 auto 模式下由协调者会话起头):①子会话用绝对路径写槽位文件(Edit / Write 改表说明与业务代码,Bash 里 python 改 xlsx)全部直接落盘,未见权限确认;②子会话再开子会话开不出——由别的会话的消息起头的会话,桌面端不认 `user_asked`(须用户本人在该会话里说),只能出 `own_initiative` 提案卡、等用户点开才起。故分组只做一层:协调者开组子会话,组子会话不再往下拆。

## out-of-scope-no-gate

界外顺手修在全链路零报警:自检照样通过、code-review 不查范围、呈报不逐项对照简报——范围纪律没有机器检查,只能靠本条 + 呈报「简报外改动」字段 + 自审核对保障。

## merge-early-small-tasks

槽位上的未合并提交存在越久,与其他并行槽位的失配越大;小任务、测试通过即合并,缩短并发窗口比分配策略本身更能降冲突。

## placeholder-commit-claim-race

占位提交用于防止并发领用冲突:空闲判据是瞬时快照,领用若不留痕,两个会话可先后判同一槽位空闲并双双入驻(2026-07-13 实发,两功能叠上同一分支)。占位为空提交,随分支一起合并进 main 充当领用记录,不摘除——摘除需改写历史,会作废 客户端自检 锚定的受测 commit。

## board-process-state

看板补的是「任务卡在哪一步、被什么阻塞」这类 git 推导不出的流程态;占用判据仍以 git 为准,防止回退到「文件判空闲」的竞态形态(即占位提交防的那类事故)。机器常量(仓根/槽位布局/基线分支)同理收单一事实源 `.claude/devflow/flow-config.psd1`,脚本与 hooks 统一读取。

## merge-machine-gate-no-reverify

合并的实质检查是机器检查(槽位检查通过检查凭据 + 只读预检):零阻塞合并上加人工裁定不增加拦截信息、只增加每任务一次等待;裁定保留给预检报阻塞的例外路径。合并后不设再验证(2026-07-15 裁定):快进合并的树与受测树逐字节一致,再测纯重复;真合并的残余风险(两侧各自绿、拼合出问题)由常开主编辑器的即时编译暴露编译级破坏,测试级回归由下一任务的检查与「四类归因」保障。

## correctness-review-to-nightly

全移每日审查为 2026-07-18 用户裁决:目的是白天开发时段把算力与 agent 并发容量集中于开发,正确性审查错峰到夜间空闲期由 daily-code-review 统一承载;取舍前提 = 漏检的正确性缺陷多为小问题、不阻断进度,接受缺陷先入主干、由「四类归因」返工的成本(同类缺陷第二次出现即强制根因修复,反复类不会无限累积)。安全审查与意图核对不随之移走——前者代价面最高(block-client 里缺陷先入主干且先触发开发服重启;本作则是坏存档、写出工程外这类难回收的后果),后者依赖当轮简报上下文、每日审查只读码无从执行,二者覆盖「非小问题」部分。2026-08-21 起定时任务停用,承载改为用户手动触发 `/daily-code-review`(状态正本 = 义务台账对应行),交付前零审查的兜底从「错峰夜审」变为「手动补跑、无固定节律」;该状态经当日审计呈报后由用户裁定维持,不加积压提示。触及公共接口 / 存档结构 / 配置表结构的改动,其调用方与消费方核对一并归每日审查:签名未变而语义变的误用只在调用方可见,交付前的槽位自审看不到全仓消费面。

## security-review-cwd-locked

交付前安全审查走项目自备清单、不调用内置 `/security-review` 的依据:该 skill 抓取会话 cwd 所在仓的 git status/diff,且不消费指定目标路径的入参;devflow 的实现产物恒在槽位 worktree,不在会话 cwd(主工作树)的 git status/diff 里(2026-07-29 block-client 实测:它读到的是主工程无关文档改动、代码 diff 为空,输出结论与本轮改动无关)。这不是偶发不可用而是本流程下的恒定状态,故不写成「不可用则手工」的兜底分支——兜底会让后续每轮先试一次该工具、拿到无关结论再判断是否降级,且无关结论有被误当作「已审查通过」的风险。第二个独立断点:该 skill 要求以并行子代理执行,部分会话配置禁止未经用户请求调用子代理。清单只收安全面视角,正确性与存量存档失配等已由每日审查承载的项不纳入(见 #correctness-review-to-nightly),避免同一检查项两处正本。

## no-staging-path-commit

开发中不动 git 的依据:用户在同一工作树活跃改动,提前记基线会失配、中途切分支会打断。收尾不经暂存区的依据:主工作树 git index 被多会话共享,「精确 add + 暂存集核对」只能缩小、无法关闭 stage→commit 窗口的竞态(2026-07-16 一日三发:并行会话预暂存项两次被收尾提交带入;反向一次,收尾会话已暂存的文件被并行会话的提交带走,靠未推送 + `git reset --soft` 拆开重做);按路径提交的内容 = HEAD + 指定路径的工作树状态,与他人暂存态在不相交路径上互不可见,竞态收敛为「同文件双态」一种真冲突形态(git 2.54 实测:修改/删除/`add -N` 新增/同文件双态四态行为确认;intent-to-add 条目不被并行的暂存区提交纳入,`-a` 形态例外,故登记后立即提交)。不代收非本会话未提交改动的实证:2026-07-16 同日,半成品被并行会话以「接手收尾」提交,靠原会话后续增量提交纠正。

## fast-track-anti-ritual

简化归因防的是仪式化归因:每日审查使缺陷发现集中化,轻测试使纯逻辑缺陷成为既定取舍的预期产物,逐条走四类归因只产出重复劳动;三条回拉保住规则演化信号——违规类、复发类、检查漏判类必须留在完整归因信道,否则「同类问题该上静态检查」永远无人发现(2026-07-16 裁定)。

## fixed-sequence-separate-section

四类归因只收「合并后缺陷」,不产生缺陷、只产生重复劳动与打错风险的固定序列进不了那条升级通道,故单列本条;「第二次执行」跨会话不可数,触发判据取「规则卡已成文」这一静态可核形态。

## reuse-project-ui-facilities

引擎默认资源有隐坑(内置字体 LegacyRuntime.ttf 无中文字形),工程设施已解过一次;绕开设施重复实现即同类返工重演(2026-07 实发:20 个 Text 用内置字体致中文渲染方块,整轮返工)。

## temp-test-delete-after-gate

删除时机若定在「交付前」:检查未过需回槽位修复时已无测试可用,修完只能重写。故统一锚「检查实际通过后」;测试目录被 .gitignore 忽略、删除不产生提交,删后的工作树漂移由验票的临时测试删除容忍度承接,不触发检查重跑。测试本身由实现段自行在编辑器 Test Runner 执行(2026-07-30 起检查不再运行测试),删除时机仍锚检查以复用「PASS 在手」这一确定性信号。

## slot-acquire-one-call

领用收敛为一次工具调用是 2026-07-21 用户裁定,并于同日进一步收尾为固定三个槽位:Agent 在槽位安排上花的回合(读占用面板、判陈旧占位、比对重叠、同步基线、启动编辑器、确认 UnityMCP)全是机械操作,违背「Agent 做判断、机械归脚本」的分工原则。这些判据都能写成确定性规则,故统一由 `槽位领取.ps1` 承载。`FULL` 只表示固定池各槽均占用,不得运行期动态扩容;`槽位置备.ps1` 仅用于池内槽位的初始建置或修复(池大小由 flow-config `SlotCount` 定,增减是改配置 + 跑该脚本的人工动作)。真正的取舍仍由脚本以 `VERDICT:` 交回 Agent。

## one-call-delivery

交付收敛为 Agent 面一次 `槽位交付.ps1` 调用是 2026-07-21 用户裁定(与 slot-acquire-one-call 同源):检查、提交、push、预检、合并与推送均是可机械判定的固定序列,不应由 Agent 手打或转交后台 Agent。外层入口负责推导改动面、执行自检、生成提交信息与预期提交清单;内部再调用 `单仓提交.ps1` 和 `集成交付.ps1`。校验函数仍以 校验库.ps1 为单一正本并 失败即停。判断边界保持:实现质量与意图自审由 Agent 完成;预检 blocker、二进制冲突、INFRA 一律停下交回。可重入设计使停等点处置后重跑同一入口即可续走。

## light-test-policy

「重开发轻测试」策略(工程不设常驻测试套件,建测由实现段按需裁量)为 2026-07-16 裁定确立;与 #correctness-review-to-nightly 属同一取舍链——正确性拦截集中于每日审查,接受小缺陷先入主干,由四类归因(同类缺陷第二次暴露必走完整归因、修法同轮落地)控制反复。操作条款正本在 devflow-client 卡「自检」节。

## newasset-settle-before-gate-premise

「含新增资产的检查:先等待派生资产落定,再调用交付入口」的前提:Refresh 对已落定资产不再重打包(atlas 打包确定性)。提交由 `槽位交付.ps1` 统一执行(候选提交先于客户端自检,检查跑在提交后的树上),因此落定阶段只要求编辑器导入收敛,不要求 Agent 先提交。残余 churn 表现为 STALE:客户端自检不发票,交付入口回 `GATE-FAIL`(next=judge),由会话按档位重跑;若实测稳定翻车,按归因改走检查内落定后再取哈希的代码级方案。

## devflow-check-why-exists

devflow-check 独立成 skill 的动因:工作流规则族是「改一处必须同步他篇」的高耦合文本,一次大改(槽位分工调整、git 协议变更)的影响面分散在多张卡里,漏同步即产生互相矛盾的指令,故把交叉检固化为分钟级机械核对,与 /rules-audit 的全栈广度审计分工。


## report-exception-only

交付呈报采用例外呈报制(2026-07-22 裁决):空值字段(简报外改动 / security 发现 / 自检待跑)整项省略不写「无」占位;「实现段承载」skill 清单字段删除,仅违规(客户端代码未经 devflow-client)时作异常项呈报;逐轮重复的覆盖缺口固定文本由具体「未执行验证的验收点」清单取代。动因:固定占位与逐字重复的字段无用户消费价值,反使失败/阻塞/待手测等真信息被淹没;强制自查的功能已由自审核对项与卡纪律承载,呈报侧再写声明属重复承载。代价共识:书面「无」声明的留痕消失,范围纪律与实现段不变量的保证等级维持弱约束不降级(义务台账对应行同步改承载描述)。

例外呈报制下仍保留的入口锚点级冗余只有提交主题一行:花一行换「不开任何文件就知道这轮交付了什么」。修复类定性一行与 `简报外:` / `界外:` / `顺手修:` 前缀于 2026-09-22 瘦身时删除(用户裁定):定性已由 FIX-QUALIFY 机判写进提交正文,前缀属输出形态约束,待裁定项按类概括即可。gate 首跑失败与修复留痕留在呈报而非 commit message,则是因为提交信息写定在交付调用之前,该留痕物理上进不了 commit message。

## reverse-ref-code-to-rulestack

引用完整性的两个方向保证需求不对称,故只有反向纳入检查。规则栈文档提到 `Assets/` 下的实体路径,过时了由开发与自检在代码侧发现;工程代码以字符串指名 `.claude` 脚本则没有任何编译期约束——脚本名不是符号,改名或删除后编译与 EditMode 全部通过,失配只在有人触发该功能时才暴露。2026-07-27 事故形态:devflow 脚本 py→ps1 迁移后,Unity 侧 devflow 槽位面板仍调 已不存在的 `python转发器.ps1` 与 `占用面板.py`,面板恒失败而无人知情;PowerShell 对不合法脚本路径把 usage 帮助打进 stdout,又使故障表现为 JSON 解析错、真实原因(退出码与 stderr)被掩盖。参数形态一并核对是同一事故的第二层:同批迁移把 `--slot N --close` 改成 `-Slot N -Close`,脚本名对而参数错的失配同样静默,且脚本 `PositionalBinding=$false` 只在运行时报错。

配置常量复述是第三层,静默程度更高:脚本名错至少会在有人触发该功能时炸,而注释里写死的常量值**任何时候都不会炸**,只在有人照着注释推理时把结论建歪。2026-08-30 实发(block-client 的槽位面板,本作未搬):`DevFlowDashboardWindow.cs` 类注释写「三固定槽位 dev1/dev2/dev3」,`SlotCount` 早已是 5,面板本身按快照 `slots` 数组渲染、功能全对,只有读注释的人会得出「dev4/dev5 不该出现」的错误结论;写注释者把 `NormalSlotMax`(常规任务选槽上界)的值当成了池大小,两个键语义相邻是这类失配的固定诱因。扫描面必须锚在反向段已取到的引用点上:业务代码有大量语义无关的同名常量(如订单卡的 `RewardSlotCount`),放开成全仓键名 grep 会把真信号淹进误报。

## brief-gate-machine-checked

简报出口的「自查四项」与产物段形态原先零机器强制(义务台账自认弱约束),而简报是实现段唯一接口与跨会话续接源,缺段/占位/空话验收点的劣化简报会静默穿透到实现段与 claim body。结构层(段齐全/等级枚举/验收点非空话/无占位/摘要封顶)可确定性机判,故外包 `简报校验.ps1` 绑定在领取入口——简报进 claim body 前的最后关口;语义层(自相矛盾、两读歧义、三态标注完整性)机判不可靠,硬判会以假阳性稀释信号,仍归自查。必填段清单由模板文件 `## ` 标题解析而非脚本硬编码:模板即正本,改段名单处生效,消卡片/脚本/模板三处失配。`-BriefFile` 同时升必填:台账「跨会话续接依据落 git」既认简报为续接源,无简报的空 claim 占位使续接退化,卡片签名亦从未含省略形态。`DENIED-BRIEF` 例外于「非 ACQUIRED 停下呈报」允许修复后重试一次:缺项清单给出的格式错误确定性可修,停等呈报纯增一次往返;限一次防循环重调。(2026-07-29 裁定;借鉴 OpenSpec validate/templates:结构校验交机器、模板即正本)

验收点段收窄(2026-09-22 用户裁定):常规功能的验收点与「目的」逐字同义,逐条复写只增篇幅不增信息,且把真正不显然的边界 / 异常 / 跨端点淹没;故验收点只写照目的跑一遍看不出对错的,常规功能写「同目的」,第一步直通通报同步去掉验收点。段仍必填、空话检查不变——保留段位让「有无特殊验收点」成为显式判断,而非静默遗漏。

占位词判据修正(2026-10-20,工作流审计 C-1):「待定」「待补」移出占位词表。二者是正常产品用语(「美术待补」「策划待定项」),算不算占位要靠语义判断,当初误归结构层硬判,才产生上文语义层所说的假阳性稀释信号——截至审计的 7 次占位命中全是这两个词的误报;能确定性机判的只有模板专属记号与独立 TODO / TBD。旧明细行又只给整行、不点名命中词,09-27 一个会话把行内「占位」二字当成命中词改掉,重跑仍拒,二败停机等用户。故明细行改为写出命中词、同段多处全列,一次改全。TODO / TBD 只认区分大小写的独立标记(todo 列表、TODOs、TODOS 之类不算);紧邻中文的写法(「这里TODO接口」「TBD值」)改为也拒,是有意扩面而非收窄:旧 `\b` 把汉字算词字符而漏判。「填写指引」是模板指引行专属记号,产品简报不会自然出现,留作未替换探测点。

## deterministic-fail-one-retry

`DENIED-subject` 与根因自明的 `GATE-FAIL` 比照 `DENIED-BRIEF` 授权当轮修复后重跑一次(2026-08-21 裁定):三类同构——失败确定性可修、用户指示几乎恒为「修」,停等纯增一次往返。停机契约的原始事故(rules-archive/rules-rationale.md#verdict-stop-await-user,2026-07-23)防的是契约不在场时的无限自主循环重跑;「限一次 + 二败停机 + 呈报留痕首跑失败」不复现该形态。GATE-FAIL 的例外面收窄到根因自明(自检道次点名具体违规且修法无歧义):根因不自明的失败可能携带实现质量或环境信号,仍过用户的眼。

`DENIED-qualify`(2026-10-10 用户裁定)归同一档:修复类提交正文缺根治 / 补丁结论、或定根治而没写不变量时,`槽位交付.ps1` 在入口前置拒绝。此前这条只由 `自审触发判定.ps1` 报 required、靠会话自己补,交付入口不看——会话跳过自审一步,缺定性的修复提交照样合进 main。自审四项里只收这一项进入口:它的产物就是提交正文,拒了改一行输入文件即可重跑,不存在「拦截误判堵死流程」;安全审查、资产落定、目视证据没有可机判的产物,仍只报不拦。

## test-matrix-catches-logic-regression

入口脚本回归跑全量测试矩阵而非静态 grep 的依据:测试是脚本行为的单一事实源,同时捕获函数删除与逻辑/接线回退;静态 grep 只抓得到函数名删除,抓不到会话外 git 合并把旧版入口脚本整份覆盖(绕过 script-authoring 按改动触发的验收检查)带来的逻辑回退。

## instance-binding-path-only

实例身份只能按 `active_instance` 的 path 判的依据:各槽位实例同名 `Demo`、场景路径又是工程相对路径,`get_active` 的返回分不出绑的是哪个实例。第 1 步身份校验不可省的依据:`active_instance` 是 MCP server 进程级全局共享的,绑错会让所有 agent 的调用同时路由到错误实例,而主编辑器与多个槽位编辑器常同时开着,本会话的其他 agent 可能把它切到过别处。

## rules-named-by-script
