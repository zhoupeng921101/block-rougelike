# rules 栈设计理由库

本文件收纳从项目根 CLAUDE.md、`.claude/rules/*.md` 与已移出注入路径的 `.claude/rules-ondemand/*.md` 外移的**审计期理由**——「为何这样设计、当初踩了什么坑」。前两者每会话注入进上下文、rules-ondemand 按需读,而这些理由只有**改规则/审计的人**才读,故按读者频率拆出本文件(置于非注入的 `rules-archive/`,不随规则注入),不占常驻 token(机制正本 = `.claude/rules-ondemand/file-conventions.md` 规则 2)。

**用法**:CLAUDE.md、rules 与 rules-ondemand 文件对应规则处留一行指针 `理由见 .claude/rules-archive/rules-rationale.md#<slug>`,全文在此。改规则时循指针核理由是否仍成立;理由与所注规范同步存废。

**对齐保证**:`.claude/devflow/理由对齐核对.ps1` 双向核对(CLAUDE.md、rules 与 rules-ondemand 文件 ↔ 本文件),无未被引用项、无失效指针。改动引用文件或本文件后跑一次。

> 本文只承载审计期理由。规范(规则本身)仍在 rules 文件;执行期告诫(禁止事项/入口契约/边界处置)也留 rules 文件原地,不外移。
>
> 本文随规则栈从 block-client 搬来:条目里的日期、实测数字、提交号与事故出自 block-client,是理由的来历,本仓查不到对应提交;只服务于服务端与玩家数据归属(data-authority / db-schema / server-perf)的条目已随那几篇删除。

## shell-single-engine

devflow 脚本层 2026-07-27 收敛为单一引擎(全 `.ps1`),终结 2026-07-17/18 两次裁定形成的双语言并存。

为什么终点是 pwsh 而不是 python:pwsh 侧存在**迁不走的硬核**——hooks 安全检查(靠命令词法触发,harness 直接调用)、`语法自检` 的 PS 语法解析器、Win32 进程操作(服务端重启)、依赖 hook函数库 发凭据的检查、Agent 面入口契约、依赖 校验库 验凭据的受控 git 构件。python 吃不掉这些,故「迁 python」的终点必然是双语言;反向则可收敛到一种。

两类脚本的实测成本不同,迁移时按类分批:文本扫描类 pwsh 更短(管道 + Select-String,409→314 行);JSON 状态类基本持平且需补 CLI 层测试(138→128 行,测试 146→192 行)。故语言统一的收益不在代码量,在于消除下述整类故障与共享层副本。

**消除的故障类**:会话(Claude Code)跑在 MSIX 沙箱内,`python` 别名启动的子进程继承沙箱身份,写 `%LOCALAPPDATA%\claude-wf-3b` 被静默重定向进应用私有容器——写入方自读一切正常,pwsh 侧与用户视角却看不到,看板/遥测无声分裂且无报错。旧解法是经 `python转发器` 探测真实 exe 转发,脆弱点在「依赖每个顶层调用方都不漏」。pwsh 不受该虚拟化影响,转发器与其自检随之退役。2026-07-27 迁 归因留痕 时当场复现:同一条遥测,py 直调命中真实文件 0、ps1 命中 1。2026-09-27 复核:「pwsh 不受影响」已不成立——Claude Code 的 shell(含 pwsh)同样跑在桌面端包容器内,新建项落进 `Packages\Claude_*\LocalCache\Local`,分裂转到容器内会话与容器外 Unity 编辑器之间(槽位面板恒读 2026-08 的旧看板)。换引擎不再能避开,改为 `hook函数库` `Resolve-WfStatePath` 直接解析物理路径,静态扫描 R18 拦直拼。

**测试形态**:契约测试落在 **CLI 层**而非函数层——调用方本就只经 CLI 用这些脚本,CLI 是真正的契约面,而函数层测试绑死实现语言、换引擎即作废。迁移期靠同一份 CLI 测试先对现役实现跑通过(自证判据),再对新实现跑通过(验等价);该纪律逮到的真缺陷包括 `File.Replace` 的 `$null` 绑定、函数返回数组在输出边界解包导致的跨引擎 JSON 契约破坏、`cmd` 吃掉 `^` 转义、`(?m)$` 遇 CRLF 全失配。

**准入**:再次整层换语言须先有两项证据——实测事故计数(归因到语言侧)+ 单文件试点的实测成本;缺任一项不启动。前两次裁定都缺第二项。

## shell-session-powershell-tool

2026-08-18 本机卸载 pwsh 7 后 PowerShell 工具调用 exit 1 零输出,会话命令才改经 Bash 嵌 `powershell.exe`。2026-09-27 复测前提已失效:PowerShell 工具跑的就是 5.1,控制台代码页 65001,子进程(powershell.exe / python / cmd)中文输出均正常;同机 Bash 侧 `[Console]::OutputEncoding` 为 gb2312、python stdout 为 gbk(系统 ACP=936)。

同日扫两端会话记录(约 420 份)的失败命令,Bash 通路自带的故障族:输出 GBK 乱码 481 次(含参数缺失等本可自解的报错因乱码读不出而重试)、Bash 双引号吞 `$`(`$_` 变 `unsetenv`)8 次、未加引号路径吞 `\` 约 20 次。换 PowerShell 工具后三族同时消失,调用侧编码前置也随之只剩非 UTF-8 控制台一种场合。

同批另两族与通路无关:`cmd /c x.bat` 报找不到 76 次——harness 置 `NoDefaultCurrentDirectoryInExePath=1`,`cd /d` 之后也不搜当前目录(两工具实测一致,`.\x.bat` 即通);scratchpad 临时 `.ps1` 无 BOM 含中文致解析错约 8 次(Write 工具不写 BOM,`语法自检` 只扫 `.claude` 下)。python 在 Bash 下的乱码由 settings.json `env.PYTHONIOENCODING=utf-8` 统一,与 PowerShell 工具侧 harness 自带值同口径。

## shell-safe-by-default-cli

风险位置错配是这族缺陷的根:正确性依赖调用方的一次自觉行为(读文档、记住加某个开关),而漏读的代价由被调用方的副作用承担,且漏读当场无任何反馈信号。副作用不可逆时,这个契约必然在某次调用上失效。

2026-08-04 实例:`单仓提交.ps1` 主仓通道曾缺省 commit 后即 push,由 CLAUDE.md 一句「`-NoPush` 是必需的显式覆盖」托底;裁定改为全通道缺省不推、`-Push` 才推,`-NoPush` 保留为显式关闭以免既有调用方失配。同轮在 settings.json 给 `git push` 加 `ask` 分类,构成第二道拦截。

分工不因此改变:脚本承载「怎么用不出事」(安全属性),文档承载「什么时候用哪个」(选择问题)。本规则不构成删减文档用法说明的依据。

`-CheckOnly` 只给有实写副作用的入口而不铺全量:只读脚本本就零副作用,加探查开关是纯噪音,且会稀释「带该开关 = 有副作用」的信号价值。沿用 `-CheckOnly` 而非 PS 原生 `-WhatIf`:现役两处(单仓提交、集成交付)已用此名,统一成本低于改名;`SupportsShouldProcess` 在嵌套调用链上的传播行为需逐个入口验证,收益不抵验证成本。

## verdict-stop-await-user

2026-07-23 实发:续接会话中用户仅说「重跑槽位交付」,当时承载交付段的技能卡未装载,其「非 DELIVERED 立即停下等指示」契约不在上下文;Agent 收到 INFRA 后自行诊断并再次重跑,直至用户打断。失效机制:契约只写在技能卡内,而卡的装载依赖 /devflow 调用路径,续接/中断重跑场景可绕过该路径。对策双保险:停机契约上移常驻层(CLAUDE.md 工作流条款),交付脚本在非 DELIVERED 返回时自带一行处置指引——两者分别覆盖「卡不在场」的判断面与返回面。2026-08-21 扩例外:三类确定性可修错误(DENIED-BRIEF / DENIED-subject / 根因自明 GATE-FAIL)授权修复后重试一次,细则正本 = devflow 卡「停机呈报」条;限一次 + 呈报留痕,不复现本条防的无限自主循环。

## main-repo-channel

产品代码的默认通道是 devflow 槽位流程;主工程通道是 2026-08-01 新增的窄口径旁路,承接三类摩擦:槽位流程的固定开销对小改动不成比例、不入库的试跑缺少落地位置、改动归属模糊时需由用户当场裁定通道。触发面刻意窄(须用户明确指向主工程或明确表示不走流程),含糊表述按默认通道——错判成本不对称:误走 devflow 只是慢,误走主工程会绕过隔离。

**保留项的理由各不相同**。需求审计与自审两项轻核对是判断质量的来源,与在哪个工作区落地无关,换通道不构成豁免依据。自检则是机制性前置而非流程礼节:提交检查 hook 在主仓通道同样要求 PASS 凭据,触及 `Assets/GameScripts|Launcher` 的 `.cs/.asmdef` 的提交缺票即被拒,跳过自检的结果是提交不了而非省一步;客户端自检的其余读取面(prefab / ProjectSettings 等)不拦,只靠收尾条款装载,漏跑的违规会在之后的槽位交付里以本轮之外的 GATE-FAIL 显形。客户端自检不启动 Unity,静态各道加一道 dotnet 编译,成本可接受。

**不推送**:推送属全机串行点,由槽位交付统一承担(主工程通道的提交在下次任意槽位交付推 `main` 时被带上)。代价是主工程通道期间无远端备份,已作为已知代价接受。(block-client 另有部署点,同理由下次槽位交付补部署。)

**单任务串行**:主工作树是单分支单编辑器,两个任务的改动物理上混在同一份 diff 里;且 gate 凭据绑定签发时的工作树哈希,后一个任务动到受检面会使前一个任务已铸的票判 `tree-mismatch`。并行需求走槽位池,那正是槽位存在的理由。

**基建改动在交付前入库**:基建改动一旦留在索引里不提交,就与槽位交付的合并步骤互斥。机制与路径重叠无关——git 的 merge 在开始前要求索引与 HEAD 一致,主工作树里任何**已暂存**的改动都会让它直接 abort 并列出全部脏路径,返回 `INFRA` 而非冲突;仅工作树修改、未暂存的不阻断。故合并预检的 `overlap=0` 不构成放行依据:重叠判据看的是本次改动范围,而 git 看的是索引整体是否干净。
> 2026-08-02 实测:同一会话先交付 GameEvent 接口收敛通过,随后交付推送落地模块时被拒,报错列出的 6 个路径恰为当时全部已暂存文件(4 个本会话基建改动 + 2 个非本会话残留),而同时存在的一个仅工作树修改文件不在其中。首次通过是因为那时索引恰好干净,不是因为文件无重叠——按此机制,任何留着暂存改动的会话都会撞上。

**不动分支拓扑**:曾评估三种结构性方案——基线整体下移到 main_dev、新增专用集成工作树承载 main、交付时临时切分支——分别因「未受检提交成为槽位 fork 基线」「多一份 Unity 工作树的磁盘与导入成本」「每次交付触发主工程编辑器两次域重载」否决。主工程通道的残留改动导致的交付阻塞改以事后归因处理:合并类失败的呈报须点名根因归属,不以结构改造预防。残留的机制后果须持续可见——主工作树未提交改动落在合并触碰面内即阻塞槽位交付,这是 2026-07-28 半完成合并事故的判据来源。

## device-only-cause-unverified

block-client 实发,2026-09-03 至 09-10,同一个 HybridCLR 缺陷(8.8.0 为 Unity 6000.3 配的 il2cpp_plus 在 `GetMethodHandleFromVTableSlot` 不处理抽象方法的 NoData 虚表槽)在热更程序集 `Assembly.Load` 处原生崩溃五次。前四次先后被判为「该程序集不宜走热更」「托管裁剪留下空槽」「补充元数据加载时序竞态」「AOT 泛型零实例化」,每轮都在没有真机对照的情况下定性根治,并据此加了提交闸、构建闸、保活锚点与注释断言:构建闸上线当天即误拦出包;锚点确证进包而崩溃依旧;注释里的「已知必崩组合」「Release 下断言为空操作」又成了下一轮排查的前提。失效机制:这类缺陷只在出包运行时显形,槽位无 HybridCLR 安装、跑不了出包,验证天然推迟到交付之后,而定性与加闸发生在交付之时。根治由 6088a900f 升级 8.14.1 取得,依据是上游源码差异与 global-metadata.dat 实证,不是某一轮工程侧改动。本作现走 Windows Mono 包、HybridCLR 暂关,同一失效机制在开热更、改 IL2CPP 或移植手机后照样成立。

## comment-rule-split-from-file-conventions

代码注释规约(tengine-conventions「注释准入」)与持久文件写作规约(file-conventions)分置两篇、不并篇,三条依据:

**装载时机**:file-conventions 由 CLAUDE.md 按需路由在「写持久文档」时装载,tengine-conventions 在「写/改代码」时装载。注释在写代码时产生;规约放进 file-conventions,写代码的会话要么不装(规约等于不存在),要么连带读进三条与代码无关的文档规则。

**判据形态**:file-conventions 三条管文档怎么活(只写现值 / 正本在别处不抄 / 过时即重写),注释准入只有一个删除测试加一个去处。两者是同一套「信息放哪」政策的两半——注释准入把改动理由推给 commit message、设计全景推给 `新游戏/` 下的设计文档,file-conventions 接住推过来的内容——各写在各自写作者会读到的那篇。

**审计通道**:rules-audit 查项 8 拿 file-conventions 1-3 条逐句扫持久文件,并明文排除业务代码注释;注释已裁定不配任何机判道次、存量只在触碰时收敛(2026-09-04 存量试点后裁定)。并篇则查项 8 默认扫进约 770 个文件的注释,与该裁定相撞。

两篇唯一一次交叉是 62b686c7e 在 file-conventions 加的「收尾删减道次」节(适用面含代码注释),29e7260da 瘦身一期删除,此后只留 file-conventions 适用行一句分界指针。

## deletion-admission-asymmetric

删减准入与规则准入对称,但默认值相反:拿不准时准入默认不进、删减默认不删。依据是两种错误的可见度不对称——多留一条的代价是注意力税,每会话可见、可在审计里量出;误删一条的代价是某次交付出错,要等缺陷暴露并归因才显形,其间静默。2026-09-04 与 2026-09-22 两轮瘦身连续执行后,用户提出「多执行几次会不会过度简化」:扫描以「产出删除候选」为任务时本身带隐性配额,越往后剩下的越接近项目知识,分类误判率上升;事故叙事中承载「为什么」的部分被直接删掉,会让规则失去可遵循的依据。故定启动条件(按事件而非定期)、逐条判据、举证要求与恢复回路(2026-09-22 用户裁定)。

## ui-image-async-load-registered

框架的异步 `SetSprite` 只在「同一目标发起新的异步加载」时取消旧加载,加载完成时直接写 `Image.sprite`。同步换图(直接赋 `sprite`、清图)因此拦不住一次在途加载:先发起异步加载 A、再同步换成 B 时,A 完成后把 B 盖掉,此后没有请求把它纠正回来;只在加载慢时显形,编辑器里多半看不到。

block-client 2026-10-09 头像框换图时暴露,当时在 `ExImage` / `SpriteBind` 上加了「登记加载、任何换图即取消」的机制修掉。本作没有搬这两个组件,故规则退回「同一节点不混用」,非混用不可时由调用方自持取消令牌。
