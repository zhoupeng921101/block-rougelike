# Brotato v0.8.0.3 效果系统

> `配置CSV/_效果总表.csv` 的 902 条是整个游戏"内容"的最小单位——
> 171 件道具、38 个角色、14 套套装、172 条武器、64 张升级卡的全部差异都压在这张表里。
> 这篇拆的是这套 DSL 本身：一个 `Resource` 基类 + 一个 134 键的字典，怎么撑起全部内容。
> 版本口径：`Brotato_0.8.0.3/`。
>
> 相关：[角色构筑指南.md](角色构筑指南.md) §0（`gain_<stat>` 与伤害乘区如何消费这些键）、
> [升级卡系统.md](升级卡系统.md)（升级卡的 77 条效果）、
> [敌人与威胁设计.md](敌人与威胁设计.md)（危险等级的 19 条效果）。

---

## 0. 一句话结论

**整套效果系统只有一个类、七个字段、三条分支。**

`Effect.apply()` 一共 8 行代码，做的事就是往 `RunData.effects` 这个字典里
**累加一个数**、**覆盖一个数**、或者**往一个列表里塞一条记录**。
902 条效果里 **708 条（78%）连子类都不写**，只是同一个 `.tres` 模板换参数。

代价也很明确：**没有中央派发器**。
212 个消费点散在 25 个文件里，每个系统自己去字典里捞它关心的键。
加一条新效果几乎零成本，但**加一个新的效果"种类"要同时改数据和消费端两边**。

## 1. 全部机制：一个基类 + 一个字典

### 1.1 `Effect` 的七个字段

`源码/items/global/effect.gd`：

```gdscript
class_name Effect
extends Resource

enum Sign          {POSITIVE, NEGATIVE, NEUTRAL, FROM_VALUE, FROM_ARG}
enum StorageMethod {SUM, KEY_VALUE, REPLACE}

export(String) var key := ""              # 写进 RunData.effects 的哪个键
export(String) var text_key := ""         # 本地化用哪条文案（空则用 key 大写）
export(int)    var value := 0             # 数值
export(String) var custom_key := ""       # 非空 → 写进这个键指向的列表
export(StorageMethod) var storage_method = StorageMethod.SUM
export(Sign)   var effect_sign := Sign.FROM_VALUE     # 文本用什么颜色
export(Array, Resource) var custom_args := []          # 文本参数的覆写规则
```

### 1.2 `apply()` 的三条分支，就是整个系统

```gdscript
func apply() -> void:
    if custom_key != "" or storage_method == StorageMethod.KEY_VALUE:
        RunData.effects[custom_key].push_back([key, value])     # ① 入列表
    elif storage_method == StorageMethod.REPLACE:
        base_value = RunData.effects[key]                        # ② 覆盖（记住旧值）
        RunData.effects[key] = value
    else:
        RunData.effects[key] += value                            # ③ 累加
```

`unapply()` 是**逐字对称的逆操作**（`erase` / 还原 `base_value` / `-= value`）。
这条对称性是整个系统能成立的前提——
道具可以被卖掉、武器可以被合成吃掉、角色效果在换角色时要撤销，
全都只靠调一次 `unapply()`。

调用点只有两个，各三行（`源码/singletons/run_data.gd:461-470`）：

```gdscript
func apply_item_effects(item_data: ItemParentData) -> void:
    for effect in item_data.effects:
        effect.apply()
    ChallengeService.check_stat_challenges()
```

**没有 switch、没有注册表、没有事件总线。**

### 1.3 `RunData.effects`：134 个键

`init_effects()` 把两张表合并（`run_data.gd:880-1029`）：

| 来源 | 键数 | 内容 |
|---|---:|---|
| `init_stats()` | **47** | 19 条玩家属性（`stat_*`）+ 28 条全局标量（`weapon_slot: 6`、`dodge_cap: 60`、`gold_drops: 100`、`harvesting_growth: 5`、`hp_cap: 999999`…） |
| `init_effects()` 自有 | **87** | 53 个标量 + 33 个**列表** + 1 个 `BurningData` |
| 合计 | **134** | |

33 个列表型键是"带条件的效果"的载体，全部列出来就能看清这套系统的表达边界：

```
dmg_when_pickup_gold  dmg_when_death  dmg_when_heal  dmg_on_dodge  heal_on_dodge
remove_speed  starting_item  starting_weapon  projectiles_on_death
weapon_class_bonus  weapon_bonus  unique_weapon_effects  additional_weapon_effects
gold_on_crit_kill  stat_links  structures  explode_on_hit  explode_on_death
```

**命名就是设计**：`temp_stats_while_moving` / `while_not_moving` / `on_hit` / `stacking`
这一组四个键，等于把"临时属性"这个概念拆成了四种触发条件，
每一种只要有一个消费点就能支撑任意多件道具。

## 3. 三种存储方式各自负责什么

### 3.1 SUM（651 条，92%）：属性与全局标量

最朴素的一条。`stat_max_hp += 8`、`items_price += -15`、`gold_drops += 20`。
因为是纯加法，**同一件道具叠 N 份就是 `apply()` 调用 N 次**，天然支持堆叠。

### 3.2 push_back（54 条）：带条件的一组属性

`custom_key` 非空时，效果被塞进那个列表键，形如 `[key, value]`。
典型用法是"在某种条件下加某条属性"：

| `custom_key` | 条数 | 含义 |
|---|---:|---|
| `temp_stats_while_not_moving` | 11 | 站着不动时临时加属性 |
| `starting_item` / `starting_weapon` | 6 / 6 | 开局白送 |
| `stats_end_of_wave` | 5 | 每波结束加属性 |
| `consumable_stats_while_max` | 3 | 满血捡消耗品时加属性 |
| `unique_weapon_effects` | 3 | 按持有的不重复武器数生效 |
| 其余 12 种 | 各 1~2 | `dmg_when_pickup_gold`、`heal_on_dodge`、`convert_stats_half_wave`… |

⚠ **这里有一个数据层面的陷阱**：`apply()` 的判断是
`if custom_key != "" or storage_method == KEY_VALUE`——
**`custom_key` 非空时 `storage_method` 字段被完全忽略**。
902 条里有 **50 条** `custom_key` 非空但 `storage_method` 标成 `SUM`，
这 50 条的 `storage_method` 值是**死字段**，改它没有任何效果。
真正标成 `KEY_VALUE` 的只有 4 条（`stats_next_wave` ×2、`consumable_stats_while_max` ×2）。

### 3.3 REPLACE（14 条）：全部都是"改规则"

这 14 条值得整表列出来——它们是全游戏仅有的"覆盖式"效果，
而且**13/14 来自角色，1 条来自危险 5**：

| 键 | 值 | 谁 | 效果 |
|---|---:|---|---|
| `weapon_slot` | **0** | 公牛 Bull | **完全无法装备武器** |
| `weapon_slot` | **12** | 多面手 Multitasker | 12 个武器槽 |
| `max_melee_weapons` / `max_ranged_weapons` | 3 / 3 | 多面手 | 近战远程各限 3 种 |
| `hp_shop` | 1 | 恶魔 Demon | **用最大生命值代替材料买东西** |
| `destroy_weapons` | 1 | 军火商 Arms Dealer | 进商店时所有武器被摧毁 |
| `minimum_weapons_in_shop` | 1 | 军火商 | 商店至少卖一把武器 |
| `min_weapon_tier` | 1 | 骑士 Knight | 只能装 II 级以上武器 |
| `max_weapon_tier` | 1 | 野人 Wildling | 只能装 II 级以下武器 |
| `dodge_cap` | **90** | 幽灵 Ghost | 闪避上限 60% → 90% |
| `can_attack_while_moving` | 0 | 士兵 Soldier | 移动时无法攻击 |
| `trees_start_wave` | 1 | 探险家 Explorer | 树在开波时就长出来 |
| `double_hp_regen_below_half_health` | 1 | 药水（道具） | 半血以下回复翻倍 |
| `double_boss` | 1 | 危险 5 | 第 20 波双 Boss |

**这是整份表里信息密度最高的 14 行**：
Brotato 全部的"这个角色玩法完全不同"，加起来就是这 14 条覆盖 + 30 条 `gain_<stat>` 乘区改写。
[角色构筑指南.md](角色构筑指南.md) §2 分的九组角色，机制底座就在这两处。

注意 `weapon_slot` 在 SUM 和 REPLACE 两条路上都出现过：
独臂 One-Armed 用的是 **SUM** 的 `weapon_slot = -5`（6 − 5 = 1 把），
而公牛和多面手用的是 **REPLACE**（直接定为 0 和 12）。
同一个键、两种语义，靠 `storage_method` 区分——
这是这套 DSL 表达力的上限，也是它最容易读错的地方。

## 4. 子类怎么扩展

### 4.1 只覆写四个方法

一个子类最多写这四样，通常只写前两样：

| 方法 | 干什么 | 必须吗 |
|---|---|---|
| `get_id()` | 返回一个字符串，存档用来认这条效果 | 是 |
| `apply()` / `unapply()` | 写/撤字典，**必须严格对称** | 是 |
| `get_args()` | 给本地化文案填参数（§5） | 否 |
| `serialize()` / `deserialize_and_merge()` | 先调 `.serialize()` 拿父类字段，再补自己的 | 只在有新字段时 |

最小的子类是 `NullEffect`，一共 13 行，`apply` / `unapply` 都是 `pass`。

最典型的是 `StatGainsModificationEffect`（30 条，全游戏最多的子类）：

```gdscript
func apply() -> void:
    for stat in stats_modified:
        RunData.effects["gain_" + stat] += value
```

**三行代码撑起了 Brotato 全部角色的"属性乘区"机制**
（`gain_stat_percent_damage = -100` 就是"这条属性对我完全无效"，
详见 [角色构筑指南.md](角色构筑指南.md) §0①）。

而 `GainStatForEveryStatEffect`（19 条）负责"每 N 点 A 换 1 点 B"：

```gdscript
func apply() -> void:
    RunData.effects["stat_links"].push_back([key, value, stat_scaled, nb_stat_scaled])
```

它的 `stat_scaled` 还支持三个非属性的伪属性——
`materials`（当前材料数）、`structure`（场上炮台数）、`living_enemy`（当前存活敌人数），
在 `get_args()` 里特判。**给 DSL 留三个"伪变量"就多出一整类道具。**

### 4.2 两套完全不同的消费模型

| | 道具侧 | 武器侧 |
|---|---|---|
| 基类 | `Effect` | `NullEffect`（`apply` 为空） |
| 怎么生效 | `apply()` 写进 `RunData.effects`，各系统读字典 | **不写字典**，由持有者用 `if effect is XxxEffect` 就地读 |
| 条数 | 818 | **84** |
| 类 | `Effect` + 13 个子类 | `NullEffect` + 6 个子类 |
| 消费点 | 212 处散在 25 个文件 | `weapon_service.gd:70-85`、`weapon.gd:266`、`unit.gd:283`、`structure.gd:21`、`entity_spawner.gd:336` |

武器侧那 84 条（燃烧、爆炸、击杀叠属性、命中生弹、减速区、同款叠加）
**必须挂在具体武器上才有意义**，所以它们不进全局字典——
挂哪把武器上，就只有那把武器吃。

一个有意思的交叉：`ItemExplodingEffect extends ExplodingEffect`
（后者是 `NullEffect` 派生），但它**把 `apply()` 又覆写回"写字典"**：

```gdscript
func apply() -> void:
    RunData.effects[key].push_back(self)
```

也就是"同一个爆炸效果，挂武器上就地读、挂道具上进字典"。
类继承在这里已经有点绕了，是这套系统里唯一显得别扭的一处。

### 4.3 21 个子类一览

| 子类 | 条数 | 写到哪 | 干什么 |
|---|---:|---|---|
| `stat_gains_modification` | 30 | `gain_<stat>` | 改属性乘区（角色的核心机制） |
| `gain_stat_for_every_stat` | 19 | `stat_links` | 每 N 点 A 换 1 点 B |
| `turret_effect`（← `structure_effect`） | 11 | `structures` | 放炮台 |
| `chance_stat_damage` | 6 | 指定列表 | 带概率的属性/伤害触发 |
| `item_exploding` | 6 | `explode_on_*` | 道具侧爆炸 |
| `structure_effect` | 5 | `structures` | 放构筑物 |
| `class_bonus` | 5 | `weapon_class_bonus` | 角色↔套装硬绑定（5 个角色各一条） |
| `stat_with_max` | 3 | 指定列表 | 带上限的属性 |
| `projectile_effect` | 2 | `alien_eyes` 等 | 周期性发射物 |
| `convert_stat` | 2 | `convert_stats_*` | 波中/波末把一条属性换成另一条 |
| `healing_effect` | 2 | —（发信号） | 立即回血；`unapply` 为空（不可逆） |
| `stat_cap_effect` | 1 | 指定键 | 把上限设成当前某条属性的值 |
| `burn_chance_effect` | 1 | `burn_chance` | 合并燃烧参数 |
| `weapon_bonus` | **0** | `weapon_bonus` | 指定武器 id 加属性——**类写好了但一条数据都没有**；`weapon_bonus` 这个键仍被 `weapon_service.gd:56` 消费，只是没人往里写 |
| `null_effect` | 24 | — | **纯文案**，不产生任何数值 |
| `burning` / `exploding` / `gain_stat_every_killed_enemies` / `projectiles_on_hit` / `slow_in_zone` / `weapon_stack` | 60 | — | 武器侧，就地读 |

`null_effect` 那 24 条值得单说：它存在的唯一目的是**让武器能显示一句说明文字**
（"这把武器会点燃敌人"），而不产生任何数值。
**把"纯文案"也做成一条 Effect，是保证描述与数据不脱节的最省做法**——
文案和数值走同一条管线，就不会出现"改了数值忘了改描述"。

## 5. 文本是自动生成的

`Effect.get_text()` 让**一条效果自动变成一句带正负号配色的本地化描述**，
这是这套 DSL 里最省人力的一块。

默认参数是 `[str(value), tr(key.to_upper())]`——
`key = "stat_max_hp"、value = 8` 就自动取出文案 `STAT_MAX_HP` 并填成「+8 最大生命值」，
颜色由 `effect_sign` 决定。

三个枚举负责覆盖默认行为（`源码/effects/enums/`）：

| 枚举 | 取值 | 用途 |
|---|---|---|
| `Sign` | `POSITIVE` `NEGATIVE` `NEUTRAL` `FROM_VALUE` `FROM_ARG` | 文字颜色。**`FROM_VALUE` 是默认**（正数绿、负数红） |
| `Format` | `USUAL` `PERCENT` `ARG_VALUE_AS_NUMBER` | 数字格式 |
| `ArgValue` | `USUAL` `VALUE` `KEY` `UNIQUE_WEAPONS` `ADDITIONAL_WEAPONS` `TIER` `SCALING_STAT` `SCALING_STAT_VALUE` `MAX_NB_OF_WAVES` | 参数从哪取 |

`Sign` 的 `POSITIVE` / `NEGATIVE` 显式值解决了一个真实问题：
**有些效果数值是正数但对玩家是坏事**。全表有 26 条这样标的，例如
`enemy_speed = +8`、`items_price = +15`、`lose_hp_per_second`、
以及 `max_weapon_tier = 1`（"你无法装备 II 级以上武器"）。
如果只靠 `FROM_VALUE`，这些会被涂成绿色。

`ArgValue` 里的 `UNIQUE_WEAPONS` / `ADDITIONAL_WEAPONS` / `SCALING_STAT_VALUE`
让描述里能显示**运行期实时值**（"每把不重复武器 +3，当前 +18"），
这就是导出表里那些「«运行期»」占位符的来源。

151 条效果（17%）用了 `custom_args` 覆写，最常见的自定义参数是
`chance`(45)、`stat_displayed`(30)、`nb_stat_scaled`/`stat_scaled`(各 19)、
`damage`/`duration`/`spread`/`type`(各 17)。

## 6. 消费端：没有中央派发器

`RunData.effects[...]` 全局被读取 **212 次**，分布：

| 文件 | 消费点 | 读什么 |
|---|---:|---|
| `main.gd` | 50 | 掉落、收获、波末结算、各种触发 |
| `entities/units/player/player.gd` | 34 | 移动、拾取、受击 |
| `ui/menus/shop/shop.gd` | 10 | 免费重掷、物价、血买东西 |
| `singletons/item_service.gd` | 10 | 武器档位上下限、商店结构 |
| `singletons/weapon_service.gd` | 8 | 伤害乘区、套装加成 |
| `global/entity_spawner.gd` | 8 | 敌人数量、树、炮台上限 |
| `entities/units/unit/unit.gd` | 7 | 伤害结算、爆炸 |
| 其余 18 个文件 | 各 1~5 | — |

**每个系统自己去字典里捞它关心的键，没有任何中间层。**
好处是加效果零成本；坏处是**一个键被谁消费只能靠 grep**，
没有编译期保证，拼错键名会静默失败（Godot 字典读不存在的键会报错，
但拼错的是**写入方**时，等于这条效果永远不生效）。

> ⚠ **命名陷阱**：`源码/global/effects_manager.gd` **和这套系统毫无关系**，
> 它管的是粒子与打击特效（`play_hit_particles` 之类），94 行全是表现层。
> 找效果逻辑不要进这个文件。

## 7. 三个实现层面的坑

1. **`custom_key` 非空时 `storage_method` 是死字段**（§3.2）。
   902 条里 50 条标着 `SUM` 但实际走 push_back。改这个字段不会有任何效果。
2. **列表型的 `unapply()` 用 `erase([key, value])` 按值删**。
   Godot 3 的 `Array.erase` 删的是**第一个值相等的元素**，
   所以两件效果完全相同的道具各卖一次不会出错；
   但如果哪天有代码在运行期改了列表里的元素内容，`unapply` 就会静默失败。
3. **`REPLACE` 的 `base_value` 存在 `Effect` 资源实例上**，
   而 `add_item()` **不做 `duplicate()`**（`run_data.gd:328`），
   同一件道具堆 N 份时 N 个持有者共用同一个 `Effect` 对象。
   对 SUM 无所谓（加减对称），但对 REPLACE 就是隐患：
   第二次 `apply()` 会把 `base_value` 存成"已经被覆盖过的值"。
   **0.8.0.3 里不会触发**，因为 14 条 REPLACE 全部来自角色与难度（每局最多一份）。
   但只要有一天把 REPLACE 挂到可堆叠的道具上，这里就会出问题。

---

## 8. 六条可以直接拿走的设计手法

1. **效果 = 一个 `Resource` + 一个全局字典键。** 不要一开始就建事件总线或效果注册表。
   `apply()` / `unapply()` 对称的 8 行代码就能覆盖 92% 的内容需求。
2. **对称的 `unapply()` 是能不能"卖道具 / 换角色 / 合成武器"的前提。**
   这条如果一开始没做，后面补会极其痛苦——所有效果都要重写。
3. **把"条件"做成字典里的列表键，而不是效果的字段**（`temp_stats_while_moving` 等 33 个）。
   加一种触发条件 = 加一个键 + 一个消费点，已有的几百条效果一条都不用动。
4. **给 DSL 留几个伪变量**（`materials` / `structure` / `living_enemy`）。
   `GainStatForEveryStatEffect` 靠三个特判就多出一整类"按局势缩放"的道具。
5. **把"纯文案"也做成一条效果**（24 条 `null_effect`）。
   描述和数值走同一条管线，就不会出现改了数值忘了改描述。
6. **显式的 `Sign` 枚举。** 有些效果数值为正但对玩家是坏事（`enemy_speed +8`），
   只靠数值正负推断颜色一定会出错。全表 26 条要靠这个字段救。

一条反面观察：**这套 DSL 的表达力上限，就是"同一个键两种语义"**。
`weapon_slot` 在 SUM 下是增量（独臂 −5）、在 REPLACE 下是绝对值（多面手 12），
读表的人必须同时看 `key`、`value` 和 `storage_method` 三列才能判断含义。
如果要给自研项目做类似系统，**把"增量键"和"绝对值键"在命名上分开**
（例如 `weapon_slot_add` / `weapon_slot_set`）会省掉大量核对成本。
