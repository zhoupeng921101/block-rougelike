## 二、核心:难度是一套「算法调度」,不是一条曲线

这游戏的数值主体不是经济,是**每一手发什么方块**。棋盘生成有一整套具名算法,按玩家状态调度。

### 2.1c 上报名 ≠ 真实名

包里有**两套中文名**,同一批 id 各给一份:

- `OFFER_TYPE_STRINGS` —— 显示 / 上报口径
- `OFFER_TYPE_REAL_STRINGS` —— 真实名

**43 个算法两者不一致**,方向一律是「把具体的收敛成笼统的」:

| id | 常量 | 上报名 | 真实名 |
|---|---|---|---|
| 1002 | `EFFICIENT_ELIMINATE` | 填空消除 | 高效消除 |
| 1003 | `EMPTYDONGFILL` | 填空消除 | 空洞填空 |
| 1309 / 1321 / 1370 | `ALL_COMBINATION_ID*` | 填空消除 | 全组合填空id9 / id21 / id70 |
| 1401–1403 | `IOS_FILL_BLANK_*` | 填空消除 | IOS位运算填空消除 / 非运算填空 / IOS非运算填空(块池42-2) |
| 2003 | `SUI_JI_NOBAOARD` | 随机 | 首局空牌面随机 |
| 2005 | `RANDOM_BLOCK_BOTTOM` | 随机 | 放置效率出随机 |
| 2014 | `SHANG_JIAN_AND_TIE_HE` | **复活** | 熵增+贴和 |
| 2004 / 2019 | `CLEAR_BOARD_BLANK(_IOS)` | 填空消除 | 清屏填空 / 清屏填空-ios |

上报口径把 508 个算法压到 `填空消除`(21)、`死亡难题`(10)、`熵增3`(8)、`随机`(4)、`直觉难题`(4)、`复活`(4)、`终止刷分`(4) 这些大桶里。

**设计要点**:最值得注意的是 id 2014 —— 真实行为是「熵增+贴和」(加难度),上报成「**复活**」。这类映射意味着**数据面板上看到的算法分布和实际跑的不是一回事**,做归因分析时必须用 `REAL_STRINGS` 那一列。

### 2.2 行为驱动的算法选择

出处:`JS数值表/class/ClassUserBehaviorConfig.useBehaviorAlgorithm.json`

十个算法名按玩家行为切换:`填空消除 / 死亡难题 / 熵增1 / 熵增3 / 直觉难题 / 简单死亡 / 致死题 / 随机 / 随机无死亡 / 封闭填空消除`。

`JS数值表/class/ClassAlgorithmStrategyConfig.weightRatioArr.json` 给出 **6 套策略 × 8 个分数档**(200/280/310/330/350/380/430/430+),每格是 `"<百分位>_<算法下标>"` 形式的权重串,例如 `"70_2","100_0"` 表示 70% 走算法 2、剩下 30% 走算法 0。六套策略就是六个 A/B 分支。

## 七、A/B 实验体系:289 个 Trait 包 + 单向门

这是整个包最庞大的结构,也是它真正的「数值设计」所在。

### 7.1 规模

- `assets/` 下 312 个 bundle,其中 **290 个以 `Trait` 结尾**,一个开关一个包,可独立热更
- `配置JSON/resources/configs/bundle-traits-local.gp.json` —— Android 侧 **293** 条清单
- `配置JSON/resources/configs/bundle-traits-local.ios.json` —— iOS 侧只有 **109** 条

**Android 的实验密度是 iOS 的 2.7 倍。**

### 7.2 单向门名单

出处:`JS数值表/main/TraitServerOneWayDoorConfig.*.json`

| 名单 | 条数 | 面向 |
|---|---|---|
| `oneWayDoorNewer` | **571** | 新用户 |
| `oneWayDoorActive` | **470** | 活跃用户 |
| `iosOneWayDoorActive` | 105 | iOS 活跃用户 |

前两个名单**交集为 0** —— 新用户和活跃用户走的是完全分离的实验组。
实验 id 范围 `11101`–`1800004`,前缀密集在 `100x`–`106x`(约 300 条)与 `97x`/`98x`/`99x`(约 95 条)。

**「单向门」的含义是命中后不可回退**:一旦把某个用户切进某分支,就永久留在那条路径上。这是为了避免实验反复横跳污染留存数据,代价是**同一版本的线上体验可能存在数百种组合**。

### 7.3 Trait 命名透出的实验方向

按包名关键词归类(一个包可能落进多类,所以合计大于 290):

| 方向 | 命中 | 代表包 |
|---|---|---|
| 复活 / 广告 / 订阅 | **46** | `EndlessRevivePopupReduce` `UnlimitedReviveBeforeHighScore` `ReplaceRewardADToInterstitial` `ResilientPlayerComebackAdReduce` `AdSubScribePopModel*` `Ecpm_player_high_death` |

| 低端机降级 | **20** | `LD*` 与 `LowDevice_*` 成对出现(`LDEnableXxx` 是 `Xxx` 的低端机开关) |

## 九、和 Gossip Harbor 的对照

| | Gossip Harbor | Block |
|---|---|---|
| 数值主体 | 经济(体力 / 双货币 / 合成链公比) | **发牌算法调度** |
| 长线目标 | 300 级 + 主线装修 | **40 套皮肤** |
| 硬闸 | 体力 100 上限,1 点 / 120 秒 | **无体力,无货币** |
| 变现出口 | 买体力、买棋子、加速生成器 | **广告**(兴趣曲线低谷触发) |
| A/B 手段 | 配置表后缀 `_easy` `_hard` `_nerf` 等 8 种 | **289 个可独立热更的 Trait 包 + 单向门** |
| 服务端覆盖 | `LoadServerConfig` | `traitServerInfo` + `TraitServerOneWayDoorConfig` |

**最大的结构差异**:Gossip Harbor 把数值写在表里、用表的变体做 A/B;Block 把数值写成**算法**、用代码包做 A/B。前者能靠读表还原线上;后者读表只能还原「有哪些分支」,**具体哪个用户走哪条,只有服务端知道**。
