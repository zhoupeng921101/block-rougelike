# Phaser 3 全屏后处理能力与 WebGL shader 性能预算

> 调研范围：把 Balatro（LÖVE 2D）的全屏 CRT.fs + background.fs/vortex.fs/flame.fs + 20~40 个带独立 shader 的卡牌 sprite，搬到 Phaser 3 + Vite + TS（仅 localhost、桌面浏览器）的可行性、工作量与风险。
> 调研时间：2026-09。除 web 检索外，部分结论直接来自 `raw.githubusercontent.com` 上 Phaser `v3.90.0` tag 的源码 grep（标注为「源码验证」）。

## 版本前提（先说这个，会影响后面所有结论）

### Takeaway

「Phaser 3 当前稳定版」这个前提需要修正：npm 上 `phaser@latest` 现在指向 **4.2.1**，Phaser 3 线的最后一个版本是 **3.90.0**。选 3.90 意味着选一个已进入维护尾声的分支，但它的 PostFX 生态（文档、rex 插件、examples）最成熟。

### Cited Findings

- npm registry `dist-tags` 实测：`latest = 4.2.1`，`beta = 4.0.0-rc.7`，`alpha = 4.0.0-alpha.4`；`3.x` 系列最高版本为 `3.90.0`（其后是 3.88.2、3.88.1、3.88.0、3.87.0）—— 源码验证，`https://registry.npmjs.org/phaser`
- Phaser 4 引入了全新渲染器，官方有专门的《Phaser 4 Rendering Concepts》深潜文档 — [Phaser 4 Rendering Concepts](https://phaser.io/tutorials/phaser-4-rendering-concepts)
- Phaser 4 新增 `SpriteGPULayer`，官方称「适合复杂动画背景、粒子类效果、星空、人群与程序化环境」，「能比常规 sprite 快上百倍」 — [How to Render Thousands of Sprites in Phaser 4](https://phaser.io/news/2026/05/phaser4-spritegpulayer-performance)

### Inferences

- 本项目卡牌数量只有 20~40，`SpriteGPULayer` 这类大规模批渲染优化对我们没有决定性价值；选 3.90 的主要代价是「未来不再有新特性」，而不是「性能不够」。
- 但 Phaser 4 的 pipeline / filter API 与 3.x 的 `PostFXPipeline` 不兼容（3.x 的 `postPipelines` 概念在 4 中被重构），**现在写的所有 shader 胶水代码在升级到 4 时基本要重写**。这是一个明确的一次性迁移成本，应在决策时计入。

### Gaps

- 没有找到官方对 Phaser 3.90 的 EOL / 安全维护承诺声明。

## Q1. Phaser 3 全屏后处理：setPostPipeline / postFX / 链式 / 代价

### Takeaway

**能做全屏 CRT，而且这是 Phaser 3 的标准用法**：写一个继承 `Phaser.Renderer.WebGL.Pipelines.PostFXPipeline` 的类，在 game config 的 `pipeline` 数组里注册，然后 `camera.setPostPipeline(MyCRT)`。但**内建 FX 里没有 CRT/扫描线/色差**，Balatro 的 CRT 必须自己写 fragment shader；内建 FX 只能凑出「近似观感」而非还原。每个 post pipeline = 一次独立的全屏 render target pass。

### Cited Findings

**用法（两步，缺一不可）**

- 官方论坛明确了两步流程：先在 game config 里注册 `pipeline: [PostFxClass]`，再 `camera.setPostPipeline(PostFxClass)`；社区回复原话是「你必须先 register post-fx pipeline」 — [Phaser Discourse: Applying a shader/effect to the entire canvas/game](https://phaser.discourse.group/t/applying-a-shader-effect-to-the-entire-canvas-game/10669)
- 官方 example 可参考：`camera blur shader`（labs.phaser.io）、`renderer/custom-post-fx-pipeline`、`renderer/color-post-fx-pipeline` — [Custom Post Fx Pipeline](https://phaser.io/examples/v3.85.0/renderer/view/custom-post-fx-pipeline)、[Color Post Fx Pipeline](https://phaser.io/examples/v3/view/renderer/color-post-fx-pipeline)
- Phaser 3.50 的发布公告直接把 CRT 列为 PostFX 的典型用例：「blur、distortion、vignettes、**CRT overlays**、outlines、glows、pixelation、god rays、wave shaders」 — [Phaser 3.50.0 Released](https://phaser.io/news/2020/12/phaser-350-released)

**链式叠加与顺序**

- `setPostPipeline()` 接受数组：`camera.setPostPipeline([FX1, FX2])`；源码里对数组逐个 `getPostPipeline()` 后 **`this.postPipelines.push(instance)`** —— 即**按传入/调用顺序追加，先加的先执行**，没有优先级参数，要改顺序只能 `resetPostPipeline()` 后重新按序添加 — 源码验证 `src/gameobjects/components/PostPipeline.js` L166-191、L279-297（v3.90.0）
- 官方 FX 文档确认可叠加：「A `Barrel` followed by a `Blur` and then topped-off with a `Circle` effect」，靠调整顺序得到不同结果 — [Phaser 3.60 FX changelog](https://github.com/phaserjs/phaser/blob/v3.60.0/changelog/3.60/FX.md)

**内建 FX 清单（3.60+，至 3.90 未变）**

- 源码 `src/fx/index.js` 实际导出 14 个效果 + 1 个 `Controller` 基类：**Barrel、Bloom、Blur、Bokeh(TiltShift)、Circle、ColorMatrix、Displacement、Glow、Gradient、Pixelate、Shadow、Shine、Vignette、Wipe** — 源码验证（v3.90.0）
- PreFX 只对「texture-based」对象可用（Image / Sprite / TileSprite / Text / RenderTexture / Video）；**PostFX 对所有 Game Object 和 Camera 可用** — [Phaser 3.60 FX changelog](https://github.com/phaserjs/phaser/blob/v3.60.0/changelog/3.60/FX.md)
- 官方性能建议原话：「Applying effects to cameras rather than individual Game Objects provides significantly better performance for scene-wide effects.」 — 同上
- FX 是 **WebGL only**，Canvas 模式不可用 — [Phaser FX 概念文档（搜索摘要）](https://docs.phaser.io/phaser/concepts/fx)

**全屏 post pipeline 的实现代价**

- `PostFXPipeline` 默认 `config.renderTarget = 1`（即申请 1 个全屏 render target），`config.batchSize = 1`，内部只有**一个硬编码的全屏 quad**（两个三角形，attributes 仅 `inPosition` vec2 + `inTexCoord` vec2） — 源码验证 `src/renderer/webgl/pipelines/PostFXPipeline.js`（v3.90.0）
- 类注释原文：Game Object「先用自己的标准 pipeline 渲染，但被重定向到 post pipeline 拥有的 Render Targets，再由 post pipeline 施加自己的 shader 与效果，然后交回主渲染器」 — 同上
- `RenderTarget` 构造带 **`scale` 参数**，`resize` 里 `width = Math.round(width * this.scale)`、`height = Math.round(height * this.scale)` —— **降采样是原生支持的**，把 `scale` 设成 0.5 即可让后处理在 1/4 像素数上跑 — 源码验证 `src/renderer/webgl/RenderTarget.js` L105、L283-284（v3.90.0）
- `PostFXPipeline` 提供的 helper：`copyFrame` / `copySprite` / `drawFrame` / `blendFrames` / `blendFramesAdditive` / `blitFrame` / `copyFrameRect` / `bindAndDraw` / `clearFrame` —— 多 pass 效果要自己在这些之间 ping-pong — 源码验证（v3.90.0）
- **`camera.postFX.addXxx()` 每加一个效果就是一个独立的 post pipeline 实例**：`FX` 组件的 `add()` 在 `isPost` 分支里直接调 `this.gameObject.setPostPipeline(type, config)`，再把 controller 挂到取回的 pipeline 上 — 源码验证 `src/gameobjects/components/FX.js` L395-415（v3.90.0）
- 对比：PreFX 走的 `FXPipeline` 是**一个** pipeline 内含 16 个 shader，`onDraw` 里遍历 `sprite.preFX.list`，对每个 active controller 调一次 handler，内部 `runDraw()` 做 `copy(source, target)` 并在 3 个 render target 间 ping-pong —— 仍然是 **N 个效果 ≈ N 次全屏 copy** — 源码验证 `src/renderer/webgl/pipelines/FXPipeline.js`（v3.90.0）

### Inferences

- **结论：每个 camera post pipeline 都是一次「读全屏纹理 → 跑 fragment shader → 写另一张全屏纹理」的 pass。** 3 个 postFX 叠加 ≈ 3 次全屏 fill + 至少 2 次 RT 切换。所以**能合并就合并到一个 shader 里**：Balatro 的 CRT（扭曲 + 扫描线 + 色差）本来就是一个 `CRT.fs`，照搬成**一个** PostFXPipeline 即可，不要拆成 barrel + scanline + chromatic 三个 pass。
- 用内建 FX 拼 CRT 的可行性逐项判断（推论，基于各 FX 的语义）：
  - `Barrel` → 屏幕桶形扭曲，**能**对应 CRT 的 curvature；
  - `Vignette` → **能**对应 CRT 边缘压暗；
  - `Bloom` / `Glow` → **能**近似 phosphor 辉光；
  - `Pixelate` → 只能做方块化，**不能**做扫描线（扫描线是逐行 alpha 调制）；
  - `Displacement` → 需要一张位移贴图，理论上能做屏幕扭动但不适合做静态 barrel；
  - `ColorMatrix` → 全局调色，**不能**做色差（chromatic aberration 需要 RGB 三通道**分别偏移采样**，矩阵变换做不到）；
  - `Blur` / `Bokeh` / `Shine` / `Gradient` / `Circle` / `Shadow` / `Wipe` → 与 CRT 无直接对应。
  - **缺口明确：扫描线 + 色差这两项内建 FX 无解**，必须自写 shader。既然都要自写，就一次写完整的 CRT，不要混搭（混搭还多花 2~3 个 pass）。
- `scale` 参数给了一个廉价的性能旋钮：CRT 这种效果在 0.75x 甚至 0.5x 分辨率下跑再上采样，观感损失小（CRT 本来就是「糊」的），fill-rate 直接降到 56%/25%。

### Gaps

- 没有查到 Phaser 3 是否会在多个 camera post pipeline 之间复用同一组 RenderTarget（还是每个 pipeline 各自持有全屏 RT）。如果是后者，显存占用 = N × 全屏 RGBA。建议实测时看 `renderer.renderTargets`。
- `docs.phaser.io` 在本次调研环境被网络策略拦截，FX 的完整参数表没能逐项抓到原文，上面的 FX 语义判断部分依赖搜索摘要与推论。

## Q2. 社区现成的 Phaser 3 CRT shader

### Takeaway

有三条现成路径：**RetroZone**（专门的开源 retro 显示引擎，明确支持 Phaser）、**rex 的 Horri-fi post FX 插件**（含 scanlines / CRT 参数）、以及官方 examples 里的自定义 post FX 模板。但没有任何一个是「Balatro CRT.fs 的 Phaser 移植」——Balatro 的 CRT 需要自己搬。

### Cited Findings

- **RetroZone**：免费开源 retro 显示引擎，作者 Marco van Hylckama Vlieg，仓库 `https://github.com/TheMarco/retrozone`。它「post-process 你画在 canvas 上的任何东西」，用 WebGL shader 实现 phosphor glow、scanlines、vector display。CRT 模式包含「gaussian beam scanlines、Trinitron aperture grille、halation、warm color temperature、interlace flicker」；Vector 模式含 multi-pass bloom、per-channel persistence trails、**chromatic aberration**、grain。明确声称「Works with Phaser, PixiJS, Three.js, or plain Canvas2D」，无引擎锁定 — [RetroZone: CRT and Scanline Effects for HTML5 Games (phaser.io news)](https://phaser.io/news/2026/03/retrozone-open-source-retro-display-engine-phaser)
- RetroZone 对 Phaser 的具体建议：Graphics 对象要设成 additive blending，让重叠的 glow pass 相加而非遮挡；形状分三 pass 渲染（outer glow / mid bloom / sharp core） — 同上
- **rex Horri-fi**：rexrainbow 的 phaser3 插件，post FX pipeline，含 scanlines 与 CRT 效果，可配置属性包括 `scanStrength`、`crtWidth`、`crtHeight` — [Horri-fi - Notes of Phaser 3](https://rexrainbow.github.io/phaser3-rex-notes/docs/site/shader-horrifi/)（注：本次 WebFetch 该页时 socket 关闭，细节来自搜索摘要，**使用前需自行核对**）
- **rex Barrel shader**：单独的桶形畸变 shader 插件 — [Barrel - Notes of Phaser 3](https://rexrainbow.github.io/phaser3-rex-notes/docs/site/shader-barrel/)
- rex 还有 post fx pipeline 的通用教程页（本次访问 404，可能已迁移到 Phaser 4 的 `camera-shader-effect` 页） — [camera-shader-effect（Phaser 4 版）](https://rexrainbow.github.io/phaser3-rex-notes/docs/site/camera-shader-effect/)
- 官方 camera shader examples：`camera/render-to-texture-shader-3`、`camera/change-camera-shader` — [Phaser Examples v3.85.0](https://phaser.io/examples/v3.85.0/camera/view/render-to-texture-shader-3)

### Inferences

- RetroZone 是「独立后处理层」而非 Phaser pipeline 插件（它 post-process canvas），接进 Phaser 可能意味着**在 Phaser 的 canvas 之上再叠一层 WebGL context**，这会多一次 canvas→texture 的上传/合成。对只跑 localhost 的项目可接受，但比原生 PostFXPipeline 多一层开销，且可能与 Phaser 自己的 postFX 冲突。**更保守的做法是只借它的 GLSL 代码**（开源），塞进自己的 PostFXPipeline。
- Horri-fi 是最省事的「先跑起来看看」选项（一行 `setPostPipeline`），适合做 spike 验证；最终观感要贴 Balatro 的话还是得换成搬过来的 CRT.fs。

### Gaps

- 没能确认 RetroZone 的 license（页面未提及具体 license 名称），也没能确认它是否提供真正的 Phaser post-pipeline 封装还是只有「叠一层 canvas」的用法。需要直接读 `github.com/TheMarco/retrozone` 的 README。
- Horri-fi 的完整参数表与它是否包含 chromatic aberration 未验证。

## Q3. 全屏动画背景 shader（background.fs / vortex.fs / flame.fs）

### Takeaway

**不要用 `Phaser.GameObjects.Shader` 做常驻全屏背景**——官方明说它会打断 batching。正确做法是**自定义 pipeline**（继承 `WebGLPipeline` 或 `PostFXPipeline`），在 pipeline 的 pre-render 里每帧更新 `time` uniform。而且 Balatro 背景 shader 的 GLSL 已经有现成的 Shadertoy 移植可直接拿。

### Cited Findings

- 官方 `GameObjects.Shader` 文档原话：「Because Shader GameObjects block the pipeline, they interrupt any batching that is currently going on, so you should use these Game Objects **sparingly**. If you need to have a fully batched custom shader, then please look at using a **custom pipeline** instead.」同时承认「for background or special masking effects, they are extremely effective」 — [Phaser GameObjects.Shader 文档（搜索摘要）](https://docs.phaser.io/phaser/concepts/gameobjects/shader)
- 官方教程《Shader Tutorial — EarthBound's Scrolling Background Effect》用的就是 **custom pipeline class**，不是 `GameObjects.Shader`；uniform 更新原话：「Update these uniforms in the pipeline's **pre-render method** each frame」；示例建立两个 uniform：`Time`（elapsed game time，驱动动画）与 `Speed`（横纵滚动速率） — [Shader Tutorial — EarthBound's Scrolling Background Effect](https://phaser.io/news/2025/12/shader-tutorial-earthbounds-scrolling-background-effect)
- 官方性能提示：「如果你有一张全屏背景图或 game object，可以关掉帧间的 canvas 清屏（`clearBeforeRender`）」 — 同上来源搜索摘要
- **Balatro 背景 shader 已有公开 WebGL/GLSL 移植**：
  - Shadertoy `XXtBRr`「Balatro Background Shaders」 — [Shadertoy XXtBRr](https://www.shadertoy.com/view/XXtBRr)
  - Shadertoy `WXGBWm`「Balatro Background (Optimized)」——**已有人做过性能优化版** — [Shadertoy WXGBWm](https://www.shadertoy.com/view/WXGBWm)
  - Shadertoy `w3lGzH`「balatro main menu background」 — [Shadertoy w3lGzH](https://www.shadertoy.com/view/w3lGzH)
  - Godot Shaders 上的「Balatro Background Shader」，作者注明**直接取自 Balatro 源码**，并引用了上面的 Shadertoy 链接 — [Godot Shaders: Balatro Background Shader](https://godotshaders.com/shader/balatro-background-shader/)
  - Godot Shaders「Balatro Paint Mix」，注释写明「取自 Balatro 源码」的原始 paint swirl shader — [Godot Shaders: Balatro Paint Mix](https://godotshaders.com/shader/balatro-paint-mix/)

### Inferences

- 两种方式的代价对比：
  - `GameObjects.Shader` 铺满屏：实现最快（几行），但**每出现一个就强制 flush 一次 batch**。如果背景是场景里唯一/最底层的一个，flush 代价实际上只有 1 次（背景先画，后面卡牌才开始 batch），**对本项目其实可以接受**。它真正的问题是不能和其他 sprite 混在同一层里用。
  - 空 Image + 自定义 pipeline / PostFXPipeline：多写十几行胶水，但完全融入 Phaser 的渲染流程，`time` uniform 在 `onPreRender` 里更新，没有额外 flush。**推荐这个。**
  - 第三条路（最省）：把背景做成**最底层的一个 camera post pipeline**，或者用 `PostFXPipeline` 但不读 source 纹理而是纯程序化输出——不过那样会覆盖已画内容，要改成先画背景 pass。实践上还是「空 Image + custom pipeline」最直接。
- **`background.fs` 的移植风险几乎为零**：已有三个独立的 Shadertoy 版本（Shadertoy 就是 WebGL + GLSL ES），意味着这段 GLSL 在 WebGL 上已被验证能跑。移植工作 ≈ 把 `mainImage(out vec4 fragColor, in vec2 fragCoord)` 改成 `main()` + `gl_FragColor`，`iTime` → 自定义 `uniform float uTime`，`iResolution` → `uResolution`。这是机械改写，**每个 shader 半小时到一小时量级**。
- 「Optimized」版本的存在本身是一个信号：**原版 Balatro 背景 shader 的 fill-rate 成本不低**，有人专门优化过。全屏跑它是本项目最大的 GPU 成本项（见 Q4）。

### Gaps

- 没有抓取 Shadertoy 上那几个 shader 的实际源码与指令数/采样次数（Shadertoy 页面是 JS 渲染的，WebFetch 拿不到代码）。**优化版相对原版省了多少，未量化。** 建议实测：把 `WXGBWm` 贴进 Shadertoy 自己看帧率，或直接移植后用浏览器 profiler 量。
- `vortex.fs` / `flame.fs` 没有找到公开的 WebGL 移植先例，只有 `background.fs`(paint mix) 有。

## Q4. 性能预算（关键）

### Takeaway

**判断：有条件能。** 30~60 次 draw call + 2~3 个全屏 pass，在中档集显笔记本上跑 60fps **不是 draw call 问题，而是 fill-rate 问题**——瓶颈在全屏 fragment shader 的复杂度和 pass 数量，不在卡牌数量。具体：卡牌部分（20~40 个小 sprite，每个切 shader）**几乎必然够用**；全屏背景 shader + CRT 后处理**取决于 shader 本身**，有翻车可能，但有明确的止损手段（RenderTarget `scale` 降采样、合并 pass、简化噪声）。

### Cited Findings

**draw call 预算**

- 性能预算框架建议：60fps 总预算 16.6ms，其中 draw call 约占 4ms；桌面硬件上单次 draw call 约 **50~200 微秒 CPU 时间**，折算 4ms 预算 ≈ **20~80 次 draw call** — [Digital Strategy Force: GPU Performance Budgets](https://digitalstrategyforce.com/journal/what-are-gpu-performance-budgets-and-how-do-you-optimize-render-pipelines/)（**注意：这是二手聚合来源，非一手 benchmark，数量级参考即可**）
- 反例数据点：Windows 7 + Nvidia 实测可维持约 **75,000 次 draw call** 而不掉到 60fps 以下，但该数字严重依赖硬件 instancing，属极端情况而非典型预算 — 同上来源引用
- MDN 官方建议：「'Batching' draw calls into fewer, larger draw calls will generally improve performance. If you have 1000 sprites to paint, try to do it as a single `drawArrays()` or `drawElements()` call.」 — [MDN: WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- MDN：texture atlasing 的价值在于「切换纹理就必须拆 batch」，atlas 让更多 draw call 合并进更大的 batch — 同上

**shader 切换（useProgram）与 uniform 上传**

- NVIDIA GLES2 性能文档：切换 shader program（`glUseProgram`）**可能非常昂贵**，因为 program 负责保存/恢复它全部 uniform 的状态，**开销随 shader 的 uniform 数量增长**；建议把可绘制对象按 shader program 这类昂贵状态**分组累积后一起渲染**，只在每组开头切一次状态 — [NVIDIA: GLES2 perf — maximize GPU](https://docs.nvidia.com/gameworks/content/technologies/mobile/gles2_perf_maximize_gpu.htm)
- MDN 间接佐证「程序切换会 flush 管线」：「Most texture uploads from DOM elements will incur a processing pass that will temporarily switch GL Programs internally, **causing a pipeline flush**」，并建议把上传集中在绘制开始前或 pipeline 之间 — [MDN: WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- 有引擎在讨论「缓存未变化的 vec4 uniform、避免无条件调用 `glUniform4fv`」以降低 CPU 提交开销 — [neotolis-engine issue #422](https://github.com/d954mas/neotolis-engine/issues/422)

**Phaser 3 自身的 batch 参数**

- **`batchSize` 默认 4096**（单位是 *quads*，不是顶点），注释：「The default WebGL Batch size. Represents the number of _quads_ that can be added to a single batch」 — 源码验证 `src/core/Config.js` L441-443（v3.90.0）
- 对比：Phaser 4 master 已把该默认值提到 **16384** — 源码验证 `src/core/Config.js`（master, v4.2.1）
- `maxTextures` 默认 `-1`（用满所有可用纹理单元）；注释：「The WebGL1 spec says all browsers should provide a minimum of 8」 — 源码验证 `src/core/Config.js` L446-448（v3.90.0）
- `autoMobilePipeline` 默认 `true`：检测到 iOS/Android 就自动启用 Mobile Pipeline — 源码验证 `src/core/Config.js` L364-366（v3.90.0）；搜索摘要补充：该路径下 WebGL 被限制为**每个 batch 只用 1 张纹理** — [Phaser Config 文档（搜索摘要）](https://docs.phaser.io/api-documentation/class/core-config)
- `mipmapRegeneration` 注释里给了一个罕见的官方量级数据：「Mipmap generation is expensive (**10 microseconds or more per texture**), so be careful with this setting」（默认 `false`） — 源码验证 `src/core/Config.js` L370-372（v3.90.0）

**fill-rate / 移动端**

- MDN：不要假设系统限制，「Don't assume you can use thirty texture samplers per shader just because it works on your machine!」 — [MDN: WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- MDN 移动端坑：大多数移动系统**不支持把 RGBA32F 纹理挂到 framebuffer**（`checkFramebufferStatus()` 返回 `FRAMEBUFFER_INCOMPLETE_ATTACHMENT`）；iOS 上 float 纹理必须用 `highp sampler2D`，否则会静默降到 `lowp` — 同上
- MDN：「Storing data that you won't use again can have high cost, particularly on **tiled-rendering GPUs common on mobile**」，建议用 `invalidateFramebuffer` 丢弃 — 同上
- MDN 未直接论述 fill-rate/overdraw 与 framebuffer copy 的成本（本次抓取的 best-practices 页中没有这两节）

### Inferences

**逐项判断（这是本节的结论）**

1. **20~40 个卡牌各自一个 shader → 能。**
   - 40 次 `useProgram` + uniform 上传，按桌面 draw call 50~200μs 的上限算最多 8ms，按下限算 2ms。看起来吓人，但那个 50~200μs 是「复杂场景下的 draw call 均摊成本」，对**只画一个 quad、uniform 不到 10 个**的 post/sprite shader，实际 CPU 提交成本远低于这个区间。**风险来自 CPU 侧的 JS 开销（Phaser 每次 flush 的簿记），不是 GPU。**
   - 真正的浪费是 **batch 被打断**：Phaser 的 `batchSize=4096` quads 意味着 40 张卡本可以 1 次 draw call 画完；给每张卡挂独立 pipeline/postFX 后变成 40+ 次 flush，**batch 优势完全归零**。但 40 次 flush 在桌面上仍是毫秒级以内的量级。
   - **更优解（强烈建议）**：不要给每张卡一个 pipeline，而是做**一个统一的卡牌 shader**，用 per-sprite 的 uniform / 顶点属性（`pipelineData` 或自定义 attribute）区分 Foil / Holographic / Polychrome / Negative 等 edition。这样能把 40 张卡合回少数几个 batch。Balatro 本身就是靠 LÖVE 的 `send()` 传参 + 少数几个 shader 文件（不是 40 个不同 shader）。
2. **2~3 个全屏 post pass → 能，但要管住 shader 复杂度。**
   - 1080p = 约 200 万像素。一个 pass 就是 200 万次 fragment shader 调用。集显（如 Intel Iris Xe）的 fill-rate 大约能在 16ms 内做几千万到一亿次「简单」fragment。3 个简单 pass（600 万次简单调用）**轻松**；但如果背景 shader 里有多层 fbm 噪声（每像素几十次 `sin`/`fract`/纹理采样），单个 pass 就可能吃掉 5~10ms。
   - **这是全项目唯一的真实风险点。** 依据：社区专门做了「Balatro Background (Optimized)」版本，说明原版确实重。
3. **卡牌 shader 的 fill-rate → 不是问题。** 用户自己的观察是对的：40 张卡各占屏幕百分之几，加起来的像素总量远小于一个全屏 pass。**卡牌 shader 哪怕写得很复杂，成本也远低于背景。** 预算应该优先给卡牌、优先砍背景。
4. **移动端 / 低端设备（供参考，不阻塞本项目）**：`autoMobilePipeline` 会自动退到单纹理 batch；tiled GPU 上多个全屏 RT 的读写（每次 pass 都要 resolve tile buffer 到显存）代价远高于桌面；float RT 不可用。**如果将来要上移动端，全屏后处理 pass 数必须压到 1。**

**性能止损手段（按性价比排序）**

| 手段 | 收益 | 代价 |
|---|---|---|
| `RenderTarget` 的 `scale` 设 0.5~0.75 跑 CRT | fill-rate 降到 25%~56% | CRT 本来就糊，观感损失小 |
| 把 CRT 的扭曲/扫描线/色差合并进**一个** fragment shader | 3 pass → 1 pass | 需要自己写完整 CRT.fs（本来就要写） |
| 背景 shader 降采样后上采样（背景是低频的） | fill-rate 大降 | 几乎无损 |
| 背景改为「每 N 帧更新一次 RT」 | 背景成本 /N | 动画变卡，需权衡 |
| 卡牌合并为统一 shader + per-instance uniform | 40 次 flush → 少数几次 | 实现复杂度上升 |
| `clearBeforeRender: false`（有全屏背景时） | 省一次全屏 clear | 必须保证背景真的铺满 |

### Gaps

- **没有找到任何针对 Phaser 3 post pipeline 的一手 benchmark 数据**（帧时间 vs pass 数 vs 分辨率）。上面的 draw call 数字来自二手聚合来源，可信度中等，仅供数量级参考。
- 没有找到「中档集显 60fps 下可承受的 fragment shader 指令数」这类可引用的硬数据。这个只能靠实测。
- MDN 的 WebGL best practices 没有覆盖 fill-rate/overdraw 与 framebuffer copy 成本，未找到等价权威来源。
- Phaser 每次 pipeline flush 的具体 JS/CPU 开销没有公开量化数据。

**建议的最小验证实验（做这个比继续查资料有用得多）**：
新建空 Phaser 3.90 工程 → 铺一个全屏 `background.fs`（从 Shadertoy `XXtBRr` 移植）+ 挂一个自写 CRT PostFXPipeline + 放 40 个带 postFX 的小 sprite，开 Chrome DevTools Performance 看 GPU 帧时间。**半天工作量，能把上面所有不确定性一次性消除。**

## Q5. Phaser 3 的 WebGL 版本（决定写 GLSL ES 1.00 还是 3.00）

### Takeaway

**Phaser 3.90 是纯 WebGL 1，无法强制 WebGL 2** —— 渲染器源码里只请求 `'webgl'` 上下文，没有 `'webgl2'` 分支。**所有 shader 必须写 GLSL ES 1.00**（`gl_FragColor`、`texture2D`、`varying`/`attribute`，无 `#version` 行）。

### Cited Findings

- Phaser 3.90 `WebGLRenderer.js` 唯一的上下文创建语句：`gl = canvas.getContext('webgl', config.contextCreation) || canvas.getContext('experimental-webgl', config.contextCreation);` —— **没有任何 `'webgl2'` 字样** — 源码验证 `src/renderer/webgl/WebGLRenderer.js` L770（v3.90.0）
- Phaser 4 master 的对应位置仍是 `canvas.getContext('webgl', ...) || canvas.getContext('experimental-webgl', ...)`（L709），但下方 L896-897 有注释：「Make WebGL2 core features which were extensions available on the WebGL1 context. This allows us to use a WebGL2 context.」—— 即 Phaser 4 做了 WebGL1/2 的特性归一化，但默认仍从 `'webgl'` 起步 — 源码验证（master, v4.2.1）
- Phaser 3 的 `maxTextures` 注释以 **WebGL1 spec** 为基准描述最低保证（8 个纹理单元） — 源码验证 `src/core/Config.js`（v3.90.0）
- 存在第三方对 Phaser 4 的 fork 以补全 WebGL 2：「Circolo 的开发需要更高级的渲染能力，于是团队 fork 了 Phaser 4.0 并加上了完整 WebGL 2.0 支持」 — [Phaser 4.0 forked with full WebGL 2.0 support](https://phaser.io/news/2025/11/phaser-40-forked-with-full-webgl-20-support)

### Inferences

- **Balatro 的 LÖVE shader 正好对口。** LÖVE 的 GLSL 方言基于 GLSL ES 1.00/OpenGL 2.x 语法（`vec4 effect(...)`、`Texel()`），转 WebGL 1 的 GLSL ES 1.00 是**平移级改写**，不需要处理 `in/out`、`texture()`、`layout` 这些 ES 3.00 差异。这反而降低了移植成本。
- 要注意的 GLSL ES 1.00 限制：**不支持非常量索引的数组下标、不支持动态循环上界（循环次数必须编译期可知）、`precision` 必须显式声明**。Balatro 的 shader 如果有 `for (int i = 0; i < n; i++)` 且 `n` 是 uniform，必须改成常量上界 + `break`。
- 也不能用 ES 3.00 的便利特性：`textureLod`、整数运算、多渲染目标（MRT）、`gl_FragDepth` 等。对 CRT + 卡牌效果来说**都用不上**，不构成障碍。

### Gaps

- 没有验证 Phaser 3.90 是否提供任何配置项能换成 WebGL2 context（grep 未发现，但只搜了 `WebGLRenderer.js` 与 `Config.js`，不排除有其它注入点）。实践上可以自己先 `canvas.getContext('webgl2')` 再传 `canvas` 给 Phaser——但 Phaser 3 内部的扩展检测逻辑全按 WebGL1 写，**不建议尝试**。

## Q6. Vite + TS 下加载 .glsl / .fs

### Takeaway

**推荐 `?raw`**，零依赖、零配置、TS 类型开箱即用。只有当需要 `#include` 拆分多文件 shader 或要压缩 GLSL 时，才上 `vite-plugin-glsl`。

### Cited Findings

- Vite 原生支持 `?raw` 后缀把文件作为字符串导入，例：`import vertexShader from "./VertexShader.vert?raw"`；该导入**本身就有 string 类型**，可用于任意文件类型 — [How to use Glsl shader files with Typescript](https://medium.com/@jarekmyjak/how-to-use-glsl-shader-files-with-typescript-c1d50fc72244)
- `vite-plugin-glsl`：「Import, inline (and minify) GLSL/WGSL/Slang shader files」；自 **v1.1.1 起有完整 TypeScript 支持**；TS 配置方式是在 `tsconfig.json` 的 `types` 数组里加 `"vite-plugin-glsl/ext"` — [vite-plugin-glsl (GitHub)](https://github.com/UstymUkhman/vite-plugin-glsl)、[vite-plugin-glsl (npm)](https://www.npmjs.com/package/vite-plugin-glsl)
- 若不用插件而用 `?raw`，需在项目根建 `index.d.ts` 声明 glsl 模块（部分教程做法；实际上 `?raw` 已被 `vite/client` 类型覆盖，通常只需 `"types": ["vite/client"]`） — [delasign: React, Typescript & ThreeJS GLSL Vite](https://www.delasign.com/blog/reactjs-3js-vitejs/)
- 另有 `vite-plugin-glslify`（走 glslify 生态） — [KusStar/vite-plugin-glslify](https://github.com/KusStar/vite-plugin-glslify)

### Inferences

**推荐方案**：
```ts
// tsconfig.json -> compilerOptions.types 包含 "vite/client"
import crtFrag from './shaders/crt.frag?raw';   // string

class CRTPipeline extends Phaser.Renderer.WebGL.Pipelines.PostFXPipeline {
  constructor(game: Phaser.Game) {
    super({ game, renderTarget: true, fragShader: crtFrag });
  }
}
```
- 本项目 shader 数量不多（CRT + background + vortex + flame + 几个卡牌 edition），**不需要 `#include` 机制**，`?raw` 足够。
- 只跑 localhost，不在乎 GLSL 体积，`vite-plugin-glsl` 的 minify 收益为零。
- 如果后面发现多个 shader 共享噪声函数库想复用，再切到 `vite-plugin-glsl` 的 `#include`——切换成本只是改 import 后缀。

### Gaps

- 无。这一项有明确标准答案。

## 工作量与风险汇总（跨问题的综合判断）

### 工作量估计（推论，基于以上事实）

| 任务 | 估计 | 依据 |
|---|---|---|
| Phaser 3.90 + Vite + TS 工程骨架 + `?raw` shader 加载 | 0.5 天 | Q6，标准做法 |
| 写第一个 `PostFXPipeline`（哪怕只是 tint）跑通全链路 | 0.5 天 | Q1，两步注册流程是唯一的坑 |
| 移植 `CRT.fs`（LÖVE → GLSL ES 1.00） | 1~2 天 | Q5，语法平移 + 调参对观感 |
| 移植 `background.fs` | 0.5 天 | Q3/Q7，已有 Shadertoy 版本 |
| 移植 `vortex.fs` / `flame.fs` | 各 0.5~1 天 | Q7，无现成移植 |
| 卡牌 edition shader（foil/holo/polychrome/negative）+ 统一 pipeline 架构 | 3~5 天 | Q4/Q7，foil/holo 有现成 GLSL，架构设计是主要成本 |
| 性能调优（降采样、合 pass、profile） | 1~2 天 | Q4 |

**合计约 7~12 个工作日**，前提是对 GLSL 不陌生。

### 风险排序

1. **高：全屏背景 shader 的 fill-rate。** 唯一可能导致「做完了但跑不动」的项。**缓解：第一周就做 spike 实测。** 有「Optimized」版可退。
2. **中：Phaser 3 已停止演进 + Phaser 4 pipeline API 不兼容。** 未来升级要重写 shader 胶水层。**缓解：把 pipeline 封装隔离在 1~2 个文件里。**
3. **中：卡牌 shader 架构。** 「每卡一 pipeline」写起来最快但会彻底废掉 batching；「统一 shader + per-sprite uniform」正确但要提前设计。**在写第一张卡之前就要定。**
4. **低：GLSL ES 1.00 的限制。** 动态循环上界要改常量。机械工作。
5. **低：shader 版权。** 不逐行抄 Godot Shaders 上标注「from Balatro source」的代码。
6. **不适用（但值得知道）：移动端。** tiled GPU 上多 pass 后处理代价高，`autoMobilePipeline` 会退化为单纹理 batch，float RT 不可用。若将来要上移动端，全屏 pass 必须压到 1 个。
