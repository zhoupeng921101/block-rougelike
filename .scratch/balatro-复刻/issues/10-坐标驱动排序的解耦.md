# 坐标驱动排序的解耦

Type: wayfinder:grilling
Status: resolved

## Question

Balatro 的计分顺序读屏幕坐标：
`table.sort(scoring_hand, function(a,b) return a.T.x < b.T.x end)`
（`源码/functions/state_events.lua:621`，另见 `:413` 出牌、`:484` 弃牌）。

`T.x` 是卡牌的渲染 transform。LÖVE 与 Phaser 的坐标体系、布局时机、
以及「卡牌动画到位之前 x 是多少」都不同——原样直译会让排序在动画中途取到错误的值。

这条有实际后果：`参考/结论/Balatro_1.0.1o/出牌结算管线.md` §2 指出，
「打出的第一张计分牌」（未断选票、照片吃的那个）就是最左边那张，**玩家靠调手牌顺序控制它**。
排序错了，这类小丑的行为就错了，而且是静默地错。

候选方案：

- **显式 order 字段**：逻辑层给每张牌一个 `order:number`，表现层布局后写回。
  干净，但要保证「写回」发生在计分读取之前，否则同样取到脏值。
- **逻辑层自持牌序**：手牌区在逻辑层就是一个有序数组，`T.x` 完全不进逻辑。
  最稳，但要核对原版所有「靠拖动改变顺序」的交互是否都能映射成数组重排。
- **原样直译**：TS 侧也维护一个 `T.x`，由表现层驱动。最贴近原版，
  但把渲染时序变成了正确性的一部分——与对拍目标相冲。

要确认的前置事实：除了这三处 sort，还有多少地方直接读 `T.x` / `T.y` 做**逻辑**判断。
先 grep 再定方案。

带着推荐答案去问用户。

## Answer

**原样直译：TS 侧也维护 `T.x`，连 `align_cards` 每帧重算位置再排序都搬过来。**

与 [03 号票](03-Lua到TS的翻译策略.md) 的直译裁定一致，且不存在译错的可能。
但这个选择有一个**前提条件必须先钉死**，见下面「落地时的硬约束」。

### 先纠正本票自己的前提

票里写「原样直译会让排序在动画中途取到错误的值」——**这不会发生**，前提搞错了。

调查清楚的机制（`cardarea.lua:416` `CardArea:align_cards()`）：

```lua
for k, card in ipairs(self.cards) do
    if not card.states.drag.is then        -- 没被拖的牌
        card.T.x = <由下标 k 算出的位置>     -- 位置由下标决定
    end
end
table.sort(self.cards, function(a,b) return a.T.x + a.T.w/2 < b.T.x + b.T.w/2 end)
```

两个关键事实：

1. **`T` 是目标变换，`VT` 才是动画插值的那个。** `Moveable:move_xy`
   （`engine/moveable.lua:405`）驱动 `VT` 趋向 `T`。
   **所有逻辑排序读的都是 `T.x`，全仓没有一处逻辑读 `VT.x`。**
2. 没被拖的牌，`T.x` 每帧**由下标重算**，所以排序对它们是恒等操作。
   只有正在被拖的那张 `T.x` 不被覆盖——**排序就是拖拽提交进数组的方式**。

所以 `T.x` 不是「屏幕坐标驱动逻辑」，它是**拖拽的输入通道**，数组顺序才是真相。
动画不参与任何逻辑判断。

### 规模比票里估的大

票里说「除了这三处 sort」。实际 `align_cards` 一个函数里就有**六处**按 `T.x` 排序
（`cardarea.lua:454 / 470 / 484 / 513 / 534 / 550`），每种 CardArea 类型一处分支。
加上 `state_events.lua` 的三处（`:413` 出牌、`:484` 弃牌、`:621` 计分），共九处。

还有一个特例：`cardarea.lua:534` 的排序键是
`a.T.x + a.T.w/2 - 100*(a.pinned and a.sort_id or 0)`——
**pinned 的牌用一个 −100×sort_id 的偏移强制排到最前**。直译时别把它简化掉。

以及 `card.lua:1114` 用 `T.x` 找「最右边那张高亮牌」，不是排序但同属这一类。

### 落地时的硬约束：T.x 用 tile 单位，不用像素

**`T.x` / `T.y` 的单位是 tile，不是像素**：

| 量 | 值 | 出处 |
|---|---|---|
| `G.TILESIZE` | 20 | `globals.lua:308` |
| `G.TILE_W` / `G.TILE_H` | 21 / 11.2 | `globals.lua:310-311` |
| `G.CARD_W` / `G.CARD_H` | `2.4*35/41` ≈ 2.05 / `2.4*47/41` ≈ 2.75 | `globals.lua:313-314` |

像素换算是 `× G.TILESCALE × G.TILESIZE`，发生在**渲染与输入的边界**
（`moveable.lua:223` 把鼠标像素除回 tile）。

**这条是本票选择能成立的支点。** `align_cards` 里那一堆手调常数
（`0.27`、`1.8`、`0.3`、`0.1*sin(...)`、`shadow_parrallax.x/30`……）
全部是 tile 尺度的。TS 侧若用 Phaser 像素维护 `T.x`，这些常数一个都不能用，
直译立刻退化成重新调参——那就把本票选项的唯一优点丢掉了。

所以实现约定写死一条：

> **逻辑层的 `T` 全程用 tile 单位。Phaser 层只在渲染时乘 `TILESCALE × TILESIZE`，
> 在输入时除回去。换算只允许出现在这一个边界上。**

### 连带影响：倾斜 shader 的标定有依据了

[Phaser 4 渲染路线 spike](13-Phaser4渲染路线spike.md) 留了个问题：
`position()` 里 `scale` 的绝对值要重新标定，因为「Phaser 的 `inPosition` 量纲与原作不同」。

现在有依据了：原作那段数学混用了 **tile 尺度的 `vertex_position.xy`** 与
**像素尺度的 `mouse_screen_pos`**（`sprite.lua:94-98`，`cursor_position * CANV_SCALE`），
这正是调研说的「坐标空间不自洽」。
TS 侧既然把 `T` 统一在 tile 单位，这个换算边界就是显式的，标定变成可推的而不是试出来的。

### 明确不做的

- **不加 `order` 字段。** 数组下标本身就是 order，再加一个字段等于多一份要同步的状态。
- **不把 `T.x` 换成 Phaser 世界坐标。** 见上面的硬约束。
