# 事件队列调度语义的复刻口径

Type: wayfinder:research
Status: resolved

## Question

`E_MANAGER` 的调度语义要复刻到什么精度？

[Lua 到 TS 的翻译策略](03-Lua到TS的翻译策略.md) 查明：队列回调里会调用 `pseudoseed`
（Perkeo、Certificate 等），所以**队列的执行顺序直接决定 RNG 的消费顺序**。
队列因此是逻辑的一部分，不是表现层——它必须和计分核心一样精确。

全仓有 430 处 `G.E_MANAGER:add_event`。要查清：

1. `Event` 的字段语义：`trigger`（`'before'` / `'after'` / `'immediate'` / `'ease'` …）、
   `delay`、`blocking`、`blockable`、`func` 的返回值 `true`/`false` 各自意味着什么。
   源码在 `源码/engine/event.lua`（先确认文件名）。
2. `E_MANAGER:update()` 的处理顺序：队列是 FIFO 还是按 trigger 分桶？
   同一帧内入队的事件，与跨帧的，执行顺序分别是什么。
3. **嵌套入队**：`add_event` 的 `func` 里再 `add_event`（`card.lua` 里有，
   如 `:204-205` 的双层嵌套），新事件插在队尾还是当前位置之后。
4. `delay` 是否影响**顺序**，还是只影响动画时长。
   这条是判定性的：如果 delay 影响顺序，那么复刻件必须跑一套与原版一致的虚拟时钟，
   而不能「把动画时间压成 0 立即执行」。
5. 有没有哪些事件的执行依赖**真实帧率 / dt**。若有，对拍就需要固定步长。

产出：队列语义的完整说明 + TS 侧的实现要点 + 明确回答第 4 条。

与 [LuaJIT RNG 复刻口径](02-LuaJIT-RNG-复刻口径.md) 合起来才构成「同 seed 同局」的完整答案；
那张票只覆盖了 RNG 算法本身，没覆盖消费顺序。

## 范围收窄（来自 [LuaJIT RNG 复刻口径](02-LuaJIT-RNG-复刻口径.md) 的结论）

RNG 那张票查明了一件事，能把本票要保证的东西收窄一大截：

- LuaJIT 的 RNG 状态**是全局单例，但 gameplay 不受其历史影响**——
  四个包装函数在每次消费前都重新播种（`pseudorandom` 无条件播种，
  另外三个的调用点全部传了 seed）。8 个不传 seed 的调用全是纯表现层
  （粒子、抖动、转场牌、标题界面）。旁证：全局流初值是 `os.time()`，原版自己都不指望它可复现。
- **真正的顺序依赖在 `pseudoseed` 的 per-key 浮点状态上**，而它按 key 独立。

所以本票要保证的可以收窄成一句：

> **跨 key 打乱无影响；同一个 key 的调用次数与先后必须逐次对齐。**

这把问题从「复刻整个队列的调度语义」缩小到「确认队列的调度不会改变**同 key 内**的调用序」。
原票的 5 个子问题仍然要答，但判据换成上面这一句——
尤其第 4 问（`delay` 影响顺序还是只影响动画时长），
现在只需回答「会不会导致同 key 的两次调用换序」，而不必追求整个队列逐事件对齐。

## Answer

**判定性问题（第 4 问）的答案：对 RNG 而言，`delay` 不影响顺序。**
**复刻件可以把动画 delay 压成 0 立即执行，RNG 消费顺序不变——前提是保持 FIFO 与 blocking 语义。**

源码 `engine/event.lua`，195 行，全文读过。

### 1. `Event` 的字段语义

| 字段 | 默认 | 含义 |
|---|---|---|
| `trigger` | `'immediate'` | 见下表 |
| `delay` | `0` | 秒，走 `G.TIMERS[self.timer]` |
| `blocking` | **`true`** | 本事件未完成时，阻塞同队列后面所有 `blockable` 的事件 |
| `blockable` | **`true`** | 能否被前面的 blocking 事件拦住 |
| `func` | 返回 true | **返回 `true` 表示完成** |
| `timer` | `'TOTAL'`（暂停时 `'REAL'`） | 用哪个时钟 |
| `no_delete` | nil | `clear_queue` 时是否保留 |

`trigger` 五种：

| | 行为 |
|---|---|
| `immediate` | 立刻跑 `func`，`time_done` 直接为真 |
| `after` | **等 `time + delay <= now` 才跑 `func`** |
| `before` | **每轮都跑 `func`**，但 `time_done` 要等 `time + delay <= now` |
| `ease` | 在 `delay` 期间把 `ref_table[ref_value]` 从起值插值到 `ease_to`（lerp / elastic / quad） |
| `condition` | 每轮检查 `ref_table[ref_value] == stop_val` |

**移除条件是 `completed AND time_done` 两者同时成立**（`EventManager:update`）。
这解释了 `before` 的用途：副作用立刻发生，但事件占住队列（从而阻塞后续）直到 delay 走完。

### 2. `update()` 的处理顺序

- **五个独立队列**：`unlock` / `base` / `tutorial` / `achievement` / `other`。
  跨队列用 `for k, v in pairs(...)` 遍历——**Lua 的 `pairs` 顺序不确定**。
  但 `blocked` 是每队列的局部变量，队列之间互不阻塞，
  且**实测 gameplay 代码零处入非 `base` 队列**，所以这条不确定性够不着 RNG。
- **队列内严格 FIFO + 阻塞**：从 `i=1` 扫到末尾，遇到 blocking 且未完成的就置 `blocked`，
  其后所有 `blockable` 的事件本轮跳过。
- **固定步长**：`queue_dt = 1/60`，`update` 只在累积时间跨过 1/60 才处理一批，
  **不是每帧一次**。

### 3. 嵌套入队 → 队尾

`add_event` 默认 `self.queues[queue][#+1]`，即**追加到队尾**。
有个 `front` 参数可插队首，但**实测 gameplay 代码零处使用**。

### 4. `delay` 影响顺序吗 —— 判定性问题

**结论：对 RNG 消费顺序不影响。** 扫了全仓（排除 UI 层）：

| 项 | 数 |
|---|--:|
| `add_event` 块总数 | 270 |
| 其中消费 RNG 的 | 11 |
| 其中 `delay > 0` 或 `blockable = false` 的 | 6 |

那 6 处逐个核过：

| 位置 | 所在 | 第一个切片是否命中 |
|---|---|---|
| `card.lua:1312`、`:1472` | `Card:use_consumeable`（塔罗/幽灵） | 否 |
| `card.lua:1723` | `Card:open()`（开补充包） | 否 |
| `game.lua:1467` | `Game:splash_screen()` | 否 |
| `game.lua:1857` | `Game:main_menu()` | 否 |
| `common_events.lua:397` | **`draw_card()`** | **否——见下** |

`draw_card` 在切片里会跑，但它那句 RNG 被守卫着：

```lua
if G.GAME.modifiers.flipped_cards and to == G.hand then
    if pseudorandom(pseudoseed('flipped_card')) < 1/G.GAME.modifiers.flipped_cards then
```

`flipped_cards` 是**挑战模式的 modifier**，基础红牌组下为 nil，整个分支不进。

而 `calculate_joker` 里的 47 个 `add_event` 中只有 3 个消费 RNG，
全部是 `trigger='immediate'`、无显式 `delay`、`blocking`/`blockable` 取默认。

**所以：第一个切片零命中；即使做到有小丑的里程碑，那 3 处也是 immediate 无 delay。**

### 5. 依赖真实帧率吗

处理批次走固定步长 `queue_dt = 1/60`，不随帧率变；
`delay` 的比较基于 `G.TIMERS` 累积的 dt。
复刻件要跑一套虚拟时钟，但**它只影响动画节奏，不影响 RNG 顺序**。

### 本票要保证的，收窄成一句

> **保持 `base` 队列的 FIFO 与 blocking 语义即可。**
> `delay` 的具体数值、虚拟时钟的步长、动画时长，都不参与 RNG 顺序的确定。

这比原票设想的「复刻整个队列的调度语义」小了一大截。
配合 [LuaJIT RNG 复刻口径](02-LuaJIT-RNG-复刻口径.md) 的结论
（跨 key 打乱无影响，同 key 的调用次数与先后要逐次对齐），
「同 seed 同局」这条轴的完整条件就齐了：

> **同 key 的 RNG 调用序 = `base` 队列的 FIFO 序。把 delay 压成 0 不改变它。**

### 一条留给以后的

上面 6 处里的 5 处（消耗品、补充包）在**第二个里程碑**就会进范围。
到那时 `delay` 与 `blockable=false` 会真的影响 RNG 顺序，虚拟时钟必须如实复刻。
**别把「delay 可以压成 0」这条结论带过里程碑边界。**
