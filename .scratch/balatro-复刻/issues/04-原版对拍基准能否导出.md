# 原版对拍基准能否导出

Type: wayfinder:task
Status: resolved

## Question

「同 seed 同局」要可验收，就得有原版的 ground truth。拿得到吗？

要确认的：

1. 用户手上有没有可运行的 Balatro 正版（Steam / 移动端），版本是不是 1.0.1o。
   版本对不上，对拍基准就没有意义。
2. 能不能让它吐出结构化状态。候选路径：
   - LÖVE 允许挂 Lua，往 `pseudoseed` 里插日志，dump 每次抽取的 key 与返回值
   - 存档文件（`.jkr`）解析出局内状态
   - 最土的办法：手工录同一个 seed 的前 N 步，截图比对
3. 基准存哪、什么格式。它是**测试资产**不是研究产物，不该进 `参考/产物/`。

这是 HITL：跑原版、装 mod、录数据都要用户在场。

完成时记下：基准的路径、格式、覆盖到第几个 Ante、以及复现步骤。

没有这张票，[02](02-LuaJIT-RNG-复刻口径.md) 就算做出实现也无从证明它对。

## 重新定性（来自 [LuaJIT RNG 复刻口径](02-LuaJIT-RNG-复刻口径.md)）

这张票原本假定「ground truth 只能从实机导出」。**那个前提不成立了。**

RNG 调研从社区拿到了 12 条端到端真值（seed → Ante 1 Boss Blind），
来源是 balatrowiki、balatrohq、Blueprint fixture、balatro4j **四个互不相干的渠道**，
并已全部对拍通过。也就是说：**存在一个经过大规模验证的 Balatro 种子工具生态**，
可以在不跑原版的前提下提供真值。

本票因此改变性质——从「能不能拿到真值」变成「**社区真值的覆盖面够不够**」：

1. 现有 12 条只覆盖 **Ante 1 的 Boss Blind 选择**。
   商店出货、补充包内容、标签、小丑抽取、洗牌顺序都没覆盖。
2. 去查那几个工具（尤其 Blueprint 与 balatro4j）**还能吐出什么**。
   如果它们能模拟整局，那本票的答案就是「用它们当真值」，成本骤降。
3. 只有社区工具覆盖不到的部分，才回到「跑原版实机导出」这条贵路子。
   到那时再判断需不需要用户在场。

**优先级下调**：不再是「同 seed 轴的唯一命门」。
先做 1、2 两步（AFK，查工具能力即可），确认缺口有多大再说要不要 HITL。

## 优先级回调（来自 [第一个可玩里程碑的切片边界](07-第一个可玩里程碑的切片边界.md)）

## Answer

**社区工具拿不到洗牌真值，原因是结构性的。裁定走结构性验证，不动实机。**

### 调研结论：这条路走不通，且不是偶然

Blueprint、balatro4j、TheSoul、Immolate **全部源自同一个 seed-search 模型**：
商店队列、补充包、Boss、标签、优惠券。没有一个建模洗牌。

原因不是它们没做完，而是**洗牌对种子搜索没有价值**——
牌组组成会随局内购买、塔罗、幽灵牌变化，脱离实际牌组的洗牌顺序预测不了任何东西。

逐条核实：

| 来源 | 结论 |
|---|---|
| Blueprint fixture `7LB2WVPK.json` | 顶层只有 `analyzeState` / `options` / `immolateResults`，**无牌序** |
| balatro4j | 文档明确只覆盖 shop / pack / boss / tag / voucher，**未实现 pseudoshuffle** |
| TheSoul | 同一家族（`include/util.hpp` 的 RNG），定位是 seed analyzer |
| 游戏内置 `G.DEBUG` | 只是画包围盒的调试叠层（`engine/node.lua:94`），**不是状态导出器** |

### 裁定：结构性验证

洗牌链只用到两个**已被外部真值验证过**的原语：

- `pseudoseed` —— 由 16 条向量验过
- `math.random`（TW223）—— 由 4 条 TW223 向量验过

真正的新代码只有 `sort_id` 排序 + 4 行倒序 Fisher–Yates。
所以把未验证面缩到「这几行有没有抄错」，用**独立重推**来证：
测试里照 `misc_functions.lua:209` 另写一遍 `referenceShuffle`，两边逐位比对。

**刻意没用 mock 计调用次数。** ESM 下 `vi.spyOn` 拦不住已绑定的导入，
而且那种测试只验「调了几次」，验不了「怎么用返回值」——
下标 1-based 换算错、或把 `math.random(i)` 写成 `math.random(1, i)` 都能蒙混过关。

**这不等于证明了与原版一致**，只是把风险压到最小。写进里程碑的验收口径里，别当成对拍。

### 已落地

`复刻/Balatro/src/core/rng/pseudoshuffle.ts` + `pseudoshuffle.test.ts`，8 个测试。
全仓现在 **32 个测试全绿**。

实现时核实的两个调用点：

- `game.lua:2600` 开局 `deck:shuffle()` → key 取 `CardArea:shuffle` 的默认值 `'shuffle'`
- `state_events.lua:365` 每回合 `deck:shuffle('nr'..ante)` → Ante 1 即 `'nr1'`

与 `pseudorandom` 的关键差别已在测试里锚定：**只播种一次然后连抽 51 次**，
不是每次抽取都重新播种。

### 顺带验掉的一条传闻

搜索带出「Balatro 的 PRNG 有 NaN 缺陷，NaN 传播会让整副牌变成黑桃 10」。
本 session 用 50 万个随机种子跑 `pseudohash`：**NaN 0 次、Inf 0 次、恰好为 0 的 0 次**。

**但这只覆盖了 `pseudohash` 一段**，不能据此说整条链没问题。
传闻提到的是 Erratic Deck 的生成链路，那段本切片用不到。记为未证实，
真做 Erratic Deck 时要重新查。

### 实机导出这条路没有废，只是没走

若将来需要真正的对拍（比如第二个里程碑要验商店出货顺序，
或结构性验证被怀疑不够），实机路线仍然成立：
Steamodded 或直改 `.love`，挂钩子到 `pseudoshuffle` / `pseudoseed` dump 状态。
**一旦挂上钩子，后面所有里程碑都能用同一套装置取真值**——
这是它真正的价值，不该为了一个洗牌顺序单独开工。
前提是手上有可运行的 **1.0.1o** 正版，版本对不上基准就没意义。
