# 09 · 局内存档的形态与时机

Type: wayfinder:grilling
Status: resolved
Claimed by: save-format
Blocked by: 06, 07, 08

## Question

目的地要「中途退出重进能接着打」；工程计划说「局内状态第一天就要可序列化，后补得全部返工」。

要裁的：

- **存什么**：全量状态快照，还是种子加操作日志重放（后者天然验证确定性，但规则一改旧档全废）；
- **什么时候存**：每次落子、弃置之后，退出时，还是都存；结算演出播到一半退出，读回来是哪个状态；
- **格式与位置**：JSON 还是二进制，放 `Application.persistentDataPath` 下哪个文件，要不要版本号与校验；
- **分工**：序列化在纯 C# 规则核心里做，Unity 侧只管读写文件。

block-client 的 `MergeIngameSave`、`IngameBoardCodec`（按不可信输入解码）可以参考，但它的存档要经服务端，本作单机。

[切片边界](05-首个可玩盲注的切片边界.md) 已定的前提：要存的状态清单；关窗、强退也要能续；结局一确定就删档；主界面凭有没有档显示「继续」。见其 Answer。

[规则核心的工程形态](10-规则核心的工程形态与跑局测试.md) 已定的前提（见其 Answer「对其它票」）：
- **快照序列化要规范**：同一状态必须输出逐字节相同的文本，做法是成员次序固定、一律用 InvariantCulture、不依赖哈希容器的遍历序。跑局测试比终局状态时直接比这份文本；
- 规则核心目前零外部引用。序列化如果要用 Newtonsoft 这类库，asmdef 的 `precompiledReferences` 和镜像库的 `PackageReference` 要在同一笔改动里一起加，版本对齐 Unity 包里的那份；
- 跑局测试会隔几步存读一次再接着打，和不中断的那一局逐行比对。存档漏存了状态，续打就会分叉，测试变红。

[PC 操作](12-PC上的落子与旋转操作.md) 加了两条：
- 结算演出期间 Esc 和关窗都不锁，所以一步的存档要在演出开始前写完。
- 转动不算「步」，但续局要保留朝向，所以转动也要触发存档（可以合并写）。

[结算管线](07-结算管线与事件流.md) 已定的前提（见其 Answer「对下游票」）：
- 一步在规则核心里同步算完，返回 `StepResult`（有序事件）。存档点在它返回之后、表现层开演之前；读档后直接显示这一步之后的状态，不重放事件。
- 底分、倍率、独立倍率三个累加器是步内临时量，不进存档。要存的计分状态只有累计分（`long`）、连击、类型等级（本图恒为 1）和基因槽上的效果状态（本图没有）。累计分建议写成十进制文本，以后换大数类型时旧档还能读。
- 计分全是整数，存档里没有浮点。
- 效果注册表和类型表一样是开局时传进来的规则配置，不进存档。

## Answer

**据此裁定：**

- **存全量快照，不存操作日志。** 快照 = 06 §6 两行「全部」减去 §7 的派生量，读回就能接着打，不重放任何东西。规则改了，旧档照读、按新规则接着打。
- **存档点都在稳定态**：开新局发完第一组写一次；每一步被接受之后（`StepResult` 返回、交给表现层之前）同步写。转动只置脏，到 0.5 秒没再转、下一次写档、离开战斗界面、窗口失焦、退出这几个时刻合并写。被拒的步不写。
- **结局一定，先照常写一次终局快照，再删档**（先删 `.bak`，再删正档）。读到终局快照，一律当无档。
- **格式是规范 JSON 文本**：UTF-8 无 BOM、LF、两格缩进，成员次序由写出代码固定。64 位的量写成字符串（累计分、目标分写十进制，`s0`、`s1` 写 16 位十六进制），枚举写名字，格层写成 8 行 8 列。
  同一状态写出的字节逐个相同，它就是 10 号票跑局轨迹里的 `state`。
- **不引 Newtonsoft，在规则核心里自写一个只认整数的 JSON 子集读写器。** GameRules 保持零外部引用，asmdef 和镜像库都不用加引用。
- **版本号有两个**：`schema` 整数，加上 08 的 RNG 方案号。首次对外发包之前 `schema` 恒为 1，形状随便改，旧档作废；发包之后，改形状就升版本、写迁移、留样档。
  读档严格：多一个或少一个成员都算坏档，缺省值只从迁移里来。
- **不加校验和**。写坏靠原子替换防，坏档靠严格解析加完整的稳定态校验挡；这个校验函数就是单测在每步之后断言的那一个。
- **位置**：`Application.persistentDataPath/save/run.json`，Windows 上是 `%USERPROFILE%\AppData\LocalLow\block-rougelike\3B\save\`。
  旁边还有三个文件：`run.json.tmp`（写入中）、`run.json.bak`（上一份）、`run.json.bad`（读不了的那份，留着报 bug）。
- **分工**：规则核心出「状态 ↔ 文本」两个纯函数和校验，不碰文件，不抛异常。GameLogic 出两样：文件层（原子写、回退、挪走坏档）和时机（脏标记、防抖、失焦与退出）。
  文件层不引 UnityEngine，像 `TextKeys.cs` 一样链接进 dotnet 测试。

没有一项改变目的地或产品形状，全部按授权自裁。依据写在各节，要推翻哪条只改那一节。
玩家看得见的只有一条：退出重进不能撤回已经落下的一步。已补进规则 §8.1。

### 1 存什么：全量快照

| | 快照 | 种子 + 操作日志重放 |
|---|---|---|
| 规则改了 | 照读，按新规则接着打 | 重放出另一局，或者中途某一步不合法、整档报废 |
| 读档代价 | 解析几 KB 文本 | 从开局重跑每一步，越打越长 |
| 验确定性 | 不验，由 17 号票的 D 路验 | 天然验 |
| 撤回一步 | 做不到，快照里只有当前态 | 删掉日志最后一行就是撤回 |

- **选快照**。GameRules 进了热更清单（10 第 3 节），规则是改得最勤的代码。重放档每次热更后都可能失效，而且是悄悄失效：重放能走完，只是走成了另一局。
- **确定性另有人验**。17 号票的 D 路每隔几步做一次「快照 → 文本 → 读回 → 接着打」，再和不中断的那一局逐行比，漏存的状态会让它变红。重放档能给的好处，跑局测试已经给了。
- **随机的结果本身就是状态**（08 第 5 节）：剩余抽牌顺序直接存，读档不靠重放 RNG。
- Balatro 1.0.1o 也存快照：`save_run()` 把 `G.GAME`、各牌区、盲注、牌背整表存下来，带 `VERSION`（`functions/misc_functions.lua:1472-1503`）。
- **不另附操作日志**。没有消费方，复现 bug 用 `Sim` 的轨迹。以后要加，就是快照里多一个可选成员，不影响本票。

**v1 快照的内容**。成员按下面的次序写出。名字是建议，落地票可以改，但一经定下就是 schema 的一部分。

```
{
  "format": "3b.run",
  "schema": 1,
  "seed": "TESTSEED",
  "rng": { "scheme": 1, "streams": [ { "key": "shuffle@1.1", "s0": "<16 位小写十六进制>", "s1": "…" } ] },
  "nextInstanceId": 29,
  "library": [
    { "id": 1, "kind": "I", "points": 1, "enhancement": "None", "edition": "None" },
    …                                                 一块一行，按 id 升序
  ],
  "typeLevels": { "<类型名>": 1, … },                  11 项，按类型枚举序
  "genes": [],
  "blind": {
    "spec": { "segment": 1, "layer": 1, "target": "350", "discards": 3, "groupSize": 3 },
    "outcome": "InProgress",
    "failReason": "None",
    "step": 0,
    "group": 1,
    "score": "0",
    "combo": 0,
    "discardsLeft": 3,
    "draw": [ … ],                                     下标 0 先抽
    "tray": [ { "id": 3, "rot": 1 }, null, … ],       定长 = groupSize，空槽写 null
    "owner": [
      [0,0,0,0,0,0,0,0],                               8 行，一行盘面占一行文本，row 0 在上
      …
    ],
    "dead": [],                                        死格的格号 row*8+col，升序
    "discarded": [ … ],                                按进堆先后
    "departed": [ … ],                                 同上
    "tempBlocks": []                                   形状同 library
  }
}
```

- **不进快照的**：
  - 派生量：占用掩码、盘上集合、一块还剩几格（06 §7）；
  - 步内临时量：三区累加器（07）；
  - 规则配置：类型表、效果注册表、默认方块库清单（07 第 5 节）。读档和开新局一样，要传入同一份配置：`Read(文本, 配置)`；
  - 表现层的一切：拖着哪块、悬停、演出进度、预览；
  - `Sim` 策略自己的随机流（08）；
  - 语言设置，它在 PlayerPrefs 里（14）。
- **死格写格号列表，不写掩码**。按地图「已知的坑」，掩码的位是 `row*8 + (7-col)`，数组下标是 `row*8 + col`。把位布局写进文件，等于把这个坑带进存档格式。格号列表和 `owner` 用同一套下标。
- **`blind` 在本图恒非空**。两个盲注之间（商店）没有盲注，那是阶段 5 的形状，到时候升 schema。
- 金钱、利息不预留（05）。基因槽上的效果状态本图没有，`genes` 恒为空列表。

### 2 什么时候存

| 时机 | 做什么 |
|---|---|
| 开新局（主界面「开始游戏」） | 先删掉正档、`.bak`、`.tmp`，再建局、开盲注、发第一组，然后写一次。先删，是为了让 `.bak` 永远只属于当前这一局 |
| 一步被接受（落子、弃置） | `StepResult` 返回之后、把事件交给表现层之前，同步写。被拒的步没改状态，不写 |
| 这一步定了结局 | 照常把终局快照写一次，然后先删 `.bak`、再删正档 |
| 转动（`SetRotation`） | 只置脏，不立即写。下面任一时刻到来时合并写：0.5 秒内没有新的转动（占位）；下一次写档（顺带写进去）；离开战斗界面；窗口失焦；`Application.quitting` |
| 返回主界面（按钮或 Esc） | 只处理脏标记；步的状态早已写好 |

- **演出播到一半退出**：存档已经是这一步之后的状态，读回来直接显示它，不重放事件（07、12）。丢掉的只是动画。
- **拖拽中退出**：拖拽不是状态。块回到托盘原来的槽，朝向是最后一次转到的那一档（失焦、退出都会把脏标记写掉）。
- **强退、崩溃**：最多丢掉最后 0.5 秒内的转动。步不会丢，因为一步的档在开演之前就写完了。用任务管理器结束进程时，游戏窗口通常会先失焦，连转动也保得住。
- **为什么步要同步写**：写一份 3～4 KB 的文本再改个名，是 1 毫秒的量级，回合制游戏在落子那一帧承受得起。
  改成异步写，就要处理「上一份还没写完又来了一步」和「退出时要等它写完」，换来的只是这 1 毫秒。真机上量出来超过 4 毫秒，再考虑挪到后台线程（接线票要量）。
- **为什么转动要防抖**：滚轮一秒能转十几下，每下写一次盘没有必要。05 要的是续局后朝向不变，0.5 秒的窗口加上失焦、退出两个写入点，已经够了。
- **为什么结局要先写再删**：直接删的话，删到一半崩溃，留下的会是这一步之前的档，重进就回到了已经输掉的那一步之前。
  先写终局快照，再按「先 `.bak` 后正档」的次序删，中途哪里断掉，留下的都是终局快照，读档时当无档处理。
- **对照 Balatro 1.0.1o**：它也在稳定态构造快照，比如出完一手、补完牌、回到选牌时（`update_selecting_hand`，`game.lua:3421-3428`）。
  但落盘是节流的：默认 30 秒一次，或者换场景、暂停时才真写（`game.lua:3020-3037`，`globals.lua:41`）。写由后台线程直接覆盖，不经临时文件改名（`engine/string_packer.lua:118-120`）。
  所以它崩溃时可能退回到 30 秒前。Balatro 一个盲注只出几手，每手有长演出，退回一两手玩家重打就是了。
  3B 一个盲注几十步，步步都是决策，退回一步就等于「能靠强退撤回」，所以每步都写。

### 3 格式：规范 JSON

- **用 JSON 文本，不用二进制**：
  - 存档只有几 KB；
  - 文本能直接读，玩家报 bug 时附上存档就能看；
  - 跑局轨迹要把终局快照原样打进去逐行比（10 第 7 节），二进制只能比哈希；
  - 单机买断，改档是玩家自己的事，用不着混淆。
- **规范形**：同一状态写出的字节逐个相同（10 的要求）。
  - UTF-8 无 BOM，全文只有 ASCII。种子字母表、键、枚举名本来都是 ASCII；写出时万一遇到非 ASCII 字符，一律转成 `\uXXXX`。行尾 LF，文末一个换行。
  - 两格缩进。排版由写出代码逐处指定：标量成员一个一行，`library` 一块一行，`owner` 一行盘面一行，短的整数列表写在一行。不靠通用的自动换行规则。
  - 成员次序就是写出代码的次序，不排序。
  - 整数一律按 InvariantCulture 写十进制。**32 位以内写成 JSON 数，64 位写成字符串**：累计分、目标分写十进制，`s0`、`s1` 写 16 位小写十六进制（08）。这样任何 JSON 工具打开都不会丢精度。
  - 枚举写名字（`"kind": "T"`），不写数字。
- **枚举写名字的代价**：改名就是改形状，要升 schema、写迁移（首发前随便改，见第 4 节）。换来的是档能读懂。
  写数字防的是改序，而 06 已经规定枚举只追加、不改序，这个风险本来就不存在。读的时候按名字精确匹配，不认数字，不忽略大小写。不调 `Enum.Parse`，它会把 `"3"` 也当成合法值。
- **自写读写器，不引 Newtonsoft**：
  - 要的只有六样：整数、字符串、布尔、null、数组、对象。写出端约 150 行，读入端连同各种上限约 300 行。
  - Newtonsoft 要写出规范形，得逐个成员标 `Order`，还得钉死换行符：它缩进时取 `TextWriter.NewLine`，默认随平台，Windows 上是 CRLF。解析不可信输入时，还要另外设深度上限。
  - Unity 包里的 Newtonsoft（`com.unity.nuget.newtonsoft-json` 3.2.2，同步自 13.0.2）有普通和 AOT 两份 dll，IL2CPP 用的是后者。它和镜像库从 NuGet 拿的 13.0.2 不是同一个二进制，「两端编同一份代码」在这里打了折扣。
  - 引了它，就破了规则核心的零外部引用，10 第 1 节还要求两端同批加引用。自写的话这些全免。
  - `UnityEngine.JsonUtility` 不能用，规则核心不引引擎；`System.Text.Json` 不在 netstandard2.1 里。
- **读入端按不可信输入写**，口径照 block-client 的 `IngameBoardCodec`，但更严：
  - 任何输入都不抛异常，返回错误码，加上第一处出错的成员路径（比如 `blind.tray[1].rot`）；
  - 上限：文本 1 MiB，嵌套 16 层；
  - 数字只认整数，带小数点、指数或越界都是错；
  - 开头如果有 UTF-8 BOM，先跳过（防外部工具存出 BOM）；写出端永远不写 BOM。
- **形状严格**：对象里多一个成员、少一个成员，或者次序不对，都算坏档。
  - block-client 的档靠「旧档没有这个字段，就读成缺省值」过日子，结果是注释里一条接一条的坑：退役的键 `combo` 会被当成新值读进来，`ulong` 存出来恒为 0（`MergeIngameSave.cs:68-72, 97-102, 135-137`）。
  - 3B 把缺省值都收进迁移里，一个版本只有一种形状。
  - 次序也查，是因为「快照 → 读回 → 再快照」要逐字节相同（10 第 7 节 D 路），读入端认可的只能是写出端会写的东西。

### 4 版本与迁移

- **`format` 固定是 `"3b.run"`**，用来认出错拿来的文件；不对就是坏档。
- **`schema` 是存档形状的版本号**：
  - **首次对外发包之前恒为 1**。开发期形状随便改，旧档读不了就挪成 `.bad`，开新局即可，不写迁移。
  - **对外发包之后**，任何形状改动都升 1：加成员、删成员、成员改名、枚举改名、某个值的含义变了。每升一次写一个「旧 → 新」的迁移。
    迁移是纯函数，作用在解析后的 JSON 树上，一级一级串起来，最后交给当前版本的读入端。加成员也要升版本，缺省值在迁移里填。
  - 每个发过包的版本，在 `Tests/` 里留一份样档。单测读样档、迁到当前版本、过校验。
  - `schema` 比当前的大（新版本存的档、降级运行）：读不了，挪成 `.bad`，不删。
- **RNG 方案号（08）放在 `rng.scheme`**，本图为 1。换发生器或改键语法，当作一次 schema 升级处理：迁移里用新方案、从种子文本重新派生全部流。
  已经落成状态的随机结果（抽牌顺序）不受影响，变的只是还没摇的部分。08 留给本票的「旧档怎么处理」就是这一条。
- **规则改了、形状没变**（热更改了数值，或改了某条判定）：不升版本，旧档照读，按新规则接着打。这正是选快照的理由。
- **档里不记出包版本号**：规则核心拿不到 `Application.version`；而且记了它，同一状态在不同的包里就会写出不同的字节。报 bug 要知道版本，看 `Player.log`。

### 5 校验：读档用的就是每步之后那组断言

- 解析成功不等于能用。读入端解析完，调 `RunState.Validate()`：返回第一条不成立的约束，全部成立返回 null。它查这些：
  - **盘面**：06 §2 的两条不变式。占用是读档时从格层重建的，第一条自然成立；要查的是 `dead` 里的格必须是空格。
  - **区守恒**（06 §3）：方块库和临时块里每个 id，恰好在抽牌堆、待放置区、盘上、弃置堆、消尽堆其中之一；不在库里的 id 不许出现。
  - **id**：都 > 0、互不相同，`nextInstanceId` 大于所有 id；每块在盘上最多 4 格。
  - **随机流**：种子文本合法（08 第 4 节）；流的键合法、不重复、按 ordinal 升序；`(s0, s1)` 不全为 0，xorshift 的全零态出不来随机数。
  - **取值**：枚举值都有定义；`rot` 在 0..3；`tray` 长度等于 `groupSize`；各计数非负，`discardsLeft` 不超过规格；类型等级 ≥ 1；`genes` 为空（本图没有基因 id）。
  - **稳定态**：进行中的盲注，不能「待放置区全空而抽牌堆非空」（那时本该已经发了组），也不能已经满足判负条件（那一步本该判负）。
- **这个函数就是 19、20 号票单测每步之后断言的那一个**，写进规则核心的公开 API，不只放在测试里。
  同一份代码同时管住「游戏里走不出坏状态」和「坏档读不进来」，两边不会判岔。
- **不查「盘上一块的格是不是它的形状」**：没有代码依赖这一点，把档改出怪形状，只影响改档的玩家自己。
- **不加校验和**：
  - 校验和防的是写坏，写坏已由原子替换防住（第 6 节）；断电这类极端情况写出的乱码，过不了严格解析和上面的校验。
  - 防篡改用不着：单机游戏，改出来的档只要过得了校验，就是一个合法局面。
  - 加了还得规定「对哪些字节算」，又多一条规范形要守。

### 6 文件与位置

- **目录**：`Application.persistentDataPath + "/save/"`。按现在的 `ProjectSettings`（`companyName: block-rougelike`、`productName: 3B`），Windows 上是 `%USERPROFILE%\AppData\LocalLow\block-rougelike\3B\save\`。
  正式定名时改 `ProjectSettings` 会换目录，开发期的档就读不到了。可以接受，首发前的档本来就随时作废。
- **四个文件**：

| 文件 | 是什么 |
|---|---|
| `run.json` | 当前这一局 |
| `run.json.tmp` | 写入中；读档时见到就删 |
| `run.json.bak` | 上一份 `run.json`，替换时顺手留下 |
| `run.json.bad` | 最近一份读不了的档，留着报 bug，只保留一份 |

- **写**：先写 `run.json.tmp`；`run.json` 存在就 `File.Replace(tmp, run.json, run.json.bak)`，否则 `File.Move(tmp, run.json)`。
  - 不调 `Flush(true)`。进程被杀时，数据已经在系统缓存里，不会丢；只有断电才可能丢，那时还有 `.bak` 兜底。
  - 替换失败（比如杀毒软件占着文件）就重试一次；再失败就记日志、照常玩，等下一个存档点再写。旧档还在。
- **读**（主界面探测「继续」时）：
  1. 删掉残留的 `.tmp`。
  2. 读 `run.json`。读不了（解析错、校验错、`schema` 不认）就挪成 `.bad`，改读 `.bak`；`.bak` 也读不了，同样挪走，当无档。
  3. 读到的局已经结束：当无档，删掉正档和 `.bak`。不挪成 `.bad`，它不是坏档。
  4. `run.json` 不存在：当无档，**不回退到 `.bak`**。正常流程里只有两处会删正档：开新局和结局删档，两处都先删了 `.bak`。正档没了、`.bak` 还在，只可能是人为删的。
- **回退到 `.bak` 等于退回一步**。它只在正档坏掉时发生，属于事故恢复，不是能拿来用的撤回手段。
  想靠手动改坏 `run.json` 来撤回一步的玩家，复制存档文件一样能做到。单机不防这个。
- **主界面显示「继续」的条件**：探测到一份能读、校验通过、盲注还在进行中的档。探测时就整份读完、校验完，点「继续」直接用探测得到的状态，不再读第二次。
- **一份档就是一局**。将来的局外存档（解锁、统计，阶段 5）另起文件，比如 `profile.json`，和局内档分开写、互不覆盖。
  block-client 也是局内档和元层档分键存（`MergeIngameSave.cs:4-8`）。

### 7 分工

| 层 | 东西 | 依赖 |
|---|---|---|
| 规则核心 `GameRules` | `RunSnapshot.Write(RunState) → string`；`RunSnapshot.Read(string, RuleConfig)`，返回状态、错误码和出错路径；迁移链（本图为空）；`RunState.Validate()`；JSON 子集读写器 | 零外部引用；不碰文件和时钟；读入不抛异常 |
| GameLogic 文件层 `RunSaveFile` | 第 6 节的四个文件：原子写、读与回退、挪走坏档、删档 | 只用 `System.IO`，目录由构造参数传入，不引 UnityEngine。像 `TextKeys.cs` 一样用 Link 编进 `DotNet/Tests/`，在临时目录里测 |
| GameLogic 时机 `RunSaveService` | 第 2 节那张表：步后写、结局删、转动置脏与防抖、失焦与退出时写；主界面探测 | Unity：`Application.persistentDataPath`、`Application.quitting`、`Application.focusChanged` |

- **战斗流程里的次序**：`var r = rules.Place(…)` → 被接受就 `save.CommitStep(run, r)`（写档；定了结局就写终局再删）→ `presentation.Play(r.Events)`。
  存档排在表现层之前，07、12 的要求就落在这一行。
- 规则核心不知道有文件，也不知道什么时候存。GameLogic 不知道快照里有什么，只搬字符串。
- 迁移和校验放进规则核心，因为它们和状态的形状是一回事：要和 `RunState` 一起改，一起被 dotnet 单测覆盖。

### 为什么不是别的做法

| 做法 | 不选的理由 |
|---|---|
| 种子 + 操作日志重放 | 第 1 节：规则一改，旧档会悄悄变成另一局；GameRules 在热更清单里，这会经常发生 |
| 快照和日志都存 | 日志没有消费方；复现 bug 用 `Sim` 的轨迹 |
| 只在退出时存 | 05 要求强退、崩溃也能续；Windows 上退出事件不一定送得到 |
| Balatro 式节流落盘（30 秒一次） | 第 2 节：步步都是决策，退回一步就成了「强退撤回」 |
| 每次转动立即写 | 滚轮一秒十几下，没必要每下写盘；防抖加上失焦、退出两个写入点，已经保得住朝向 |
| 二进制或压缩 | 跑局轨迹要逐行比快照；档只有几 KB |
| Newtonsoft | 第 3 节：规范形要逐成员标次序、钉死换行；破了规则核心的零外部引用；IL2CPP 下和镜像库用的不是同一个 dll |
| 缺字段读成缺省值（block-client 的做法） | 第 3 节：缺省值散在各处注释里，退役的键会被误读；收进迁移，一个版本只有一种形状 |
| 加校验和 | 第 5 节：写坏由原子替换防，坏档由校验挡，篡改不用防 |
| 存进 PlayerPrefs | Windows 上存在注册表里，不能原子替换，玩家也导不出来报 bug |
| 结局直接删档 | 第 2 节：删到一半崩溃，会留下这一步之前的档，重进就回到了输掉之前 |
