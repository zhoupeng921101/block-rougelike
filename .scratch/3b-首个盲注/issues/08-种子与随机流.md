# 08 · 种子与随机流的口径

Type: wayfinder:grilling
Status: resolved
Claimed by: rng-streams
Blocked by: 02

## Question

工程计划已裁「统一用种子，按用途分流（发块、商店、效果各一条），做法同 Balatro 的 pseudoseed」。剩下要定的：

- **发生器**：直接用 block-client 的 `XorShift128PlusRng`（已为 Mono、IL2CPP、.NET 逐位一致做过），还是另选；
- **分流**：子流种子怎么从主种子加用途键派生；流内要不要再按盲注、段细分（Balatro 是 `pseudoseed(key..ante)`）；
- **洗牌**：Fisher–Yates 的方向与取整口径钉死；
- **主种子的形态**：数字还是 Balatro 式 8 字符串，将来开种子局要给玩家看；
- **RNG 状态怎么进存档**。

本图的消费点只有「盲注开始洗方块库」，但口径要给商店、效果留好。

## Answer

**据此裁定：**

- **发生器**：原样用 block-client 的 `XorShift128PlusRng`。
- **分流**：每个键一条独立流，子流种子 = FNV-1a 64(`种子文本/键`)，第一次用到时派生。
- **取随机**：规则核心只取整数随机，不碰 `NextDouble`。
- **洗牌**：先按实例 id 升序排，再做从后往前的 Fisher–Yates。
- **主种子**：8 位种子文本。
- **存档**：存种子文本，加上每条已开流的 `(s0, s1)`。

本图只有一个键：`shuffle@段.层`。原型与测试向量见 [research/08-随机流向量](../research/08-随机流向量.md)。

### 1 发生器：原样用 `XorShift128PlusRng`

- 02 号票已经裁定原样拷 `PortableRng.cs`。这个发生器全程用 ulong 位运算，能导出状态，也能从状态重建（`PortableRng.cs:42-51`），续玩和分流都能直接用。
- 换成 PCG、xoshiro256** 也得不到什么。xorshift128+ 已知的短板是最低位的线性复杂度低，只在 BigCrush 的线性检验里会暴露，玩家感知不到。
- 实测：把它链进 net8.0，两个进程各跑一次，输出逐行一致。

### 2 分流：一个键一条流，键是用途名，需要时带 `@段.层`

- **派生方式**：子流种子 = `FNV1a64(种子文本 + "/" + 键)`，按 char 逐个异或。只允许 ASCII，超出范围就抛异常。结果转成 long，交给 `XorShift128PlusRng(long)`，构造时还会再过两次 SplitMix64 扩散。种子字母表和键语法里都没有 `/`，所以拼接不会有歧义。
- **不用 `string.GetHashCode`**：CoreCLR 每个进程算出的值都不同（03 号票；这次两个进程分别给出 148622727 和 181219200）。
- **也不照搬 Balatro 的浮点哈希链**（`misc_functions.lua:282-316`）。它用 π 做乘除，再用 `%.13f` 格式化截断，复刻 02 号票为了逐位对上要用 BigInt 展开。只借它的思路：一个用途一条流，键带底注。
- **登记表**：`RngStreams.Get(key)` 第一次调用时派生，之后一直返回同一个实例。键全部定义在一个常量类里，调用点不拼字符串。键语法是 `[a-z][a-z0-9_.]*`，后面可以跟 `@段.层`；段和层从 1 数，用 InvariantCulture 格式化。
- **怎么细分**：
  - 如果一个用途的消费次数会随玩家操作变，而后面的结果不应该跟着变，键就带 `@段.层`。
  - 同一个效果的连续判定不细分，一个效果定义对应一个键。
- **本图的键 `shuffle@段.层`**：
  - **按层分，不按段分。** Balatro 用的是 `'nr'..ante`，一个底注里三次洗牌共用一个键。3B 的普通节点可以跳过（规则 §2.3）：如果按段分，跳过前一层就会让后一层的洗牌变样；按层分，就不受影响。
  - **键里不带节点。** 同一层可选的 1～3 个节点洗的是同一个库，结果相同。这样玩家没法靠换节点去刷洗牌。
- **以后的默认做法**（不在本图，引入时由对应的票确认）：
  - 商店用 `shop@段.层`，补给包用 `pack@段.层`；
  - 地图生成、首领抽取按段分；
  - 基因、改造、强化的概率判定一个效果一个键，比如 `gene.<id>`，不细分。这和 Balatro 的 `'lucky_mult'`、`'wheel_of_fortune'` 一样，加一个基因不会改变别的基因的判定结果。

### 3 取随机与洗牌：全整数，没有取整这回事

- **规则核心只调 `IRandomSource.Next(min, max)`**。它是无偏的拒绝采样，全程整数运算（`PortableRng.cs:90-99`）。规则核心不调 `NextDouble`，所以根本没有「取整口径」要定。
  - **这和 block-client `OfferRandom` 的取法不同。** 它用 `(int)(NextDouble()*n)`，是为了逐次对拍研究实现（`OfferRandom.cs:6-9`），3B 没有要对拍的外部实现。
  - **浮点取法也不是不行**：x64 的 SSE2 上同样确定。但在 x87 扩展精度下，有极少数值会差一，比如 n=6 时乘积离 5 刚好半个 ulp。走整数路径就不用论证这些。
  - **拒绝采样的消费次数不固定**，但重抽的概率小于 2^-33，而且由状态决定，不影响确定性。存档存的是状态，不是次数，也不依赖它。
- **落地时放进一个静态类的四个助手**：
  - `Index(n)` = `Next(0, n)`；
  - `Chance(num, den)` = `Next(0, den) < num`。「1/4 概率」写成 `Chance(1, 4)`，不做浮点比较；
  - `Weighted(整数权重)` = 先 `Next(0, 总权重)`，再逐项累加整数比较；
  - `Shuffle`。
- **洗牌**：Fisher–Yates，从后往前。`for i = n-1 .. 1: j = Next(0, i+1); swap(i, j)`，消费 n-1 次。方向和 Balatro 的 `pseudoshuffle`（`misc_functions.lua:216-219`）、block-client 的 `OfferRandom.Shuffle` 一致。
- **洗之前先按方块实例 id 升序排**。Balatro 洗前也按 `sort_id` 排（`:212-214`）。不排的话，洗出来的结果就取决于上一个盲注结束时各块在哪个集合、按什么顺序回库，而这些是打法决定的。
- **洗完的列表就是抽牌顺序**，下标 0 先抽。盲注内抽牌不再消耗随机。

### 4 主种子：8 位种子文本

- **字母表 32 个字符**：`23456789ABCDEFGHJKLMNPQRSTUVWXYZ`，去掉了容易认混的 0、1、I、O。8 位是 40 bit，约 1.1 万亿个种子。Balatro 也是 8 位（`misc_functions.lua:273-280`），用 34 个字符，只去掉 0 和 O。
- **种子文本就是正本。** 派生只认文本，不另存一个数字形式，玩家看到的、抄走的、再输回来的是同一个东西。
  - 输入时先 `Trim`，再 `ToUpperInvariant`。不能用随区域设置变化的 `ToUpper`，土耳其语区会把 i 变成 İ。
  - 1～8 位、每个字符都在字母表里，才算合法。
- **新开局的种子在规则核心外面生成。** Unity 侧取 40 bit 熵（`Guid`、时钟都可以），规则核心提供 `SeedText.FromEntropy(ulong)`，每 5 bit 映射成一个字符。规则核心自己不碰任何非确定来源。
- **本图不做种子局入口，也不显示种子。** 复现 bug 要用的调试入口，归 05 号票的「进入方式」。

### 5 RNG 怎么进存档

- **存什么**：种子文本，加上每条已开流的 `(键, s0, s1)`。
  - 按键的 ordinal 序输出；s0、s1 写成 16 位小写十六进制，避开 JSON 数字超过 2^53 丢精度的问题。
  - 读档时用 `XorShift128PlusRng(s0, s1)` 重建。存档里没有的键，第一次用到时照常派生。所以不管存档发生在流打开之前还是之后，读回来都能接上。
  - 实测：导出状态、重建实例，再接着取 5 个数，两边逐位一致。
- **带一个 RNG 方案版本号**：v1 = xorshift128+ / FNV-1a 64 / 本票的键语法。换发生器或改键语法就升版本，旧档怎么处理由 09 号票定。
- **随机的结果也进存档。** 洗出来的剩余抽牌顺序本身就是状态，读档时不靠重放 RNG 来重建。这条对 09 号票的两条路都成立：选快照，就照上面存；选重放，只存种子文本。
- **推论**：退出再进不会重摇。

### 对其它票的约束

- **06 数据模型**：方块实例 id 是整数，本局唯一，只增不复用，要进存档。洗牌按它排序。
- **07 结算管线**：
  - 规则核心要随机，只能经 `RngStreams` 取。
  - 试算要在 `RngStreams` 的副本上跑，跑完丢弃，否则拖动预览会推进随机流。
  - 预览不显示任何随机判定的结果，不然玩家来回拖就能偷看下一次判定。Balatro 的预览也只显示牌型和底分、倍率。
- **10 跑局测试**：
  - 把 research/08 那张向量表写成单测常量。常量是另一个进程算出来的，所以这组断言本身就是一项跨进程比对。
  - 落子策略如果要随机，自己开一个 `RngStreams` 实例，键用 `sim.` 前缀，不进对局状态。
  - 比「逐项一致」时，最终状态里要包含所有流的 `(s0, s1)`。
- **表现层**：演出、粒子、音效要随机，用 `UnityEngine.Random`，绝不取规则核心的流。否则改一个动画就改了这一局。
- **Mono 侧**：RNG 全程整数，也没有靠字典遍历序定先后，所以按论证应当跨运行时一致，但只在 CoreCLR 上实测过。地图「Unity 侧的确定性复核」里剩下的风险，在计分的数值类型（07）和遍历序。

**规则文档不用回写。** §2.1「整库洗回、洗匀」本来就是规则，本票只定它的实现口径。工程计划里「做法同 Balatro 的 pseudoseed」一句，指的是分流的思路，和本票不冲突。
