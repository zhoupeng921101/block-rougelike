# 07 · 一步落子的结算管线与事件流

Type: wayfinder:grilling
Status: resolved
Claimed by: settle-pipeline
Blocked by: 06

## Question

一次放置从落子到分数入账，规则核心按什么顺序做事、往外吐什么？

要裁的：

- **逐格顺序**（审计 §2.2 遗留；规则 §3.1 写着「格与格之间的先后待定」）：被消的格按什么序结算——行优先扫描、按块、按消除线？
  行列交叉格只算一次，它归哪条线。将来的重触发作用在哪些格。
- **管线形态**：规则核心同步算完、返回一份有序事件列表（block-client `BoardPlayFlow` 的「一步推进结果」做法），
  还是像 Balatro 那样的事件队列？基因、强化的钩子挂在哪些点（落子前、定类型后、每格、每基因、结算后）。
- **分数的数值类型**：三乘区相乘，独立倍率会有 ×1.5 这类小数。分数用 long、double 还是定点，取整在哪一步；跨 Mono 与 .NET 要逐位一致。
- **试算**：拖动预览要的「这一手会消什么、底分、倍率」，能不能用同一条管线无副作用跑一遍。
- **胜负判定的时机**：规则 §2.4「达标立即结束」是整次结算完之后判，还是逐格中途就判。

[切片边界](05-首个可玩盲注的切片边界.md) 已定的前提：管线段落、连击的更新时机、先判胜再判负、预览的口径（只到定类型、不碰随机流），见其 Answer「对下游票」。
[种子与随机流](08-种子与随机流.md) 已定的前提：随机只经 `RngStreams` 取，而且全是整数（概率写成 `Chance(num, den)`）；试算在流的副本上跑，跑完丢弃。见其 Answer「对其它票的约束」。

[规则核心的工程形态](10-规则核心的工程形态与跑局测试.md) 已定的前提（见其 Answer「对其它票」）：
- 钩子是规则核心的公开入口。dotnet 单测的测试替身和阶段 5 的真效果都从同一个入口注册，不开 `InternalsVisibleTo`；
- 事件里只放整数、枚举、布尔、字符串和有序列表，不放 `Dictionary` / `HashSet`。跑局测试按成员名反射打印事件，逐行比对；
- 分数如果用浮点，跑局测试按位模式比对。规则核心只在 CoreCLR 上实测过，Mono 侧的复核还在迷雾里。

参考 Balatro 1.0.1o 的 [出牌结算管线.md](../../../参考/结论/Balatro_1.0.1o/出牌结算管线.md)。裁完回写规则 §3.1。

## Answer

**据此裁定：**

- **逐格按线走**：先走行，从上到下，行内从左到右；再走列，从左到右，列内从上到下。行列交叉的格归行，走到列上时跳过。
  结算顺序、演出顺序、「首个被消的格」都是这一个顺序。
- **重触发以格为单位**：走到一格时先问清它要触发几次，然后把这一格的整段（点数、强化、版本、对单格起作用的基因）连着重复，走完才到下一格。定类型和基因段不会重来。
- **管线同步算完**：一步（落子或弃置）在规则核心里一次推进到下一个稳定状态，返回一份有序事件列表。
  不做 Balatro 式的事件队列；规则核心不回调表现层；事件不带演出时长，但自带演出要用的块属性。
- **分数全整数**：底分、倍率用 `long`；独立倍率用千分值的 `long`（1000 = ×1），逐项相乘、每次向下取整。
  一次的得分 = ⌊底分 × 倍率 × 独立倍率 / 1000⌋，不为负，溢出时饱和、不回绕。没有浮点。
- **钩子六个点**：定类型后（结算前）、每格的重触发次数、每格每遍、基因段的每个基因、入账与清格之后（结算后）、每步收尾。
  钩子只返回数据（加多少、乘多少、重触发几次），由管线按固定字段序结算并吐事件。
- **试算就是管线的前半段**：预览调用落子也用的那个「判线、定类型」纯函数，只读、不碰随机流；不给管线加试算开关。
  要看完整一手（策略搜索用），就在 `RunState.Clone()` 上真走一步。
- **胜负在一步的最后判**：入账、清格之后先判胜，没胜才发组，最后判负。逐格中途不判。

全部按授权自裁，没有一项改变目的地或产品形状。依据写在各节；要推翻哪条，改那一节。
逐格先后、重触发口径和第 7 节的后果已回写规则 §3.1。

### 1 逐格顺序：按线走，先行后列

```
for 行 r in 满行（升序）:  for c in 0..7:  格 (r, c)
for 列 c in 满列（升序）:  for r in 0..7:  格 (r, c)，在行里走过的跳过
```

- 规则 §3.1 原来写着「格与格之间的先后待定」，审计 §2.2 把它和「重触发作用在哪些格」一起列为未定（`新游戏/设计/3B审计.md` §2.2）。
  基因清单里 #28 连票「首个被消除的方块格重算 2 次」、#39 定格「首个被消除结算的 L 块」都要一个确定的「第一个」；审计对 #28 的批注就是「一行是同时消掉的，没有先后」。
- **为什么按线**：
  - 玩家眼里消除的单位是线（「我消了这一行和那一列」）。一条线一条线扫过去、线上的格依次跳分，演出和计数对得上。block-client 的消除表现也是按线的光带（05 的表现最小集）。
  - 线这一层结构留着，以后要加「每条线开始 / 结束时」的效果，插在两条线之间就行，顺序本身不用改。
  - 交叉格归第一次走到它的那条线，也就是行。骈纹改造（§4.3.1 #4）「可同时计入最多 2 条线」就是在列上再走到它时多给一遍，不用另设口径。
- **为什么先行后列、行从上到下、列从左到右**：和读字的方向一致，玩家不用学。
  有满行时，第一格是最上那行的最左一格；只有满列时，是最左那列的最上一格。玩家想让某一格先结算，把它往左上放。
  这对应 Balatro 1.0.1o「计分牌按屏幕 x 坐标从左到右」，玩家靠摆位控制（[出牌结算管线.md](../../../参考/结论/Balatro_1.0.1o/出牌结算管线.md) §2，`state_events.lua:601-620`）。
- 满行、满列由 `CanClearRowCols(false)` 给出，满列是降序返回的（06），进管线前统一排成升序。
- 死格不会出现在被消格里，它所在的线凑不满（规则 §3.3）。
- **离场顺序不跟着改**：几块同时离场，仍按 id 升序入消尽堆（06）。本图没有规则读消尽堆的顺序。

### 2 重触发：只作用于逐格段，以格为单位

- 走到一格时，先问各来源这一格要额外触发几次，次序是所属块的强化 → 所属块的版本 → 基因从左到右，合计 n。然后把这一格的整段连走 1 + n 遍，再到下一格。
  这和 Balatro 1.0.1o 一样：`reps` 在一张牌开始结算时攒好，然后连着跑（`state_events.lua:689-705`）。
- **一格的整段** = 计一次所属块的点数 → 所属块的强化 → 所属块的版本 → 对单格起作用的基因（从左到右）。
  重触发是把这一整段原样再走一遍，不是「点数 ×2」。以后琉璃的碎裂判定、金箔的给钱如果挂在这一段里，也会跟着再来一遍。
  Balatro 的重触发同样会连带金蜡封、玻璃碎裂一起再跑（结论 §10 第 3 条）。
- **定类型、底注、基因段都只走一次。** #78 暮沉写的「立即重触发一次完整消除结算」，按这条读作「这次消除的每一格各多触发 1 遍」。
  审计说它「可读成总分翻倍」（`3B审计.md:376`），这里排除了那种读法；清单重长时照这条改写措辞。

### 3 管线形态：同步算完，返回有序事件

一步就是一个命令：`Place(实例 id, rot, row, col)` 或 `Discard(实例 id)`。规则核心在这次调用里把状态推进到下一个稳定状态，返回：

```
StepResult
  int                       Step     // 这一步之后的步数；被拒时不变
  StepReject                Reject   // None / NotInTray / CannotPlace / NoDiscards / BlindOver
  IReadOnlyList<RuleEvent>  Events   // 按发生次序；被拒时为空
```

- **被拒不抛异常、不改状态。** 表现层已经校验过落点，规则核心再校验一次（block-client 的「二次 gate」同理）。拒绝原因是枚举，调用方据此弹回。
- **规则核心从不回调表现层。** block-client 的 `BoardPlayFlow` 留了三个「清除前」回调（`BoardPlayFlow.cs:96-104`），
  因为它的结果对象里没有颜色，表现层得赶在格被清掉之前自己去读。3B 反过来：**事件自带演出要用的东西**（格、实例 id、种类、点数）。
  表现层只按事件演，演出中途不回读规则核心的盘面——那时盘面已经是这一步结束后的样子。
- **事件不带演出时长。** 时长是表现层的事；放进事件，改一次动画跑局轨迹就变（10 的轨迹逐行比事件），也违背 08「改一个动画就改了这一局」那条。
  迷雾「消除演出的节奏」因此只剩表现层的事，已转成新票（见文末）。
- **不做 Balatro 的事件队列。** Balatro 的 `evaluate_play` 一边算一边往 `G.E_MANAGER` 里排动画（`state_events.lua:592-1106`）。
  3B 要在演出开始前存档（12），跑局测试要逐步比事件（10），都要求一步的计算先完整结束。
- 存档、跑局、试走都只看 `StepResult` 返回之后的状态，步内没有可观察的中间态（06「步不留状态」）。

### 4 段落与事件

落子一步的完整段落。`[…]` 是第 5 节的钩子挂点；事件成员名是建议。

| # | 段落 | 做什么 | 事件 |
|--:|---|---|---|
| 1 | 校验 | 实例在待放置区、落点合法（问影子盘，06）、盲注进行中；否则拒绝 | — |
| 2 | 落子 | `BoardState.Place` 写盘，槽置空 | `PiecePlaced{InstanceId, Kind, Rot, Row, Col, Cells}`，Cells 按块内序号（06） |
| 3 | 判线 | `CanClearRowCols(false)`。没有满线：连击清零，跳到 #13 | — |
| 4 | 连击 | 连击 +1（05：结算前更新，结算里读到的值含本次） | — |
| 5 | 定类型 | 按第 1 节排出被消格，记下各格的 owner；按 §3.3 定类型（清屏看「占用去掉被消格」是否为空） | `ClearResolved{Rows, Cols, Cells, Type}` |
| 6 | [结算前] | 可以改类型等级、改基因自身的状态；不能改类型和被消格 | 各钩子的事件 |
| 7 | 读底注 | 按（类型，当前等级）查表：底分 A = 底注，倍率 B = 基础倍率，独立倍率 C = 1000 | `BaseApplied{Type, Level, Chips, Mult}` |
| 8 | 逐格段 | 按第 1、2 节：每格先问 [重触发]，再逐遍 A += 点数，然后 [每格] | `RepetitionGranted{…}`、`CellScored{Cell, InstanceId, Kind, Points, Repetition, Chips}`、`EffectApplied{…}` |
| 9 | 基因段 | 基因槽从左到右，每个基因 [基因]。本图是空列表 | `EffectApplied{…}` |
| 10 | 入账 | 得分 = ⌊max(A,0) × max(B,0) × C / 1000⌋，累计分 += 得分（第 6 节） | `ScoreBooked{Chips, Mult, XMultPermille, Gain, Total}` |
| 11 | 清格、离场 | 按被消格顺序 `ClearCell`；最后一格被消的块按 id 升序进消尽堆 | `CellsCleared{Cells, Departed}` |
| 12 | [结算后] | 碎裂判定、基因成长这类 | 各钩子的事件 |
| 13 | [步收尾] | 每一步都走：落子不论消没消，弃置也走 | 各钩子的事件 |
| 14 | 判胜 | 累计分 ≥ 目标分 → 胜，盲注结束，跳到 #17 | `BlindEnded{Outcome, Reason}` |
| 15 | 发组 | 待放置区全空、抽牌堆非空：按每组块数抽，剩几块抽几块（§2.2） | `GroupDealt{Group, Slots}` |
| 16 | 判负 | 抽牌堆和待放置区都空 → 负（预算耗尽）；否则待放置区非空、剩下的块怎么转都放不下、弃置用完 → 负（放不下） | `BlindEnded{Outcome, Reason}` |
| 17 | 收尾 | 步数 +1 | `StepEnded{Step, Combo, Total, DiscardsLeft, DrawLeft}` |

- 没消除的落子只走 1–3、13–17。
- **弃置一步**：校验（在待放置区、弃置次数 > 0、进行中）→ 槽置空、进弃置堆、次数 −1，吐 `PieceDiscarded{InstanceId, DiscardsLeft}` → 走 13–17。连击不变（§2.2）。
- **开盲注**不算一步（步数仍为 0），但同样返回事件：`BlindStarted{Target, Discards, GroupSize, DrawLeft}`、`GroupDealt`，再判一次负。
  空盘上四格骨牌不可能放不下，有死格之后才可能。
- **每步最后一个事件是 `StepEnded`**，带这一步之后界面要刷的数。连击 05 定了不上界面，但要进轨迹，放在这里。
- **事件形态**：每种事件一个类，成员只有整数、枚举、布尔、有序整数列表（10）。格一律用 `row*8 + col`；行、列列表升序；`Cells` 的次序就是它所在段落的次序。
- `EffectApplied{Source, SourceIndex, Cell, AddChips, AddMult, XMultPermille, Chips, Mult, XMultTotal}`：
  Source 是枚举（强化 / 版本 / 基因），SourceIndex 是强化或版本的枚举值、或基因的槽位，基因段里 Cell 为 −1。后三个成员是结算到这里时三区的累计值，表现层拿来跳数字。
  钩子返回空效果时不吐事件，所以本图的跑局轨迹里不会出现 `EffectApplied`，只有测试替身会让它出现。

### 5 钩子：挂点、能改什么、怎么注册

| 挂点 | 时机 | 拿到什么 | 能做什么 |
|---|---|---|---|
| 结算前 | #6，定类型后、读底注前 | 类型、被消格及各格 owner、局与盲注的只读视图 | 改类型等级（同 Balatro「出牌前」升级当次生效，结论 §1），改基因自身状态。不能改类型和被消格 |
| 重触发 | #8，每格开始 | 同上 + 当前格 | 返回额外触发次数，≥ 0 |
| 每格 | #8，每格每遍 | 同上 + 第几遍、三区当前值 | 返回效果：+底分、+倍率、×独立倍率（千分值） |
| 基因 | #9，每个基因 | 同上（没有当前格） | 同上 |
| 结算后 | #12 | 这次的得分、清格后的盘面 | 改状态（碎裂、成长）。不能再改这次的得分 |
| 步收尾 | #13 | 这一步是落子还是弃置、有没有消除 | 改状态。不能加分 |

- **钩子只返回数据**：一个效果结构（`AddChips`、`AddMult`、`XMultPermille`），重触发挂点返回次数。
  管线按固定字段序结算：先加底分、再加倍率、最后乘独立倍率，和 Balatro 单条效果里 `chips → mult → x_mult` 的次序一致（结论 §4.2）。
  事件也由管线吐，钩子自己不吐。改状态（改等级、碎裂、改基因计数）走上下文对象上的方法，管线据此记事件。
- **效果对象无状态。** 基因的计数、成长值一律挂在局状态里该基因的槽上，用整数。
  这样 `RunState.Clone()` 和存档天然带上它们，测试替身也不会在两局之间串状态（10 的 B 路拦的就是这个）。
- **要随机**就经 `RngStreams` 取，一个效果定义一个键（08）。
- **注册**：效果实现放进一张注册表，按（来源种类，id）查：强化、版本按枚举值，基因按基因 id。
  注册表和类型表一样，是开局时传进来的规则配置，不是状态：不进存档，`Clone` 共享同一份。本图的默认注册表是空的。
  - dotnet 单测往注册表里放测试替身，再把库里几块的强化设成对应枚举，验证「每被消 1 格触发一遍、次序同第 1 节」，这就是 05 要的钩子验证。
  - 阶段 5 的真效果走同一个入口（10：钩子是公开入口，不开 `InternalsVisibleTo`）。
- 效果基类用带空虚方法的抽象类，不用接口默认实现：后者要运行时支持，Unity 的 Mono 和以后 HybridCLR 的解释器是否都支持没核过，抽象类哪里都能用。
- **一步只判一次线**（#3）。以后有效果在结算后往盘上加块、凑满了线，这条线留到下一次落子判线时一起消（`CanClearRowCols` 扫的是整盘）。不做连锁消除，`Core/` 本来也没有。

### 6 分数的数值类型：全整数

| 量 | 类型 | 说明 |
|---|---|---|
| 底分 A | `long` | 底注 + 各格点数 + 加算分值，全是整数（11） |
| 倍率 B | `long` | 基础倍率 + 加算倍率。现有基因清单里的加算倍率全是整数（#2 +3、#10 +12、#30 +4…） |
| 独立倍率 C | `long`，千分值，1000 = ×1 | 每乘一项：C = ⌊C × 项 / 1000⌋。项也是千分值，≥ 0 |
| 一次的得分 | `long` | ⌊max(A,0) × max(B,0) × C / 1000⌋ |
| 累计分 | `long` | 进存档 |

- **为什么要小数位**：独立倍率区在清单里有 ×1.5（#66、#126、#127、#128）、每次 ×0.1 地叠（#76）、×0.25（#88、#92、#120）、×0.75（#85），#103 续丝每弃一块 −0.01。
  千分值装得下这些，还多留一位。0.75 的连乘这类，由效果自己按整数取整。
- **为什么不用 double**：
  - 迷雾「Unity 侧的确定性复核」点名剩下的风险是「计分的数值类型和遍历序」。遍历序 06 已经堵上；计分全用整数，就和 08 的随机流是同一个论证：没有浮点，就没有跨运行时的舍入差。
  - double 的加减乘除在 x64 SSE2 上是确定的，但还有几处要逐条论证：Mono 和 CoreCLR 的 `double.ToString("R")` 历来不一致，存档和轨迹都得改打位模式（10 为此留了口子）；
    以后移植手机走 IL2CPP，C++ 编译器在 ARM 上可能把乘加合成一条 FMA；`Math.Pow` 这类函数各平台的实现不同。全整数这几条都不用谈。
  - 3B 用不上 double 的量程：三区分开累加、最后才乘一次（第 7 节），不会像 Balatro 那样逐张 `mult *= x` 连滚。
    11 的占位下一次不到 1000 分，`long` 的上限约 9.2 × 10^18；规则里没有无尽模式，Balatro 1.0.1o 第 8 底注的基础目标在 10 万量级。
- **溢出饱和到 `long.MaxValue`，不回绕。** 乘除写成先除后乘的饱和形式：⌊x·y/d⌋ = (x/d)·y + ⌊(x%d)·y/d⌋。C 设一个不让中间积溢出的上限。具体写法归实现票。
- **取整**：A、B 是整数和，不用取整。C 每乘一项向下取整到千分位，所以同一区里的乘项换个先后，C 的末位可能差 1，对得分的影响小于千分之一，玩家看不出来。
  最终得分向下取整，和 Balatro 的 `floor(hand_chips × mult)` 一样（结论 §0）。
- **负数**：A、B 在累加过程中允许暂时为负，只在 #10 相乘时按 0 截。所以加算的先后不影响结果，一次的得分不会为负、不会倒扣累计分。
- **事件和存档里只有整数**，10 留的「浮点按位模式打印」用不上。累计分建议在存档里写成十进制文本，以后真要换大数类型，旧档照样能读（归 09）。
- **界面**：独立倍率按千分值格式化成「×1.5」，用 InvariantCulture。本图恒为 ×1。

### 7 同一乘区内的先后不改变得分

> 2026-10-28 已推翻：规则把乘区改成 ×倍率当场乘进倍率，先后会改变得分。见 [效果系统.md](../../../新游戏/设计/效果系统.md) §1、§9。

照规则 §3.1、§3.2，三区各自累加、最后乘一次；05 又定了独立倍率是各项之积。所以在 3B 里：

- 加算分值、加算倍率、独立倍率各自的项，谁先谁后，得分都一样（只差第 6 节的千分位取整）。
- 先后只在三种场合有意义：效果读了当时的累计值（比如「倍率 ≥ 20 时……」）；效果复制相邻基因（#73 血祭看右侧，#129 拓印复制右侧，#130 思潮复制最左）；
  同一个效果的几份副本做概率判定，它们共用一条随机流（08），谁先判谁先取数。
- **这和 Balatro 不同。** Balatro 只有一个 `mult` 累加器，×倍率当场乘进去，只放大在它之前进来的部分，所以「+倍率放左、×倍率放右」是硬机制（结论 §0、§6）。
  3B 规则 §4.1 的「基因可以拖动换位」分量因此轻得多。
- 本图没有基因，这条不影响任何实现。**记给阶段 5 重长基因清单**：如果想让位置像 Balatro 那样重要，要改的是 §3.1 的乘区结构，不是本票的管线。
  这条后果已写进规则 §3.1，免得以后照 Balatro 的直觉去设计基因。

### 8 试算：管线的前半段，不另开一条

- **拖动预览**（05、12）调用的是 #3、#5 那个纯函数：`ResolveClear(盘面, 种类, rot, row, col) → (合法?, 满行, 满列, 被消格（已按第 1 节排好）, 类型)`。
  真落子在 #3、#5 用的也是它，预览和真结算不会判岔。它只读盘面和块，不碰随机流，不跑钩子，不用 `Clone`。
  界面上的底注与倍率按类型和当前等级查表，和 #7 是同一个查表函数。
- **不给管线加「试算模式」开关。** 开关的毛病是：以后每加一种副作用（改状态、取随机、吐事件）都得记着判它，漏一处，预览就会偷偷推进随机流或改了状态。
- **要看完整一手**（含点数、钩子、随机），就在 `RunState.Clone()` 上真走一步、看返回的事件，然后丢掉拷贝。
  `Clone` 连 `RngStreams` 一起深拷（08：试算在流的副本上跑），原局的流不动。这条路只给 `Sim` 的搜索型策略用（18 的一步贪心、整组规划）；
  界面不用，05 定了预览不显示点数、强化、基因和随机结果。
- **另外两个只读查询**：「这块在这个落点合法吗」（落点吸附逐格问它）；「这块怎么转都放不下吗」（托盘置灰和 #16 判负共用，12）。
- 10 的 `greedy` 策略要的（类型底注 × 基础倍率，被消格数），预览正好都给。

### 9 胜负判定的时机

- **在一步的最后判，逐格中途不判。** 得分要到 #10 才入账，逐格段里只有三区累加器，谈不上「累计分已经达标」。
  §2.4 的「达标立即结束」指的是：判胜之后不再发组、不再判负，结果浮层直接出来。
- **次序：入账 → 清格 → 结算后 → 步收尾 → 判胜 → 发组 → 判负。**
  - 判胜在发组前：达标了就不发下一组，事件里不会出现一个刚发出来又用不上的组。
  - 判负在发组后：一次判负就盖住了 05 说的三种时机（落子后、弃置后、发新一组后）。发了新组就判新组，没发就判剩下的块。
- **第二种失败要求待放置区非空。** 待放置区空了，「剩下的块怎么转都放不下」是空真命题；那时抽牌堆如果也空，走的是第一种失败。两种失败因此互斥，原因只会有一个。
- 弃置不加分，也照走判胜：规则统一，代价只是一次比较。
- 结局一确定，规则核心就拒绝一切落子和弃置（`StepReject.BlindOver`）。删档归 09。

### 为什么不是别的做法

| 做法 | 不选的理由 |
|---|---|
| 整盘按扫描序逐格（行优先，交叉格自然只出现一次） | 一句话就能说清，但线的结构没了：十字的列会被行拦腰切成两段，演出没法一条线一条线地扫，以后也插不进「每条线」的效果 |
| 按块逐格（同一块的格挨着结算） | 块的先后要另定，id 序玩家看不见也控制不了；一块被消的格常分在几条线上，演出会在盘上来回跳 |
| 重触发 = 整次结算再来一遍 | 定类型、底注、基因段跟着重复，等于总分翻倍，正是审计对 #78 的担心；Balatro 的重触发也只作用于单张牌 |
| Balatro 式事件队列，边算边演 | 演出前存不了档，跑局测试比不了每步事件，动画时长一改计算顺序就可能跟着变 |
| 分数用 double | 第 6 节：要多论证几处跨运行时的一致性，3B 又用不上它的量程 |
| 独立倍率用 `BigInteger` 精确连乘 | 先后完全无关、零误差，但规则核心要多背一个大数类型，换来的只是玩家看不见的千分之一 |
| 预览单写一个函数 | 两份判线定类型的代码迟早判岔，玩家会看到预告是 A、落下去却是 B |
| 管线加试算开关 | 第 8 节：每加一种副作用都要记得判它 |
| 逐格中途达标就停 | 得分要三区乘完才有；中途停还会让后面的格和基因段白白不触发 |
