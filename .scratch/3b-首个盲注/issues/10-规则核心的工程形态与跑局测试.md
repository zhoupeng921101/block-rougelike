## Question

规则核心程序集落在 `Demo/` 哪里、叫什么、怎么被 GameLogic 引用；dotnet 测试工程放哪；devflow 的客户端自检怎么跑它。

依 [规则核心的双端编译与单测](03-规则核心的双端编译与单测.md) 的调查选布局。
命名空间、程序集要不要进热更清单（工程计划：热更分层照留，HybridCLR 暂关）一并定。

[种子与随机流](08-种子与随机流.md) 已定的前提：
- [research/08](../research/08-随机流向量.md) 的向量表直接写成单测常量，这本身就算一项跨进程比对；
- 落子策略如果要随机，自己开 `RngStreams`，键用 `sim.` 前缀，不进对局状态；
- 比较的最终状态要包含所有流的 `(s0, s1)`。

## Answer

**据此裁定：**

- **程序集 `GameRules`**：正本放 `Demo/Assets/GameScripts/HotFix/GameRules/`，命名空间 `GameRules`，进热更清单并排在 `GameLogic.dll` 前面；GameLogic 的 asmdef 引用它。
- **dotnet 侧放 `Demo/DotNet/`**，下设三个工程：镜像库 `GameRules/`、唯一的测试工程 `Tests/`（NUnit；15 号票的文本表校验也写进这里）、跑局工程 `Sim/`（17 号票建）。
- **客户端自检加第十四道 `dotnet单测.ps1`**（并行跑）。restore 失败判 INFRA，编译失败或用例失败判 FAIL。
- **跑局测试**：两种策略，贪心和 `sim.policy` 随机。比的是**规范化轨迹的全文**：每步的动作、每步的事件、终局摘要，再加上终局状态的存档快照（含各流的 `(s0, s1)`）。
  比四种：同进程跑两次、换区域设置再跑一次、子进程跑一次、每隔几步存读一次接着跑。

没有一项改变目的地或产品形状，全部按授权自裁。依据写在各节，要推翻哪条只改那一节。
（wayfinder 要求的 domain-modeling 技能本机没有，只按 `.agents/skills/grilling` 裁。）

### 1 程序集：名字、位置、asmdef

| 项 | 裁定 |
|---|---|
| 程序集名 | `GameRules`。architecture.md 的命名规则：`Game*` 无后缀 = 热更层（`Demo/.claude/references/tengine/architecture.md` 命名规则表），和第 3 节一致 |
| 正本目录 | `Demo/Assets/GameScripts/HotFix/GameRules/`，与 `GameLogic/` 平级。模块分子目录（`Random/`、`Board/`、`Scoring/` …），由各执行票按需建 |
| asmdef | `noEngineReferences: true`；`references: []`；`overrideReferences: true` + `precompiledReferences: []`；`autoReferenced: false`；`allowUnsafeCode: false`；`rootNamespace: "GameRules"` |
| 谁引用它 | 只有 GameLogic：`GameLogic.asmdef` 的 `references` 加一条 `GUID:<GameRules.asmdef.meta 的 guid>`，写法照现有几条 |

依据：

- 放在 `Assets/GameScripts/` 下，主工程通道的验凭据面 `GatedRe` 才管得到它（`hooks/校验库.ps1:80`），命名空间扫描、Editor程序集编译 也都现成覆盖（研究 03 §四）。
- `overrideReferences: true` 并清空预编译引用：不加的话，`Assets/Plugins` 里勾了自动引用的 dll 会被 Unity 那一侧悄悄引进来，而镜像库里没有它们，两端引用集就不一致了。
  这样两端都是「零外部引用」。规则核心将来真要用第三方库（比如存档序列化，见「对其它票」的 09），asmdef 和镜像库的 `PackageReference` 要在同一笔改动里一起加，版本对齐 Unity 包里的那份。
- `autoReferenced: false`：predefined 程序集里不该有运行时代码（`tengine-conventions.md`「程序集归属」），关掉也不影响 Editor程序集编译，它经 GameLogic 的引用照样会编到规则核心。
  以后要是有编辑器工具得直接调规则核心，再把这一项打开，只改一行。

### 2 命名空间：`GameRules`，不落全局

本作的业务代码都落全局命名空间（`tengine-conventions.md`「客户端命名空间」）。规则核心不照这条，要声明命名空间。依据：

- **全局类型会静默顶替引擎类型。** 规约里写了，全局命名空间的类型优先于 `using` 引进来的同名类型。
  规则核心里很自然会出现 `Grid`、`Event` 这样的名字，而 `UnityEngine.Grid`、`UnityEngine.Event` 都存在。规则核心如果落全局，GameLogic 里所有 `using UnityEngine;` 的文件都会静默改指向，编译也不报错。
  带上命名空间以后，GameLogic 写 `using GameRules;`，遇到同名就是 CS0104 歧义报错，问题会当场暴露。
- **有先例。** 配置层（`GameConfig`）同样是热更层、被 GameLogic 消费，它的根命名空间就等于程序集名（architecture.md 命名规则第 2 条）。规则核心按同一条处理。
- **代价**：
  - 从 block-client 拷来的 `Core/` 五个文件和 `PortableRng.cs` 原来都在全局命名空间，要包一层 `namespace GameRules { … }`。C# 9 没有文件作用域命名空间，只能用块写法。
    **这几个拷来的文件只在首尾各加一行，正文不重新缩进**，这样逐行仍和 block-client 相同，以后对照上游修补时 diff 里只多两行。新写的文件照常缩进。
    这和[数据模型](06-盘面与方块实例的数据模型.md)票的「`Core/` 五个文件一行不改」不冲突：那张票明写了命名空间以本票为准，包这一层也不动任何声明和逻辑。
  - 命名空间扫描要加一条覆写，规约表和 architecture.md 要同步改，都由 [规则核心的工程骨架](16-规则核心的工程骨架.md) 来做。
- 测试与跑局工程在 `DotNet/` 下，客户端的命名空间规约和扫描都管不到这里，执行票自己定命名空间就行。

### 3 进热更清单

裁定：进。`UpdateSetting.asset` 的 `HotUpdateAssemblies` 改为 `GameRules.dll`、`GameLogic.dll` 两项，依赖的排在前面。

依据：

- 规则核心就是玩法规则，是全游戏改得最勤的代码。工程计划要「保留热更程序集分层」，留着它，移植手机时一打开就能用。

  收集到的列表交给 `GameApp.Entrance`，但只存起来、没人用（`GameApp.cs:23`）。
- **代价**（由 16 号票做）：
  - `HybridCLRSettings.asset` 要同步；
  - `热更程序集核对.ps1` 的 `$Whitelist` 要加 `GameRules.dll`。这个脚本头注写明「加入前须实测出包」（`:35-37`），所以 16 号票的验收里要出一次 Windows 包。

### 5 客户端自检的挂点

新加第十四道，脚本 `Demo/.claude/devflow/dotnet单测.ps1`，Tag `dotnettest`，`Async`。

- **跑什么**：
  1. 先 `dotnet restore DotNet/Tests/Tests.csproj`，失败判 **INFRA**（多半是离线又没有缓存）；
  2. 再 `dotnet test DotNet/Tests/Tests.csproj --no-restore`，编译失败或任一用例失败都判 **FAIL**；
  3. 找不到 `dotnet` 判 **INFRA**。
  - 编译失败判 FAIL，因为镜像库拦住的正是「Unity 编不过的写法」，这算代码违规。
  - FAIL 时把失败用例名和断言消息的前几行打出来。
  - 关掉 MSBuild 常驻节点（`-nodeReuse:false`），免得常驻进程锁住 `obj/` 里的文件。
- **准入登记**：`Basis=用户裁定`，`Origin` 写 2026-10-26 工程计划阶段 2 的原话「客户端自检加一道规则核心的 dotnet 单测」，`Retire` 写「规则核心与文本表的校验改由别的机判承接时」。判据见 `hooks/hook函数库.ps1:594-613`。
- **读取面登记**（`ClientGateScanSurface`）：`'^Demo/(Assets/GameScripts/HotFix/GameRules/.*\.(cs|asmdef)|DotNet/.*\.(cs|csproj|props|targets))$'`。
  15 号票接文本表校验时，再把 `texts.json`、`TextKeys.cs`、`AssetRaw/UI` 下的 prefab 和主字体资产的 meta 加进来。
- **产物**：`DotNet/**/bin|obj` 已由 `.gitignore` 新加的三行忽略，`TestResults/` 原本就在忽略里。跑局的子进程只往 stdout 写，不落文件。这样不改树哈希，不会被判 STALE（研究 03 §3.4）。
- **耗时预算**：本道热跑控制在 10 秒内。研究 03 实测增量 `dotnet test` 约 2.5 秒，余下的给跑局测试（第 7 节的种子数按这个预算调）。

  主工程通道按 CLAUDE.md 收尾时本来就要跑自检，这个缺口照 `GatedRe` 的注释（`hooks/校验库.ps1:75-79`）登记进台账的「已知缺口」，不在本图扩面。

### 6 规则核心的编码约束

两端编的必须是同一份代码，每次跑的结果也必须一样。约束和拦截手段：

| 约束 | 谁拦 |
|---|---|
| 不引 UnityEngine，不写 `#if UNITY_*` | asmdef + 镜像库（研究 03 §2.3）；`#if` 由下面的源码禁用清单拦 |
| 不用 `record`、`init`，不用 C# 10 以上的语法和 .NET 6 以上的 API | 镜像库 |
| 不碰非确定来源：`System.Random`、`DateTime.Now/UtcNow`、`Guid.NewGuid`、`Environment.TickCount`、`Stopwatch`；不调 `.NextDouble(`（08 号票：只取整数） | **源码禁用清单测试**：一个 NUnit 用例按文本扫正本目录下的 `.cs`，清单写在用例里 |
| 不拿字符串哈希、默认对象哈希派生任何东西；任何可观察的结果（事件顺序、存档文本、发块）都不依赖 `Dictionary` / `HashSet` 的遍历序 | 静态扫不出来，由第 7 节的子进程比对兜底：CoreCLR 每个进程的字符串哈希都不同 |
| 格式化和大小写转换一律用 InvariantCulture（08 号票） | 第 7 节换区域设置的那一路 |

这几条由 16 号票写进 `tengine-conventions.md`，新开一节「规则核心」。

### 7 跑局测试

**落子策略**放在 `Sim` 工程里，不放进规则核心：它是测试和定标用的工具，不该随包发出去。两种策略都只调规则核心的公开 API。

| 策略 | 怎么选 |
|---|---|
| 贪心 `greedy` | 按（槽位、朝向 0–3、行、列）的字典序枚举全部合法落子，每个都调一次无副作用的试算（05 号票的拖动预览）。取（类型底注 × 基础倍率，被消格数）最大的那个；没有能消的就都算 0。平手取枚举序第一个，不排序，所以不依赖排序是否稳定。没有合法落子时，弃掉槽位最靠前的一块；弃置次数用完的话，规则核心已经判负了 |
| 随机 `random` | 合法动作 = 全部合法落子（同上枚举序），弃置次数还有时再加上「弃第 i 块」。用策略自己的 `RngStreams`，种子文本与对局相同，键 `sim.policy`，取 `Index(n)`。这条流不进对局状态（08 号票） |

- 贪心不带状态，是「存读续跑」那一路的前提。随机策略覆盖到的落子和弃置更杂。
- 两种都设步数上限：方块库块数 + 弃置次数 + 1。超过上限说明规则核心没能结束这一局，直接判用例失败。

**「逐项」比的是规范化轨迹的全文**，不是哈希。轨迹是纯文本，出错时报第一处不同的行，比一个哈希值好查。一局的轨迹：

```
game seed=<种子文本> policy=<策略>
step <n> place inst=<实例 id> rot=<朝向> r=<行> c=<列>    或  step <n> discard inst=<实例 id>
  <事件类型名> <成员>=<值> …                              规则核心这一步吐出的每个事件一行，按吐出的次序
end outcome=<结局> reason=<失败原因> score=<累计分> steps=<步数>
state <终局的存档快照文本>                                 含各流的 (键, s0, s1)，见 09
```

- **事件**：反射打印，成员按名字的 ordinal 序排列（不按声明序，`GetProperties` 的返回顺序没有保证）。
  - 整数、枚举名、布尔、字符串直接打印；有序列表打成 `[a,b,…]`；嵌套对象递归打印。
  - 浮点（如果 07 号票定了用浮点）打印成位模式的十六进制。
  - 遇到 `Dictionary` / `HashSet` 直接抛异常：事件里不许出现无序容器。
- **终局状态**：直接用 09 号票的存档快照文本，不另写一套状态转储。这样存档格式本身也跟着受测。

**比四种，都要求和基准 A 全文一致**：

| 路 | 做法 | 拦什么 |
|---|---|---|
| A 基准 | 测试进程里跑一局 | — |
| B 再跑 | 同一进程，全新对象再跑一次，`CurrentCulture` 设成 `tr-TR` | 静态可变状态、缓存串局；区域设置相关的格式化和 `ToUpper` |
| C 子进程 | 测试起一个 `dotnet Sim.dll --seeds … --policy …`，从 stdout 读回所有局的轨迹 | 跨进程才会暴露的不确定：字符串哈希、默认对象哈希、遍历序 |
| D 存读续跑 | 只用贪心策略。第 1、2 步，以及之后每隔 5 步：存档快照 → 文本 → 读回一个新状态 → 用同一策略接着打完，再和 A 比 | 存档漏了什么状态：漏掉的状态只要影响后面的发展，续跑就会分叉。另外每一步都比一次「快照 → 读回 → 再快照」两份文本是否相同 |

- **种子**：`TESTSEED`，加上 `SeedText.FromEntropy(1)` 到 `(7)`，共 8 个；每个种子各跑两种策略。超出第 5 节的耗时预算就先减种子数。
- **方块库和盲注规格**用游戏实际出包的那份默认值（占位，11 号票），不另做测试专用规格。
  不断言「每种结局都出现过」，因为它会随占位数值变，容易误报。胜负各条路径由规则核心单测覆盖。
- **不存入库的基准轨迹**：规则和占位数值一改，基准就得重生成，噪声太大。跨进程这一项靠 C 路的子进程。
  RNG 那一层另有 08 号票的向量表常量，那组常量本身就是一项跨进程比对，由 16 号票先写进去。

**17 号票落地后定下来的数（2026-10-28，`d33b4cf3`）**：

- 种子没减，仍是 8 个 × 两种策略，共 16 局；D 的存读点也没减，仍是第 1、2 步及之后每隔 5 步。每局平均 24.3 步（贪心 26.1、随机 22.5）。
  `dotnet单测` 热跑 3.5–4.1 秒（落地前 1.9–2.2 秒），跑局测试 33 个用例本身约 0.4 秒，其中 C 路的子进程约 0.1 秒，离第 5 节的 10 秒还远。
- **改了上表两处**，原因是按原样做，17 号票的故意出错有两种拦不住：
  - **B 的区域设置**：以 `tr-TR` 为底（大小写规则不变），数字再夸大成每 1 位一组、负号写成 `~`。本图的分数到不了 1000，原样的 `tr-TR` 下 `ToString("N0")` 和别的区域写出来一样。

### 没选的

| 做法 | 不选的理由 |
|---|---|
| 规则核心落全局命名空间 | 第 2 节：会静默顶替 `UnityEngine.Grid` / `Event` 这类同名类型 |
| 规则核心放 AOT、不进热更清单 | 第 3 节：规则是改得最勤的代码，放 AOT 每改一次都得出整包 |
| 测试拆成规则核心、文本表两个工程 | 要多一个 `.slnx` 和一条反忽略，那一道要跑两次 `dotnet test`；按目录分开就够了 |

| 入库基准轨迹或基准哈希 | 第 7 节：规则和占位数值一改就要重生成；跨进程比对改由子进程做 |
| 落子策略放进规则核心 | 机器人代码会跟着发进包里。Unity 侧要用的话，到那张复核票时再搬 |
| 只比终局哈希 | 出了错不知道是哪一步分叉的，也查不到存档漏了什么 |
