# 03 · 规则核心双端编译：调查记录

对应票：[03-规则核心的双端编译与单测](../issues/03-规则核心的双端编译与单测.md)。2026-10-27，只读调查 + scratchpad 一次性原型（不在仓里建工程）。

出处约定：`TEngine_block/` = `E:\TEngine_block`（main@4cb5dc49f）；`Demo/` 即本仓 `Demo/`；`Unity/` = `C:\Program Files\Unity\Hub\Editor\6000.3.19f1\Editor\Data`。

## 结论

**推荐布局 A：源码正本放 `Assets/` 下的独立 asmdef（`noEngineReferences: true`、`references: []`），`Demo/DotNet/` 下放一个只做链接的镜像库（`netstandard2.1` + C# 9），测试与跑局工程都引用这个镜像库。**

理由三条：

1. **边界由机器保证，不靠注释。** block-client 的双端文件靠头注「不得引入引擎类型」自律，链进去的文件一碰客户端就得写桩（NumericSim 有 81 行 `Adapters.cs`）。独立 asmdef 关掉引擎引用、不引任何程序集，Unity 那一侧就编不过越界代码；dotnet 侧因此能整目录通配，不写桩。
2. **镜像库与 Unity 同语言、同 BCL。** 实测 9 种 Unity 编不过的写法，镜像库 9 种全拦；照 block-client 先例直接链进 net8.0 工程只拦 1 种。
3. **devflow 现成的两道直接覆盖它。** 工程链接核对自动扫到 `Demo/**/*.csproj`；Editor程序集编译会经 GameLogic 的引用把规则核心用 Unity 自己的 csproj 再编一遍。只差一道 `dotnet test`，台账已登记这个缺口。

要动的东西：`Demo/.gitignore` 加三行（不加则测试工程入不了库、bin/obj 让自检判 STALE）；客户端自检加一道单测。名字、命名空间、热更归属留给 10 号票。

## 二、Unity 6000.3 的语言与 BCL 上限

### 2.1 本机工程的实据

| 项 | 值 | 出处 |
|---|---|---|
| 实际编译参数 | `-langversion:9.0` | `Demo/Library/Bee/artifacts/1900b0aP.dag/GameLogic.rsp:360` |
| 实际引用的 BCL | `NetStandard/ref/2.1.0/netstandard.dll` | 同上 `:257` |
| API 兼容级别 | `apiCompatibilityLevel: 6`（.NET Standard 2.1） | `Demo/ProjectSettings/ProjectSettings.asset:986` |
| 宏 | `NET_STANDARD_2_1`、`NETSTANDARD2_1`、`CSHARP_7_3_OR_NEWER` | 同 rsp 的 `-define` 段 |
| Unity 生成的 csproj | `LangVersion 9.0`；`TargetFrameworkVersion v4.7.1` 只是给 IDE 的占位，真实编译看 rsp | `Demo/GameLogic.csproj:4`、`:21` |
| 自带编译器 | Roslyn 4.3.1（语法能到 C# 11，被 `-langversion:9.0` 锁住） | `Unity/DotNetSdkRoslyn/Microsoft.CodeAnalysis.CSharp.dll` 文件版本 |
| 运行时 | MonoBleedingEdge，mscorlib 4.6.57 | `Unity/MonoBleedingEdge/lib/mono/4.5/mscorlib.dll` |

### 2.2 官方文档

- C# 9.0；不支持的 C# 9 特性：suppress localsinit、协变返回、模块初始化器、函数指针扩展调用约定、**init-only setter**。record 要 `IsExternalInit`（.NET 5+ 才有），可自声明绕过；Unity 序列化不支持 record。—— https://docs.unity3d.com/6000.3/Documentation/Manual/csharp-compiler.html
- 默认 API 兼容级别是 .NET Standard 2.1。—— https://docs.unity3d.com/6000.3/Documentation/Manual/dotnet-profile-support.html
- asmdef 的 No Engine References：开启后编译时不加 UnityEditor / UnityEngine 引用。—— https://docs.unity3d.com/6000.3/Documentation/Manual/class-AssemblyDefinitionImporter.html

### 2.3 实测：哪种 dotnet 配置能提前拦住 Unity 编不过的写法

原型在 scratchpad 里搭（`proto/Demo/Assets/GameScripts/Rules/` + `proto/Demo/DotNet/`），三种 csproj 链接同一目录，逐个放探针编，SDK 10.0.204：

| 探针 | Unity 能编? | 镜像库 netstandard2.1 + C#9 | net8.0 + C#9 | net8.0 + latest（先例） |
|---|---|---|---|---|
| 文件作用域命名空间 `namespace X;` | 否（C# 10） | CS8773 | CS8773 | **编过** |
| `global using` | 否（C# 10） | CS8773 | CS8773 | **编过** |
| `init` 访问器 | 否 | CS0518 | **编过** | **编过** |
| `record` | 否（缺 IsExternalInit） | CS0518 | **编过** | **编过** |
| `Random.Shared` | 否（.NET 6） | CS0117 | **编过** | **编过** |
| `ArgumentNullException.ThrowIfNull` | 否（.NET 6） | CS0117 | **编过** | **编过** |
| `PriorityQueue<,>` | 否（.NET 6） | CS0234 | **编过** | **编过** |
| LINQ `Chunk` / `TryGetNonEnumeratedCount` | 否（.NET 6） | CS1061 | **编过** | **编过** |
| `using UnityEngine;` | 否（noEngineReferences） | CS0246 | CS0246 | CS0246 |
| `HashCode.Combine` / `Math.Clamp` / `MathF` | 能 | 编过 | 编过 | 编过 |
| `Span<T>` / 元组 / switch 表达式 / 目标类型 new | 能 | 编过 | 编过 | 编过 |

结论：**只锁 LangVersion 不够，要连目标框架一起锁到 netstandard2.1。** 测试与跑局工程可以是 net8.0，但规则源码不能在它们里面编，要经 `ProjectReference` 引镜像库。

另外两条约定，免得两边编的不是同一份代码：

- **规则核心里不写 `#if UNITY_*`。** 镜像库没有 Unity 宏，这类分支在 dotnet 侧走另一条路，测的不是出包的那份。
- **不用 `record` / `init`。** 加 `IsExternalInit` 桩能编过，但 Unity 文档把 init 列为不支持；规则核心是纯数据，用不着。

## 三、测试工程放哪：目录冲突

### 3.1 Unity 不导入什么

- 只导入 `Assets/`（和 `Packages/`）。工程根下的其他目录不扫：`Demo/Build`、`Demo/Captures`、`Demo/.claude` 现在就在那里，没有被导入。
- `Assets/` 里跳过：隐藏目录、`.` 开头、`~` 结尾、名为 `cvs` 的目录、`.tmp` 文件。—— https://docs.unity3d.com/6000.3/Documentation/Manual/SpecialFolders.html
- devflow 的实扫与之同口径：`Demo/.claude/devflow/hooks/hook函数库.ps1:1246`（`Test-UnityIgnoredPath`）。

### 3.2 `Demo/` 根目录不能放

| 坑 | 后果 | 依据 |
|---|---|---|
| Unity 在根目录按 asmdef 名重生成 `<名>.csproj` 和 `Demo.sln` | 同名手写 csproj 被覆盖 | `Demo/` 根现有 22 个生成的 csproj |
| 根目录已有一堆 csproj / sln | `dotnet test` 不带路径报 MSB1011 | 原型实测 |
| SDK 工程默认通配 `**/*.cs` | 放根目录会把整个 `Assets/` 编进来 | SDK 默认行为；先例都关了 `EnableDefaultCompileItems` |
| Editor程序集编译 在根目录写临时重建 csproj | 与手写工程同目录，易混 | `Demo/.claude/devflow/Editor程序集编译.ps1` 头注「重建的临时 csproj 落工程根」 |

### 3.3 `Directory.Build.props/targets` 只能放在 `DotNet/` 里

Unity 生成的 csproj 是旧格式，但导入的 `Microsoft.CSharp.targets` 会连带导入路径上的 `Directory.Build.props` 和 `.targets`（原型用 `dotnet msbuild -preprocess` 实测，两者都进来了）。放在 `Demo/` 根或仓根，会混进自检对 Unity csproj 的 `dotnet build`。

### 3.4 `.gitignore` 现在会挡住测试工程

`Demo/.gitignore` 的三条规则：

- `:31 *.csproj`、`:33 *.sln`、`:34 *.slnx`——**任意深度**都忽略，手写的测试工程入不了库；
- `:7 /[Oo]bj/` 只管根目录，子目录的 `obj/` 和 `bin/` **不忽略**。

在一次性 git 仓里实测，加这三行后状态正确：csproj 可见，bin/obj 忽略，根目录生成的 csproj 照旧忽略。

```gitignore
# dotnet 侧规则核心工程（Unity 不导入；csproj 手写入库，产物不入库）
!/DotNet/**/*.csproj
/DotNet/**/[Bb]in/
/DotNet/**/[Oo]bj/
```

不加的后果不只是「入不了库」：自检的树哈希把**未跟踪且未忽略**的文件也算进去（`hook函数库.ps1:1139-1140`）。测试跑起来会在 `bin/obj` 写文件，首尾哈希不一致，自检判 STALE，永远发不出凭据。

### 3.5 `Assets/` 里的 `~` 目录（如 `Rules/Tests~/`）：Unity 不管，devflow 管

- 命名空间扫描的 A 段用 `Get-ChildItem -Recurse -Filter *.cs` 枚举 `Assets/GameScripts` 等根，**不跳过 `~` 目录**（`Demo/.claude/devflow/命名空间扫描.ps1:64-66`）。测试代码一旦声明命名空间就判违规；`obj/` 里的生成文件也会被扫到。
- `bin/obj` 落在 `Assets` 树里，同样要额外的忽略规则。
- 能用，但要改扫描脚本。放 `Assets/` 外更省事。

## 四、devflow 现状（`Demo/.claude/devflow/` 只读）

- **客户端自检十三道，没有单测。** 十二道静态扫描 + 末道 Editor程序集编译（`客户端自检.ps1:84-98`）。头注写明测试不在覆盖内（`:33`）。
- **缺口已登记。** 「规则核心的 dotnet 单测还不是自检的一道」，计划随阶段 3 建程序集时加道，并在 `ClientGateScanSurface` 登记读取面（`obligation-ledger.md:72`）。
- **flow-config 没有相关键。** 现有键：RepoRoot、FantasyRoot、ServerDirName、五个槽位键、SlotSparseDirs、UnityReadyTimeoutSeconds、两个 Baseline、StaleClaimHours、BoardRelPath、两个 Luban bat（`flow-config.psd1:11-58`）。dotnet 测试路径可以像 `Demo` 目录名一样写死在脚本里，不必进配置。
- **工程链接核对自动覆盖镜像库。** 它按 `git ls-files --cached --others --exclude-standard -- Demo/*.csproj` 取面（`工程链接核对.ps1:41`）。git pathspec 的 `*` 跨目录（实测能列出 `Demo/DotNet/**/x.csproj`），通配项只核通配符之前的目录在不在。前提是 3.4 的反忽略已加，否则 csproj 根本不在面里。
- **Editor程序集编译 会顺带编规则核心。** 它编 Assembly-CSharp-Editor 及其 ProjectReference 闭包（`客户端自检.ps1:25-26`）。GameLogic 一引规则核心，规则核心就按 **Unity 生成的 csproj**（C# 9 + Unity 的引用集）再编一遍。第二遍按出包平台宏编运行时程序集，跳过 `UNITY_INCLUDE_TESTS` 测试程序集（`Editor程序集编译.ps1:339-341`）。
- **新建 asmdef 的头一回会 INFRA。** asmdef 新增或引用变化只有编辑器重生成 csproj 才进得来，在那之前判 STALE-REGEN（`重建csproj.ps1:27-30`）。规则核心第一批代码落地时，要先在编辑器里刷新一次 csproj。
- **主工程通道的验凭据只认 `Assets/(GameScripts|Launcher)` 下的 `.cs/.asmdef`**（`hooks/校验库.ps1:80` `GatedRe`）。规则核心放 `Assets/GameScripts/` 下就在面内；放 `Packages/` 或 `DotNet/` 下的源码不验票。

新加一道「规则核心单测」，要满足这些既有约束：

- 脚本头带准入登记，`客户端自检.ps1:118` 开跑前就核；
- 在 `ClientGateScanSurface` 登记读取面（`hooks/校验库.ps1:37-56`），面大致是 `^Demo/(Assets/GameScripts/<规则核心>/.*\.(cs|asmdef)|DotNet/.*\.(cs|csproj|props))$`；
- 冷跑超过两秒，标 `Async`；
- 产物全部落在忽略路径里；
- restore 失败判 INFRA，不判 FAIL。

## 五、跑局测试的自动落子策略

### 5.1 `AutoPlay/` 能借的只有决策层

`TEngine_block/UnityProject/Assets/GameScripts/HotFix/GameLogic/AutoPlay/` 共 12 个文件：

- **8 个引 UnityEngine**：Session、Pointer、Scene、Input、Cursor、Paths、Stats、Story。它们驱动真界面的指针拖拽，dotnet 里用不了。
- **4 个不引**：Brain、Level、Observer、Verdict。后两个绑在会话流程上，用不着。

`AutoPlayBrain.cs`（426 行）：

- 整文件包在 `#if AUTOPLAY` 里（`:1`）；
- 随机用 `System.Random`（`:155`、`:278`、`:281`）；
- 候选排序用 `List.Sort`（`:272`、`:336`、`:384`）。这是不稳定排序，同分时的先后由实现决定，同一运行时内可复现，跨 Mono / CoreCLR 不保证；
- 四档水平：新手、普通、高手、最优。最优档零随机，整手推演，束宽 64（`:96-109`）。

`AutoPlayLevel.cs` 的 GM 开关在 `#if UNITY_EDITOR` 里（`:36`），dotnet 下自然剔掉。

NumericSim 已经在 Unity 外跑它：`new AutoPlayBrain(new Random(seed ^ 0x24681357), bot)`（`TEngine_block/Tools/NumericSim/src/BoardEngine.cs:61`）。这是「落子策略单独一条随机流，从主种子派生」的先例。

### 5.2 `MoveScoring.cs` 本身纯，但签名绑着 Block Blast 的数据模型

- 139 行，单步评分 + 三槽全枚举择优（`Module/BlockBlast/MoveScoring.cs:51`、`:79`）。
- 依赖闭包：`BinaryBoard`、`BlockShapeMap`、`BlockShape`、`ClearResult`、`Vec2Int`（Core/）；`BoardMetrics`（Offer/，头注自称零依赖，`Offer/BoardMetrics.cs:13`）；`PendingPiece`、`BlockColor`、`BlockSpecialType`。
- 全部不引 UnityEngine，全在全局命名空间，已被 NumericSim、PatternEnergyTest 链出 Unity 编过（`NumericSim.csproj:43`）。
- **对 3B 的错位有两处：**
  - 数据模型：`PendingPiece` 带颜色、特殊块、锚点；`BinaryBoard` 只记占用（map「已知的坑」第二条）。06 号票换模型后，签名要跟着改。
  - 目标：评分项是 Block Blast 的「活下去」（消行、死格、起伏、占格），3B 要的是预算内凑够目标分。

### 5.3 建议

- **阶段 3 的「同种子跑两次」不需要好策略，只需要确定。**
  - 用贪心单步：搬 `BoardMetrics` 和 `PickBest` 的枚举骨架，改用 3B 的块实例；
  - 零随机；
  - 同分按（槽位, 朝向, 行, 列）字典序取第一个，不依赖 `List.Sort` 的稳定性，以后在 Mono 里对拍也成立。
- **阶段 6 定标再加 3B 计分项。** 在评分里加入规则核心试算的本手得分，需要时再参照 `AutoPlayBrain` 的推演 / 束宽结构；随机改走规则核心的 RNG 分流（08 号票），不用 `System.Random`。
- **跨进程才暴露的不确定，要专门防。** CoreCLR 的 `string.GetHashCode` 每个进程不同（实测连跑三次，三个值）。同一进程里跑两次逐项一致，不代表存档重开、或另一台机器跑出来也一致。
  - 规则核心不得拿字符串哈希派生种子、排序或分桶；
  - 「逐项一致」最好有一项跨进程比对：Sim 输出逐步轨迹文件，和入库的基准轨迹比；或者起两个子进程互比。
  - `PortableRng.cs:16-21` 把这类隐患记成 c1 枚举序、c2 double 分支、c3 System.Random。
  - 怎么比由 10 号票定，Mono 侧复核仍按 map「Unity 侧的确定性复核」那条走。

### 布局 B：嵌入式 UPM 包 + `Tests~`


技术上可行，csproj 写法同 A，只是相对路径变了。但它和 devflow 的分区处处对不上：

- CLAUDE.md 把 `Demo/Packages/` 划为工程文件，走人工入库通道（`Demo/CLAUDE.md:69`）；规则核心却是产品代码，要走 devflow。
- `GatedRe` 只认 `Assets/(GameScripts|Launcher)`，主工程通道提交包内源码不验票（`hooks/校验库.ps1:80`）。
- 命名空间扫描只扫 `Assets`，包内代码不受命名空间与程序集归属规约约束。
- Editor程序集编译 的第二遍不把内嵌包程序集当编译根，只在被引用时连带编（`Editor程序集编译.ps1:339-340`）。
- architecture.md 把热更层代码放在 `GameScripts/HotFix` 体系里。

要走 B，得先改这几处。不推荐。

### 布局 C：dotnet 预编 DLL 进 `Assets/Plugins/`

```
Demo/DotNet/<规则核心>/            源码正本 + SDK csproj（netstandard2.1），默认通配
Demo/Assets/Plugins/<规则核心>/<规则核心>.dll (+ .pdb)    构建产物入库
```

好处：dotnet 是唯一编译点；IL 对 Mono 无所谓语法版本，可以写 C# 10+ 的纯语法糖。坏处更重：

- 二进制入库，两个槽位同时改规则核心必然撞 devflow 的 `BLOCKED-BINARY`（`Demo/CLAUDE.md:72`）；
- 改完要先 `dotnet build` 再等 Unity 重导，源码与 DLL 失配要再加一道检查；
- `Plugins/` 默认是 AOT 侧，进热更清单要另配；
- 编辑器里单步调试要靠 pdb。

不推荐。
